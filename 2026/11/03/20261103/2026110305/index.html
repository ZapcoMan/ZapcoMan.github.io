glibc 升一版，我的 exploit 废一次：fastbin dup 打到 safe-linking 堆利用断代史

2026-11-03 #漏洞利用#堆溢出#tcache#fastbin#unsorted bin#UAF#safe-linking#glibc#FSOP

堆上没有返回地址可以覆盖。

这是初学者第一次转做堆题时最困惑的地方：栈溢出你只要算偏移、填地址；可堆利用里，你打开 gdb，看到的是一堆 0x555555559290 这样的地址，既不知道哪个字段有意义，也不知道该把什么值写进去。

真正的原因是：堆溢出的攻击面不是代码，而是分配器自己的元数据。 你写的每一个字节，都是在骗 malloc 和 free 相信一些不成立的事实。

本文仅用于授权环境下的漏洞研究与 CTF 学习，示例针对本地自编译靶机。请勿用于任何未授权系统。

一、先看懂一个 chunk 长什么样

glibc 的 malloc 在 64 位下以 16 字节为粒度。你 malloc(0x20)，它实际给你的是一个 0x30 大小的 chunk（0x20 数据 + 0x10 头部）。

size 字段的低 3 位是标志位

因为 chunk 大小一定是 16 的倍数，低 4 位本来就是 0，glibc 就拿低 3 位存状态：

位 名称 含义
bit 0 PREV_INUSE (P) 前一个 chunk 正在使用（1=用着，0=空闲）
bit 1 IS_MMAPPED (M) 这个 chunk 是 mmap 来的，不在主堆
bit 2 NON_MAIN_ARENA (A) 属于非主线程的 arena

所以 size = 0x31 意思是：chunk 大小 0x30，前一个 chunk 正在使用中。这个 0x31 你在 gdb 里会看到无数次。

空闲 chunk 的 user data 会被复用

一个 chunk 被 free 之后，它的 user data 前 16 字节就变成了链表指针：

偏移 字段 作用
+0x00 fd 指向下一个空闲 chunk（forward）
+0x08 bk 指向上一个空闲 chunk（backward）

在 tcache 和 fastbin 里只用到 fd（单向链表），在 unsorted bin / small bin / large bin 里 fd 和 bk 都用（双向链表）。

这就是漏洞的入口：如果程序在 free 之后还能写这块内存（UAF），或者能溢出到下一个 chunk 的头部，攻击者就能改写 fd，让下一次 malloc 返回一个任意地址。

二、tcache：glibc 2.26 送的大礼

2017 年发布的 glibc 2.26 引入 tcache（thread cache），本意是性能优化——每个线程维护一份小 chunk 缓存，避免每次都去抢 arena 锁。

它长这样：

属性 值
bin 数量 64 个
覆盖范围 chunk 大小 0x20 ~ 0x410
每个 bin 容量 7 个
链表方向 LIFO（后进先出）
空闲标记 fd 指向下一个，key 存 tcache 指针
取用检查 glibc 2.29 前几乎不检查

最后一行是关键。glibc 2.29 之前，tcache 的 malloc 路径完全不校验 fd 指向的地址是否合法——它只看这个 bin 里有没有东西。

tcache poisoning：改一个 fd 就够了

两个 malloc 就拿到任意写原语。 这就是 tcache 让堆利用”变简单十倍”的含义——它把原本需要精心构造的 fastbin 攻击，压缩成了”改 8 个字节”。

三、fastbin dup：tcache 出现之前的经典

在 tcache 之前，小 chunk 走的是 fastbin。fastbin 的规则更严一点：

差异点 tcache fastbin
范围 0x20 ~ 0x410 0x20 ~ 0x80（默认）
每 bin 上限 7 无
分配检查 2.29 前无 检查 chunk 大小是否匹配
相邻合并 不合并 不合并

因为 fastbin 会检查 chunk->size 是否属于当前 bin，直接像 tcache 那样随便写目标地址是不行的。于是有了 fastbin dup——利用 double free 把同一个 chunk 挂两次，制造出”链表里有环”的状态：

接着按顺序取三次，第三次取到的还是 a，此时改掉 a->fd 指向目标，再取两次就拿到目标地址。

前提是能绕过 double free 检测：glibc 会检查”要 free 的 chunk 是不是就是当前 bin 的头”，所以中间必须插一个 b 把它顶下去。

四、unsorted bin：泄露 libc 的正门

前面两个 bin 解决”写哪里”，unsorted bin 解决”libc 在哪”。

当一个 chunk 被 free 且不属于 tcache/fastbin（太大，或对应的 bin 满了）时，会先进入 unsorted bin。关键点：unsorted bin 是唯一一个 fd/bk 会指向 main_arena 的结构。

所以只要把这个 fd 读出来，就拿到了 main_arena 附近的地址，减去固定偏移就是 libc 基址。

这是堆题里最常见的 libc 泄露方式，比栈题里的 puts@got 更”顺带”——你本来就要操作 chunk，泄露是副产品。

常见套路：让 chunk 同时进两个 bin

一个非常经典的组合是：先用 tcache 塞满，把本该进 tcache 的 chunk 逼进 unsorted bin。

反过来，也可以先把 unsorted bin 里的 chunk “捞”回来，利用 malloc 时的拆分行为制造重叠 chunk。

五、safe-linking：glibc 2.32 的转折点

2020 年的 glibc 2.32 引入 safe-linking，直接把”随便写 fd”这条路堵住了一半。

原理很朴素：存进 fd 的不再是裸指针，而是”指针异或上自身地址右移 12 位”。

  • 写入时：chunk->fd = (chunk_addr >> 12) ^ next_ptr
  • 读取时：next = (chunk_addr >> 12) ^ chunk->fd

这意味着：

攻击者想干的 safe-linking 之前 safe-linking 之后
把 fd 改成目标地址 直接写 必须先知道 chunk 自身地址
需要的信息 无 一个堆地址

于是攻击链被拉长了一步：你必须先泄露一个堆地址，才能算出该往 fd 里写什么。

这也解释了为什么 2.32 之后的堆题，几乎都会给你一个”打印 chunk 内容”的功能——没有堆泄露，tcache poisoning 直接失效。

六、glibc 2.34：hook 被删了

这是堆利用历史上最大的一次地震。

在这之前，__free_hook 是”万能终点”——不管你用什么手段拿到任意写，最后都把 __free_hook 写成 system，然后 free("/bin/sh")，收工。因为它足够简单、足够稳定，几乎成了堆题的默认答案。

glibc 2.34（2021 年 8 月）移除了 __free_hook、__malloc_hook、__realloc_hook、__memalign_hook。

官方理由很正当：这些 hook 在几乎所有程序里都是 NULL，却要在每次 malloc/free 时多做一次判断，是纯粹的浪费。

但副作用是：一代堆题的解法集体失效。

版本-目标对照表（务必按此核对）

glibc 版本 __free_hook tcache fd 编码 主流终点
≤ 2.25 有 裸指针 __free_hook / __malloc_hook
2.26 ~ 2.28 有 裸指针 __free_hook（tcache 时代最爽）
2.29 ~ 2.31 有 裸指针（+key 查重） __free_hook
2.32 ~ 2.33 有 safe-linking __free_hook，但要多一步堆泄露
≥ 2.34 已删除 safe-linking FSOP / 栈返回地址 / setcontext

七、2.34 之后打哪里

hook 没了，但”任意写”这个原语本身还在。问题变成：往哪里写，才能变成控制流？

按可靠性排序，目前主流的四类终点：

① FSOP：打 FILE 结构

_IO_2_1_stdout_、_IO_list_all 这些 FILE 结构里存着函数指针。通过伪造 vtable 或者改写 _IO_file_jumps，可以在 printf/exit 时劫持控制流。

最常用的是 house of apple 2，它利用 _IO_wfile_overflow 的调用链，对 glibc 版本适应性较好（2.35+ 仍有效）：

② 栈上返回地址

如果有栈地址泄露，直接写返回地址最干净。缺点是必须拿到栈地址，而堆题通常不给。

③ setcontext + 61

setcontext+61 处会从 ucontext_t 结构里恢复一组寄存器，包括 rsp 和 rip。把 __free_hook 换成它，就能做 SROP 式的寄存器控制。2.34 之后仍然是有效手段。

④ TLS 里的 dtor / exit_funcs

__exit_funcs 里的 flavor/fn 指针，以及 TLS 的 tls_dtor_list，都是”程序退出时会被调用”的位置。缺点是对堆地址布局要求较高。

一句话总结：2.34 之后，堆利用从”找 hook”变成了”找 FILE 结构”——难度上去了，但没有本质变化。

八、UAF 与 off-by-one：两个最朴素的原语

上面讲的都是”利用”层面，但堆漏洞的成因其实只有几类，最常见的是这两个：

UAF（Use After Free）

修复只要一行：free(ptr); ptr = NULL;。但现实中忘写的地方极多。

off-by-one / off-by-null

或者：

单字节溢出看起来无害，但打在 chunk 的 size 字段上就能改标志位、制造 chunk 重叠——这是 poison null byte 系列技巧的起点。

原语 一句话 典型后果
UAF free 后指针没清 直接读写已释放内存
double free 对同一指针 free 两次 链表成环
off-by-one 多写 1 字节 改相邻 chunk 的 size
off-by-null 写了个 \0 清除 PREV_INUSE，制造重叠
堆溢出 写超当前 chunk 改下一个 chunk 的头部

九、从防御视角看

堆利用能成立，根因和栈溢出一样朴素：程序在释放内存后仍然信任那个指针，或者允许写入超出分配长度的数据。

对应的工程化防御手段，按性价比排：

层次 手段 效果
源码 free 后立即置 NULL 消除 UAF（最有效、最便宜）
源码 换用 std::vector / Rust 所有权 / 智能指针 从语言层消除堆错误
编译 ASan（-fsanitize=address） 检测 UAF、越界，开发期必开
编译 -D_FORTIFY_SOURCE=3 编译期插桩检查
运行时 glibc 自身的 tcache 加固（key、safe-linking） 抬高利用门槛
分配器 换用 hardened allocator（Scudo、mimalloc-secure） 元数据隔离

一句实话：glibc 的每一次”加固”都是在补自己几十年前的设计债。tcache 是为了性能加的，结果因为它几乎没有检查，反而成了最好打的入口——这是性能与安全之间一次非常典型的权衡失误。

十、小结

堆和栈的根本差异，可以浓缩成一张表：

栈溢出 堆利用
攻击对象 返回地址（代码指针） 分配器元数据（fd/size）
核心动作 覆盖 欺骗
前置信息 缓冲区到返回地址的偏移 chunk 布局 + 堆地址（2.32+）
libc 泄露 借输出函数 借 unsorted bin
终点 system / one_gadget hook（已死）→ FSOP
版本敏感度 低 极高

最后这句最重要：堆题的第一步永远不是写 payload，而是 ldd --version。同一个 exploit 脚本，在 glibc 2.31 上通杀，在 2.35 上可能连第一个 malloc 都过不去。按版本建模，是这个领域唯一可靠的方法论。

下一篇回到”写”的能力本身——如果程序允许你任意地址任意写，但只能通过一个 printf 来实现，你能做到什么？答案是一个 %n。
