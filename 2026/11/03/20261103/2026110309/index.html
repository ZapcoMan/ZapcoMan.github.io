AES-256 二十年没被破过一次，泄露的数据却越来越多：密码学实战的七类"用法漏洞"，从 ECB 重排到 RSA 共模

2026-11-03 #密码学#侧信道#密码学攻击#ECB#CBC#Padding Oracle#长度扩展攻击#RSA#弱随机数#TLS#国密

1998 年，Daniel Bleichenbacher 在 CRYPTO 会议上演示了一件事：只要服务器对”RSA 填充是否正确”给出不同的反应，攻击者就能用大约一百万次查询，把一个他完全没有私钥的密文完整解出来。

十九年后的 2017 年，三位研究者把这个方法原封不动地重跑了一遍，扫描 Alexa 前 100 的站点，27 个存在同样的漏洞，并且在 Facebook、PayPal 等厂商的资产上成功复现。代码一行没改，论文一个字没变。

这就是密码学实战最反直觉的地方：十九年里，RSA 的数学没有被撼动过分毫，但同一个洞还在原地开着。

我写过一篇《古典密码学 (一)》，讲凯撒和 Atbash 的 Python 实现，然后就断了。那条线其实一直没接上——从”手写一个替换密码”到”看懂一个真实系统的加密为什么失效”，中间隔着的正是这篇文章。

它不讲算法怎么设计，只讲算法被用错的七种方式。

零、先把责任划清：被攻破的从来不是算法

每次出现大规模数据泄露，新闻标题里总有一个熟悉的句式：”某加密算法被破解”。从业者看到这种标题应该先条件反射地问三个问题：

  1. 对手模型是什么？ 攻击者能选择明文吗？能观察时间吗？能反复提交吗？
  2. 复杂度是多少？ 是 2^40 还是 2^120？前者一台机器几天，后者宇宙寿命不够。
  3. 影响哪个实现？ 是算法本身，还是某个库、某个模式、某个参数？

这三个问题问下来，99% 的”算法被破解”会现出原形——出问题的不是算法，是算法周围那一圈没人负责的东西。

我把责任分三层：

层次 出问题的东西 典型代表 攻击者需要什么 实战占比
算法 数学结构被找到弱点 MD5/SHA-1 碰撞、理论上的 AES 简化轮攻击 极强的密码分析能力 极低
协议 交互流程本身泄露信息 POODLE、ROBOT、DROWN、0-RTT 重放 一个能持续观察差异的位置 中
实现 / 用法 模式、参数、随机数、比较方式、错误处理 ECB 滥用、固定 nonce、短路比较 通常只需要读代码 绝大多数

MD5 和 SHA-1 是唯一真正意义上”算法层被打破且造成实战影响”的例子——Flame 恶意软件用 MD5 碰撞伪造了微软的代码签名证书（2012），SHAttered 用 2^63 的代价造出两个 SHA-1 碰撞的 PDF（2017）。除此之外，AES、SHA-256、RSA-2048 至今没有实用攻击。

而 AES 被引用最多的”攻击”，是 biclique 方法对简化轮数版本的加速，对完整 AES-128 的理论复杂度仍在 2^126 量级——这个数字的意思是：没有任何实际意义。

所以技能里那条原则是对的：一切破解以”能否拿可控优势”为准，纯理论不列为成果。

而”可控优势”这四个字，恰好是后面七类攻击的共同结构。它们全部在回答同一个问题：这个系统多告诉了我一个比特吗？

一、ECB：密文自己把结构画出来了

ECB 是所有分组密码模式里最简单的一个：每个块独立加密，C_i = E_K(P_i)。

它的后果是一句话——相同的明文块，永远产生相同的密文块。这叫等值泄露（equality leak）。

网上流传最广的演示是那张”ECB 加密后的企鹅图仍能看出轮廓”，但那张图其实把问题讲小了。图像轮廓只是视觉上的巧合，真正致命的是等值泄露在业务数据里的表现。

1.1 Adobe 2013：一亿五千万条记录，密码一眼可见

2013 年 Adobe 泄露 1.53 亿条用户记录。事后分析发现，密码字段用的是 3DES 的 ECB 模式，而密码提示是明文存储的。

这意味着研究者不需要破解任何东西，只要对密文做一次 GROUP BY，就能直接得到：

  • 有多少用户使用了同一个密码（密文相同的即同一密码）
  • 哪些是弱密码（配合明文的密码提示，猜中的概率极高）
  • 哪些账号属于同一批批量注册（密文完全一致）

ECB 把一个加密问题，变成了一个统计问题。

当攻击者能控制一部分明文、又能看到整体密文时，ECB 就退化成了一个乐高积木。

CBC 的解密公式是这个：

这个公式里藏着一个非常直接的杠杆：C_{i-1} 是攻击者能看到的密文，而它和明文之间只隔了一个 XOR。

所以对 C_{i-1} 的第 j 个字节做一次异或，P_i 的第 j 个字节就会发生同样幅度的异或，位置精确、误差为零。这就是 CBC bit-flipping。

代价是 P_{i-1} 会整块变成乱码——因为 C_{i-1} 同时是第 i-1 块解密结果的异或对象，改了它，前一块就毁了。

战术因此变得很明确：把攻击目标放在第二块之后，让第一块去吃那口乱码。

2.2 为什么它比 padding oracle 更常见

因为它的门槛极低：不需要任何反馈，不需要报错信息，不需要时序。

只要满足三个条件，一次请求就能完成篡改：

  1. 用了 CBC 模式
  2. 明文结构可预测（知道要改的字符在原位是什么）
  3. 没有 MAC

第三条是全部问题的根源。CBC 本身只提供机密性，不提供完整性。而”加密的 cookie”这种设计，绝大多数实现者都只做了加密，忘了认证。

这就是为什么现代密码学工程的第一条铁律是 Encrypt-then-MAC，或者干脆用 AEAD（GCM / ChaCha20-Poly1305）。AEAD 会先验 tag 再解密，改一个比特整个包直接丢弃，bit-flipping 无从下手。

顺带说一句，AES-GCM 的 nonce 复用比 CBC 的 bit-flipping 严重得多。CBC 篡改只是”改内容”，GCM 的 nonce 复用会直接泄露 GHASH 的认证密钥 H，攻击者从此可以伪造任意消息的合法 tag——那不是读权限，那是签名权。

三、Padding oracle：一个布尔值就够了

这是整个密码学实战里最漂亮的一类攻击，也是最能说明”一个比特的价值”的案例。

3.1 原理：把”填充对不对”变成一个可查询的预言机

CBC 解密后要去掉 PKCS#7 填充：最后一个字节是 n，就说明末尾有 n 个字节的值都是 n。如果不符合这个规则，解密就失败。

问题来了——服务端怎么告诉客户端”解密失败”？

  • 返回 500
  • 返回 200 但内容是 “invalid token”
  • 返回 200 但响应体长度不同
  • 报错快一点，成功慢一点

这四种反应里任何一种，只要成功和失败能被区分，攻击者就拿到了一个预言机（oracle）：我可以问任意密文”它的填充合法吗”，你回答是或否。

而填充合法性这一个比特，足以还原整个明文。

3.2 怎么从一个比特里抠出一个字节

设目标块是 C_i，它解密后的中间值是 I_i = D_K(C_i)，我们不知道 I_i，但知道 P_i = I_i ⊕ C_{i-1}。

攻击者构造一个伪造的 C' 当作 C_{i-1} 发过去。服务端算 P' = I_i ⊕ C'，然后检查 P' 的填充。

如果攻击者让 C' 的最后一个字节等于 g，那么 P' 的最后一个字节就是 I_i[15] ⊕ g。当这个值恰好等于 0x01 时（合法的单字节填充），预言机回答”合法”。

一个字节的明文出来了。 平均需要试 128 次（256 的一半）。

拿到最后一个字节后，把 C' 的最后一个字节固定成 I_i[15] ⊕ 0x02，让填充变成合法的两字节 0x02 0x02，然后开始爆破倒数第二个字节。如此往复，16 个字节全部恢复。

有个必须知道的细节：0x01 的歧义。当目标是最后一个字节时，guess 命中的可能是”恰好构成 0x01“，也可能是”恰好构成 0x02 0x02“之类的巧合。所以标准的实现要在 j == 15 时额外验证一次——改一下倒数第二个字节，如果预言机仍然返回合法，说明命中的是 0x02 0x02 而不是 0x01，需要换一个 guess。

这个坑我踩过，症状是整块明文最后两个字节始终不对，其他 14 个字节全对。

四、哈希的两个经典死法

4.1 长度扩展：为什么 H(secret ‖ msg) 是个错误设计

MD5、SHA-1、SHA-256、SM3 都基于 Merkle–Damgård 结构：消息被分块喂进压缩函数，上一块的输出作为下一块的初始状态。

关键在于——最终输出的摘要，就是最后一次压缩之后的内部状态。

这带来一个后果：如果签名方式是 sig = H(secret ‖ message)，攻击者拿到 sig 和 len(secret)，就能把这个 sig 直接当作压缩函数的输入状态，接着往后算，不需要知道 secret 是什么。

中间那串 padding 是 Merkle–Damgård 的填充字节（0x80 加若干 0x00 加长度），虽然不可见，但服务端解析时会把它当成消息的一部分——所以攻击者要做的只是把这段不可见字节原样塞进请求里。

三个防御答案，重要性递增：

  1. 用 HMAC——内外两层密钥，长度扩展打不通
  2. 用 SHA-3 / Keccak——海绵结构，输出不是内部状态
  3. 别把”哈希”当”签名”用

第三条才是根子上的问题。长度扩展不是 SHA-256 的缺陷，是”把摘要当 MAC”这个用法错了。

4.2 加盐挡得住彩虹表，挡不住 GPU

这是最常被误解的一条。盐的作用只有一个：让预计算失效。

  • 无盐：全世界的 123456 哈希都是同一个值，一张彩虹表通杀
  • 有盐：每个用户的 123456 哈希都不同，彩虹表作废，得逐个爆破

但盐完全不阻止针对单个哈希的暴力破解。因为盐是和哈希一起存的，攻击者拿到库就拿到了盐。

所以口令存储的强度不由”哈希算法是否被破”决定，而由”每次猜测的成本”决定：

算法 单卡速度量级 8 位随机口令（95 字符集）耗时 结论
MD5 ~10^11 H/s 小时级 等于明文
SHA-256 ~10^10 H/s 天级 勉强
bcrypt（cost 12） ~10^4 H/s 千年以上 可用
Argon2id（高内存） ~10^3 H/s 更久，且 GPU 优势被内存墙吃掉 推荐

表内为量级估计，具体随硬件变化。

看这张表就明白了：从 MD5 到 SHA-256，速度快了十倍，对爆破来说毫无区别；从 SHA-256 到 bcrypt，速度慢了一百万倍，这才叫防御。

原因在于 bcrypt 和 Argon2 是故意设计得慢且占内存的——它们的目标不是”输出不可逆”，而是”让可逆的成本高到不划算”。GPU 和 ASIC 擅长的是并行算简单函数，一旦要求每个候选值占用大量内存，并行度就被物理条件卡死了。

共用素数 两个 n 有公因子 有一批公钥 batch GCD
Wiener 私钥指数 d 过小（d < n^0.25/3） e 特别大 连分数展开
Franklin-Reiter 两条明文满足线性关系 已知 m2 = a·m1 + b SageMath

5.1 一句能记住的话

没有随机化填充的 RSA，本质上是一个确定性的公开置换——它就是非对称版的 ECB。

同一个明文用同一个公钥加密两次，密文完全一样。这一点和第一节讲的等值泄露是同一个病。而 PKCS#1 v1.5 和 OAEP 的作用，就是往每次加密里注入随机性，让同一个明文产生不同的密文。

所以当你看到一个”自研 RSA 加密”时，第一个要问的不是密钥长度，而是：**填充是怎么做的？**如果答案是”直接用 pow(m, e, n)“，那上面那张表里的攻击基本都能打。

5.3 共用素数：不是理论，是实测

2012 年的论文《Ron was wrong, Whit is right》做了一件很朴素的事：收集了 1160 万个 TLS 和 SSH 公钥，两两求 GCD。

结果是 0.2% 的密钥存在共享素数——这些设备的随机数生成器在生成素数时熵不足，撞车了。影响范围包括 0.4% 的 TLS 主机和 1% 的 SSH 主机。

**只要拿到两个共享素数的 n，两个私钥就同时破了。**因为 p = gcd(n1, n2)，剩下的就是一次除法。

这个案例值得记住的原因：它证明密码学的失败经常不在算法，而在**”生成密钥的那台机器当时有没有足够的熵”**。这就引出了下一节。

六、随机数：整栋楼最容易塌的那根柱子

密码学里所有”不可预测”都建立在随机数上：密钥、IV、nonce、盐、ECDSA 的 k。这一根柱子塌了，上面所有数学都白搭。

三个真实案例，一个比一个荒诞。

6.1 Debian OpenSSL（2008）：删了一行注释掉的代码

2006 年，一位 Debian 维护者为了消除 Valgrind 的内存警告，删掉了 md_rand.c 里的一行 MD_Update 调用——那行代码的作用是把未初始化内存混入熵池，看起来”不干净”。

后果是：OpenSSL 的 PRNG 只剩下了进程 ID 作为熵源。PID 最大 32768。

于是在 2006 年 9 月到 2008 年 5 月这两年时间里，所有在 Debian/Ubuntu 上生成的 SSH 密钥、TLS 证书、OpenVPN 密钥、会话密钥，全部只可能来自 32768 个候选值。

修复方式不是打补丁，是所有密钥必须重新生成。这是密码学史上最贵的一次代码审查。

6.2 Sony PS3（2010）：k 是个常数

ECDSA 签名需要为每条消息生成一个随机数 k。Sony 的固件里，k 被写死成了常数 4。

6.3 弱 PRNG 的通用打法

不用找那么极端的案例，日常遇到的更多是这种：

C 的 rand() 无种子或固定种子，线性同余 几个输出即可反推状态

统一的方法论是：收集足够多的输出，做熵估计和状态恢复。一个设计良好的随机源，输出应该通过卡方检验、没有周期性、和生成时间无关。而一个用时间戳播种的 PRNG，你甚至能从 token 里直接看出服务器的启动时间。

七、实现层：硬编码密钥、弱 KDF，和能被秒表量出来的比特

前面六类还都算”密码学用法”层面的错误，多少有点体面。这一节讲三种更接地气的——它们不涉及任何数学，但在真实项目里出现的频率最高。

7.1 硬编码密钥：技术债里最难还的一种

移动端和固件里，密钥经常直接躺在二进制里。常见位置和找法：

位置 怎么找
so / elf 的 .rodata strings libapp.so 之后筛 32 位以上的 base64 长串
BuildConfig / 常量类 反编译后全局搜 SECRET、KEY、AES
strings.xml / assets 解包后直接 grep
前端打包产物 搜 aes、CryptoJS、encrypt(

判定一条 base64 串是不是密钥，可以顺手做一次熵估计——真密钥的字符分布接近均匀，普通字符串不会。

硬编码密钥的麻烦不在于”泄露”，而在于它没法轮换。口令泄露了可以改，密钥泄露意味着所有历史密文全部作废，而重新加密全量数据通常是个没人敢排期的工程。所以这类问题一旦上线，往往会原样存在好几年。

7.3 时序侧信道：把毫秒变成比特

时序攻击的原理一句话：程序的执行时间依赖于它正在处理的秘密。

最经典的形态是短路比较——memcmp 在第一个不同的字节就返回，所以”前 3 个字节对了”和”前 0 个字节对了”花的时间不一样。这类差异通常在纳秒到微秒级。

于是问题变成：这么小的差异，在网络的噪声里还测得出来吗？

答案取决于信噪比，而信噪比取决于采样次数。一个实用的判断方法：

先测噪声底——同一个输入重复测，看中位数的波动范围。再测信号——两个不同输入的中位数之差。信号必须显著高于噪声底才算”可测”，否则就是自欺欺人。

远程场景下这道门槛高得多：一次 HTTP 往返可能 50ms，信号只有 1 微秒，相差五万倍。但这不代表测不出来——**网络抖动是随机的，会互相抵消；信号是系统性的，会累加。**采样足够多之后，均值会收敛到真实差异上。

Lucky Thirteen 就是这么打穿 TLS 的：它没有找到任何明文，只是发现”填充长度不同 → 参与 MAC 计算的数据量不同 → 耗时不同”，然后采样几十万次，把这个微秒级差异从网络噪声里捞了出来。

这也是技能里那句”时序侧信道（缩小到可测）”的含义——侧信道能不能用，不取决于差异有多小，取决于你能采样多少次。

八、TLS 二十年：一部”用法错误史”

把 TLS 的历史漏洞按时间排开，会发现一件很有意思的事：没有一次是”AES 被破了”。

年份 名字 本质 被利用的那个”用法”
2011 BEAST IV 可预测 TLS 1.0 用上一块密文当 IV
2012 CRIME 压缩率泄露 TLS 层压缩
2013 BREACH 同上 HTTP 响应压缩
2013 Lucky Thirteen 时序差异 MAC-then-Encrypt
2014 Heartbleed 越界读 没校验 length 字段
2014 POODLE padding oracle SSL 3.0 的填充检查
2015 FREAK / Logjam 降级到 512 位 出口管制时代的弱套件还在
2016 DROWN 跨协议 服务器同时开着 SSLv2
2016 Sweet32 生日碰撞 64 位分组（3DES）
2017 ROBOT Bleichenbacher 复活 RSA PKCS#1 v1.5
2020 Raccoon 时序 DH 的填充处理

这十一行里，被利用的东西依次是：一块 IV、一个压缩率、一次时序差、一个长度字段、一个错误码、一个填充字节。

全部是”多泄露了一个比特”的不同形态。没有一个是在数学上攻破了什么。

这也解释了为什么 TLS 1.3 的设计哲学是”减法”：删掉 CBC、删掉压缩、删掉 RSA 密钥交换、删掉重协商，只留 AEAD 和 (EC)DHE。当所有能泄露差异的分支都被删掉，攻击面就消失了。

顺带说 0-RTT。TLS 1.3 为了让重连更快，允许客户端在第一个 flight 就带上数据。这部分数据天然不防重放——攻击者录下来重发一次，服务端就会再执行一次。这是性能与安全的显式取舍，不是 bug。用 0-RTT 承载”转账””下单”这类非幂等操作，就是把这个取舍用错了地方。

九、拿到一个加密系统，先问这七个问题

上面七类攻击，其实可以由一组黑盒问题推出来。这是我实际做事时的顺序：

# 问题 得到的答案指向
1 密文长度是不是块大小（8/16）的整数倍？ 是 → 分组密码；不是 → 流密码或 AEAD
2 同一明文加密两次，密文一样吗？ 一样 → ECB，或固定 IV 的 CBC
3 改密文中一个字节，服务端怎么反应？ 出现两种以上反应 → padding oracle / bit-flipping 入口
4 有没有 MAC 或 tag？在哪一段？ 没有 → 篡改类攻击直接可用
5 密钥、IV、nonce 从哪来？ 时间戳、计数器、rand() → 弱随机
6 签名是 H(secret‖msg) 还是 HMAC？ 前者 → 长度扩展
7 错误信息、响应时间、响应长度有几种？ 每一种差异都是一个比特

**如果只能问一个问题，问第 3 个。**它同时揭示了”有没有完整性校验”和”错误处理是否统一”两件事，而这两件事决定了后面所有攻击的可行性。

这七个问题不需要源码，不需要逆向，全部是黑盒可观测的。密码学攻击的入口，绝大多数时候就摆在 HTTP 响应里。

十、三条不会过时的原则

写到这里，防御其实已经很清楚了。我把它们压缩成三条，因为这二十年里所有”复活”的漏洞，都是因为违反了其中一条。

原则一：认证先于解密

Encrypt-then-MAC，或者直接用 AEAD。先验 tag，验不过就整包丢弃，一个字节都不解释。

反过来（MAC-then-Encrypt，或者干脆没有 MAC）就是 POODLE、Lucky Thirteen、所有 bit-flipping 的土壤。判断标准很简单：**解密函数在验证完整性之前，有没有对密文做过任何解析？**有，就是错的。

原则二：所有涉及秘密的比较，都必须恒定时间

普通字符串比较在第一个不同字节就返回，攻击者可以通过测量响应时间逐字节推出正确值——每个字节最多试 256 次，但配合统计方法通常几十次就够。

这条原则的可怕之处在于：它在功能测试里永远是对的，只有在有人拿秒表量的时候才暴露。

原则三：不要自己拼

用 libsodium，用平台的 AEAD API，用经过审计的库。

原因不是”你不够聪明”，而是密码学的正确用法是一组反直觉的约束，每一条都容易被”优化”掉：IV 不能复用、nonce 不能重复、比较不能短路、错误码必须统一、填充必须随机。这些约束在代码评审时看不出来，在压测时看不出来，只在被攻击时表现出来。

每一代人都觉得自己能正确使用 RSA。然后 Bleichenbacher 就复活一次。

补一句关于国密

这几年做国密改造的项目很多，而改造中最常见的三个错误恰好对应上面三节：

错误 对应问题 后果
SM4/ECB 模式选错 等值泄露，等同没加密
SM2 签名复用 k 随机数 私钥可直接算出
SM3 当 HMAC 用（SM3(key‖msg)） 哈希用法 长度扩展

**合规不等于安全。**等保测评看的是”用了什么算法”，攻击者看的是”怎么用的”。这中间的差距，就是这篇文章存在的理由。

十一、小结

回到开头那个 1998 年的故事。

Bleichenbacher 的攻击之所以能活十九年，不是因为它精妙，而是因为它利用的东西太朴素了——一个系统对”成功”和”失败”给出了不同的反应。

密码学的数学部分是可靠的。AES 会一直是安全的，SHA-256 也会一直安全下去。真正不可靠的是”人以为自己正在使用数学”这件事：把 ECB 当成 AES、把哈希当成签名、把 == 当成安全比较、把时间戳当成随机数。

这七类攻击有一个共同的名字，叫用法漏洞。它们不在论文里，在代码里。

而检查它们，往往只需要问一句：这个系统，多告诉了我一个比特吗？
