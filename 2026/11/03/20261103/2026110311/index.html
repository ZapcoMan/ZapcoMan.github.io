一条 nonce 毁掉整条曲线：ECDSA 的五类致命错误，从索尼的常数 4 到格攻击

2026-11-03 #密码学#ECDSA#椭圆曲线#数字签名#nonce#格攻击#LLL#EdDSA#无效曲线攻击#区块链安全

2010 年 12 月，柏林，27C3。

fail0verflow 站在台上，说了一句让全场先愣住再爆笑的话：索尼在 PS3 的 ECDSA 实现里，把每次签名要用的随机数 k 写死成了常数 4。

屏幕上打出私钥的十六进制。索尼花了四年建立的主信任根，在四十分钟的演讲里永久失效——而且无法通过固件更新修复，因为根密钥一旦泄露，换密钥就等于让所有已售出的机器拒绝运行新游戏。

这件事在密码学史上的地位很特殊：它不是因为算法弱，也不是因为实现有 bug，而是因为一个人觉得”随机数太麻烦，写个常数吧”。

ECDSA 的全部安全性，悬在这一条线上：每次签名，k 必须唯一且不可预测。这条线断了，上面所有数学一起作废。

而这根线有五种断法。

一、先把 ECDSA 在做什么说清楚

所以 ECDSA 的安全模型可以压缩成一句话：**k 必须每次不同、且不可预测。**剩下的攻击，都是这句话的否定形式。

1.1 为什么 256 位的曲线等于 3072 位的 RSA

这经常让人困惑：AES 用 128 位密钥，RSA 用 2048 位模数，椭圆曲线只要 256 位——位数差这么多，凭什么说强度相当？

因为它们的”破解难度”对应的数学问题不同：

体系 依赖的难题 已知最好算法 复杂度
RSA / DH 大整数分解 / 有限域离散对数 数域筛法（NFS） 亚指数级，exp(O(n^(1/3)))
ECC 椭圆曲线离散对数 Pollard’s rho 纯指数级，O(√n)

RSA 的破解复杂度是亚指数的：随着位数增加，难度增长得比指数慢，所以必须用很长的模数。而 ECC 的破解复杂度是纯指数（更准确说是 O(√n)，靠 Pollard rho），位数每加一倍，难度平方增长。

于是 256 位曲线给出约 2^128 的强度，和 AES-128 对齐；3072 位 RSA 也是约 2^128。

这个效率差距是 ECC 在移动端、物联网、区块链上全面替代 RSA 的根本原因——同样的安全强度，密钥小十倍，运算快一个数量级。

但也正因为它”用更少的位达到同样的强度”，它没有任何冗余：256 位曲线上出现一个 8 比特的偏差，就损失了 8 位强度。而 RSA 的参数里，模数长度、指数大小这些量都有大量富余。

这是理解本文后面所有攻击的前提：ECC 的安全边界贴得很近，容错空间很小。

2.2 PS3：k = 4

索尼的实现里，k 被固定成 4。于是所有签名的 r 都相同，任意两个签名凑一起就能算出私钥。

fail0verflow 在演讲里说得很克制：”我们不是在破解加密，我们只是在做除法。”

这件事最刺人的地方在于不可挽回性：对称密钥泄露可以换，口令泄露可以改，但签名根密钥泄露意味着整个信任模型崩塌。索尼最后只能靠新固件 + 新硬件版本（3.56+ 的 metldr 更新）来阻断，老机器永久处于可被签名的状态。

2.3 2013 年 Android：随机数在开机早期不够随机

2013 年 8 月，比特币社区发现大量钱包被清空。原因不是私钥被偷，而是 Android 的 SecureRandom 在系统启动早期熵池未初始化完成时，会退化成可预测的伪随机——多个应用在同一次开机中生成的 k 相同。

这就是 CVE-2013-7372。受影响的钱包包括 Bitcoin Wallet（com.btcwire）等，实际损失估计在数百 BTC。

**关键教训：随机数的问题是环境问题，不是代码问题。**代码里写的是 SecureRandom()，看起来完全正确，错的是它运行时的那台机器当时有没有足够的熵。

2.4 区块链上的 k 复用是持续发生的

因为区块链把所有签名都公开了，所以任何人都能做这个统计：把链上所有 (r, s, z) 拉下来，按 r 分组。

  • 2013 年那波 Android 钱包，攻击者就是这么扫的
  • 后续发现的还有：错误的硬件钱包固件、导入导出过程中被复制状态、以及把 k 存在持久化存储里忘了更新

这也说明一件事：**在公开日志的环境里，”k 复用”这种错误会被立刻、大规模、不可逆地利用。**攻击者不需要接触你的系统，只需要读你的公开数据。

2.5 生产环境里 k 是怎么重复的：几乎都不是”写了个常数”

PS3 那种”写死成 4”是极端案例。真实系统里的 k 复用，绝大多数来自环境而不是代码：

成因 典型场景 为什么
fork 后子进程继承 RNG 状态 多进程 Web 服务器 父进程 seed 一次，fork 出 N 个子进程，各自从同一个状态开始
虚拟机快照回滚 云环境、测试环境 快照保存了 RNG 内部状态，回滚后重放同一段序列
容器镜像内置固定种子 Docker 镜像构建时固化了一个种子文件，所有实例共享
硬件 TRNG 故障后静默降级 嵌入式、HSM 真随机源坏了，退回伪随机，没有告警
部署脚本复制了同一个 seed 文件 集群批量部署 为了”统一配置”，把带种子的文件一起拷了
多进程共享 /dev/urandom 的早期读取 启动竞态 熵池未初始化完成，多个进程读到相同输出

这张表解释了一个关键事实：k 复用往往不是”每次都一样”，而是”某一批签名撞在一起”。

所以检测方式必须是”全量按 r 分组”，而不是”抽查两个签名看看”。也是为什么”我们本地测试没复现”完全没有意义——问题只在特定环境、特定时刻触发。

顺带说一句，这也是为什么 RFC 6979 值得被强制推行：它把 k 的来源从”系统环境”变成了”私钥 + 消息的确定性函数”，一次性消灭了上表里全部六行。

三、错误二：k 有偏——格攻击，比复用更隐蔽也更漂亮

大多数人以为”k 不能复用”就够了。真实情况是：k 不需要完全复用，只需要”不够随机”，就能被恢复。

这是 ECDSA 攻击里最优雅的一类。

3.1 直觉：把”随机数”改成”小数字”

那么 a + b·d mod n 这个值，就”恰好”落在区间 [0, 2^128) 里。这是一个关于 d 的近似线性方程：

每个签名给出一条这样的方程，m_i 是未知的整数（模运算产生的”绕圈次数”）。这就是 Hidden Number Problem（HNP），Boneh 和 Venkatesan 在 1996 年就给出了解法：构造格（lattice），用 LLL 算法求最短向量，d 就在里面。

3.2 偏差一个比特就够

关键的一点：偏差不需要很大。

  • k 完全复用：2 个签名就够，纯代数
  • k 的高 8 位固定（比如永远以 0x00 开头）：几十到几百个签名，格攻击
  • k 由”取模引入偏差”的随机数生成：偏几个比特，几百到几千个签名

为什么？因为每多一个签名，就多一条方程，噪声被平均掉一点。签名数量足够多时，即使偏差只有 4 个比特，格也会把 d 逼出来。

2019 年的论文《Biased Nonce Sense》扫描了比特币和以太坊的链上签名，用 HNP + LLL 找到了数百个存在有偏 nonce 的私钥。这些实现的共同点是：用了一个”看似随机、实际有偏”的方式生成 k（比如对大随机数取模，或者从一个窄范围的 PRNG 取值）。

3.3 一个可以记住的判断标准

k 的问题 需要的签名数 攻击方式
完全复用 2 代数除法
高/低位固定若干比特 数十 ~ 数百 格（LLL）
有偏几个比特 数百 ~ 数千 格（LLL）
来自弱 PRNG（如 rand()） 取决于能否预测状态 状态恢复
真正均匀随机 不可行 —

这张表的用途是：审计时不要只查”有没有复用”，要查”k 是怎么生成的”。

k = random.randint(0, 2**256) % n 这种写法，看起来完全随机，但因为 2^256 % n ≠ 0，取模会引入极其微小的偏差——通常不足以攻击。但如果写成 k = random.randint(0, 2**64)，那就是灾难。

判断标准很朴素：k 的取值范围必须覆盖整个 [0, n)，且分布必须均匀。

四、错误三：无效曲线攻击——当对方给你的点不在曲线上

这一类错误换了个方向：不攻击签名，攻击密钥交换。

ECDH 的流程是：A 发公钥 Q_A = d_A · G 给 B，B 算 S = d_B · Q_A；B 发 Q_B = d_B · G，A 算 S = d_A · Q_B。

问题在于：如果实现不验证”收到的点确实在当前曲线上”，会发生什么？

攻击者可以构造一个点 P，它满足另一条曲线 E’ 的方程（而不是约定好的那条）。这条 E’ 的阶可以被设计成小素数 ℓ 的乘积。

于是受害者的计算 S = d · P，其 x 坐标只会落在 ℓ 个可能值里——攻击者穷举这 ℓ 个值，就能知道 d mod ℓ。

对小素数 ℓ 重复这个过程（每次换一个 E’），就得到一堆 d mod ℓ₁, d mod ℓ₂, ...，用中国剩余定理拼起来，整个私钥 d 就出来了。

这就是 Biehl、Meyer、Müller 在 2000 年提出的无效曲线攻击（invalid curve attack）。它要求：

  1. 攻击者能反复让受害者用自己的点做标量乘
  2. 受害者不验证点的曲线归属

第一条在很多协议里天然成立（ECDH 握手里攻击者就是主动方），第二条则是最常见的实现疏漏。

**防御只需要一行：验证 y² = x³ + ax + b。**另外还要验证点不是无穷远点，且阶不是 1。

Bouncy Castle 在 2015 年修过一类相关问题；很多自研的 ECDH 实现至今没有这个检查，因为它们”用的是标准库的曲线参数”，就以为点也一定是合法的——曲线参数是标准库给的，点是对手给的。

五、错误四：曲线参数本身有问题

再往上一层：如果曲线是错的，前面所有讨论都没意义。

5.1 小群：Pohlig–Hellman 直接拆解

如果曲线的阶 #E 可以分解成一堆小素数 ℓ₁·ℓ₂·…，那么 ECDLP 就退化成在每个小素数上分别求解，再用 CRT 拼起来（Pohlig–Hellman）。难度由最大的那个素因子决定，而不是总位数。

所以曲线的阶必须是”一个大素数乘以一个很小的余因子”。这就是为什么标准曲线的余因子（cofactor）通常只有 1、4 或 8——余因子越大，小群攻击的空间越大。

5.2 奇异曲线：Smart 攻击，多项式时间

如果曲线的判别式 4a³ + 27b² ≡ 0 (mod p)，这条曲线是奇异的（singular）。经过有理参数化，ECDLP 会退化成有限域上的加法/乘法问题——可以在多项式时间内求解。

具体到一种特殊情况：#E(Fp) = p 的曲线叫异常曲线（anomalous curve）。Smart（1999）、Satoh–Araki、Semaev 各自独立发现了对它的攻击：用 p-adic 提升把点提升到 Q_p 上，在那里椭圆曲线群同构于加法群，离散对数就变成一次除法。

**多项式时间。**不是”难一点”，是”完全不安全”。

5.3 所以：永远不要自己生成曲线参数

这两条合起来给出一个铁律：

曲线参数只能用标准化的、经过大量分析的曲线：P-256、secp256k1、Curve25519、Ed25519。

自选 a、b、p 的曲线，极可能同时踩中”阶有小因子”和”可被 MOV 归约到有限域”这两个坑——后者指嵌入度太小，把 ECDLP 搬到 F_(p^k) 上用指标计算法解，复杂度随 k 减小而急剧下降。

顺便一提，这也是为什么 NIST 曲线常被质疑：不是因为它已被攻破，而是因为参数来源不透明——你不知道生成参数时有没有埋后门（Dual_EC_DRBG 事件让这种怀疑有了实证基础）。Curve25519 之所以流行，一个重要原因就是它的参数是”可验证地”生成的（nothing up my sleeve）。

5.4 怎么检查一条曲线的参数是否安全

如果项目里出现了非标准曲线（自研、合作方提供、或者某个 SDK 内嵌的），有五个必查项：

检查项 合格标准 不合格的后果
曲线阶 #E 大素数 × 小余因子（h ≤ 8） 小群攻击 / Pohlig–Hellman
判别式 4a³+27b² 在 Fp 上非零 奇异曲线 → Smart 攻击，多项式时间
嵌入度 k 足够大（> 20） MOV 归约到有限域，指标计算法
基点 G 的阶 等于那个大素数 子群攻击
参数来源 可验证生成 / 标准文档 后门嫌疑

理由很简单：检查只能发现已知的几类问题，而曲线的安全性需要几十年的公开分析来建立信心。这不是一个可以在代码评审里解决的事。

六、错误五：验证侧的三个疏漏

前面都是签名方的问题。这一节是验证方——而验证方的错误同样致命，甚至更隐蔽。

6.1 不检查 r、s 的取值范围

标准要求验证前检查 r, s ∈ [1, n−1]。如果实现跳过了这一步：

  • r = 0、s = 0 会造成除零或异常，可能泄露信息
  • 更严重的是，某些实现会在 r 或 s 为特殊值时退化，产生可预测的验证结果

这是最好修、最常被忘的一条。

6.2 签名可延展性（malleability）

ECDSA 有一个结构性特点：如果 (r, s) 是合法签名，那么 (r, n − s) 也是合法签名。

因为验证时只用到 s⁻¹，而 (n−s)⁻¹ = −s⁻¹，最终算出的点的 x 坐标相同（y 坐标符号翻转不影响 x）。

后果在区块链上被放大过：任何人拿到一笔已广播但未确认的交易，都能改掉 s 生成一个新的合法签名，从而改变交易的哈希值（TXID）。2014 年 Mt.Gox 把丢币归咎于”交易可延展性”（虽然后来查明主要是别的问题），但这确实是比特币后来引入 SegWit 的动机之一——把签名从 TXID 的计算里挪出去。

顺带说，这也是为什么 Schnorr 签名（BIP340）被引入：Schnorr 天然不具有这种延展性（配合特定的 nonce 派生规则）。

6.3 不验证公钥本身

和第四节同源：验证签名时，如果 Q 是一个不在曲线上的点，某些实现会算出”碰巧通过”的结果。验证方必须做和 ECDH 方一样的检查。

6.4 一个真实世界的高危场景：JWT 的 ES256

JWT 是最常见的”把 ECDSA 用在业务里”的场景。它的签名算法标记在 token 头部：

问题恰恰出在”算法写在 token 里”这件事上。如果验证方读取 token 头来决定用什么算法验证，就打开了三扇门：

第一扇：算法混淆。攻击者把 alg 改成 HS256，然后拿服务端的公钥当作 HMAC 密钥，自己签一个 token。验证方一看 alg=HS256，就用”公钥”作为 HMAC 密钥去验——因为公钥是公开的，能算出来，验签通过。

这个错误的本质是：**ECDSA 的公钥和 HMAC 的密钥，在代码里都是”一串字节”。**类型系统不区分，库也不区分。

**第二扇：alg: none。**某些库的历史版本允许 alg 为空，直接跳过验证。

第三扇：kid 注入。kid（key id）如果被拼进文件路径或 SQL，就是路径穿越或 SQL 注入；如果指向一个攻击者可控的 JWK 地址，就是 SSRF 加信任劫持。

七、EdDSA 为什么把这个问题从根上删掉了

看完上面五类错误，会发现一个共性：它们全都围绕 k。

EdDSA（RFC 8032，代表实现 Ed25519）的设计思路非常直接：既然 k 的随机性是最脆的环节，那就不要随机。

prefix 是私钥哈希的一部分，M 是消息。同一个私钥对同一条消息，永远产生同一个签名——没有 RNG 参与，也就没有”RNG 坏了”这回事。

这解决了两类问题：

问题 ECDSA EdDSA
RNG 熵不足 私钥泄露 无影响（不依赖 RNG）
k 复用 私钥泄露 不可能（确定性派生）
k 有偏 格攻击 不可行（H 输出均匀）
签名可延展 是 否
验证复杂度 需要求逆 更快

代价是：**确定性派生把”随机性风险”换成了”侧信道风险”。**如果实现有故障攻击（fault attack）或缓存时序泄露，攻击者可以通过扰动计算、观察输出，反推 d。所以 Ed25519 的实现仍然需要恒定时间、需要防止故障注入。

但对绝大多数应用来说，“别让 RNG 参与签名”这个取舍，收益远大于风险——因为 RNG 出错是常态，而故障注入需要物理接近。

ECDSA EdDSA Schnorr (BIP340)
nonce 来源 随机（或 RFC 6979 确定性） 确定性派生 确定性 + 可选辅助随机
可延展性 有 无 无
批量验证 难 中 易
生态成熟度 最高 高 中（区块链为主）

顺带提一句 RFC 6979：它是给 ECDSA 打的补丁，用 HMAC-DRBG 从私钥和消息确定性派生 k。如果你的系统必须用 ECDSA，RFC 6979 是最低要求——它一次性消灭了”k 复用”和”k 有偏”两整类问题。

7.1 确定性 nonce 挡不住什么

EdDSA 把 RNG 从流程里删掉了，但这不是”从此不用管实现”。它挡不住三类问题：

第一类：侧信道。确定性意味着”同一个私钥 + 同一条消息 = 同一个 r”。如果实现有缓存时序泄露，攻击者可以构造大量不同消息，观察每次 r 派生过程的泄露，做统计攻击。对抗手段不是加随机性，而是实现必须恒定时间。

**第二类：故障注入。**如果攻击者能扰动某一次标量乘（电压毛刺、激光注入），导致 r 计算错误但签名仍然输出，就能从错误签名里反推 d。这是硬件安全里的经典手法，在智能卡上被反复验证过。Ed25519 的推荐实现会重新计算并校验签名结果，就是为了挡这个。

**第三类：prefix 泄露。**EdDSA 的 r 来自 H(prefix ‖ M)，prefix 是私钥哈希的后半段。如果某个实现把 prefix 缓存到不安全的地方（比如日志、崩溃转储），r 就变得可预测——攻击者知道了 r，就等价于知道了 ECDSA 里的 k。

**所以正确的表述不是”EdDSA 没有 nonce 问题”，而是”EdDSA 把 nonce 问题从『随机性』转移到了『实现质量』”。**后者更可控，但不是零。

八、审计一个签名实现，按这个顺序查

# 检查项 不合格的后果 严重度
1 k 是怎么生成的？有没有用 RFC 6979？ 复用/有偏 → 私钥直接泄露 致命
2 有没有对 k 取模、截断、窄化范围？ 格攻击 致命
3 曲线参数是标准的吗？ Smart 攻击 / 小群 → 多项式时间破解 致命
4 ECDH 是否验证对方公钥在曲线上？ 无效曲线攻击 → 逐位恢复私钥 高
5 验证时是否检查 r, s ∈ [1, n−1]？ 边界伪造 / 异常泄露 高
6 签名比较是否恒定时间？ 时序侧信道 中
7 是否会因为可延展性导致重放/去重失效？ 业务层被绕过 中
8 私钥运算是否恒定时间（防缓存时序）？ 侧信道 中

九、小结

椭圆曲线密码学在数学上非常坚固。256 位的曲线给出的安全强度，等同于 3072 位的 RSA。至今没有任何一条标准曲线被有效攻破。

但它有一个和 RSA 完全不同的特性：RSA 的错误通常是”参数选错”（静态的、可以审计的），ECDSA 的错误通常是”每次签名都可能错一次”（动态的、难以复现的）。

一次 RNG 抖动、一次虚拟机快照回滚、一次容器镜像复用同一个随机种子——任何一个都可能让两条签名共用一个 k。而只要有一次，私钥就永久泄露，且无法通过重新签名来挽回（因为旧签名已经公开了）。

所以这条线的心智模型应该是：

对称加密的失败是”泄露了一次通信”，非对称签名的失败是”永久失去了身份”。

这也是为什么 EdDSA 值得被认真对待——它不是在”让 k 更随机”上做优化，而是把 k 这个变量从系统里删掉了。安全工程里最可靠的做法，从来不是”把容易错的东西做对”，而是”让容易错的东西不存在”。
