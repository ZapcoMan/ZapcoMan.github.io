nonce 撞一次，我就能伪造你的任意消息——而且换 nonce 也救不回来：AEAD 的六种误用

2026-11-03 #密码学#AES-GCM#TLS#nonce#AEAD#ChaCha20-Poly1305#认证加密#重放攻击#WPA3

2016 年，四位研究者在扫描全网 HTTPS 服务器时发现了一件奇怪的事：184 台服务器在 GCM 模式下重复使用了 nonce。

他们没有拿到任何私钥。但在拿到两个同 nonce 的密文之后，他们恢复了 GHASH 的认证密钥 H——然后伪造出了能被这些服务器接受的加密 Cookie。

攻击的名字起得很直白：”Nonce-Disrespecting Adversaries”。论文的核心结论只有一句：GCM 的 nonce 复用，不是”泄露明文”级别的错误，是”交出签名权”级别的错误。

AEAD 是过去十年密码学工程最重要的进步。它把”加密”和”认证”打包成一个 API，让”忘记加 MAC”这种低级错误从工程上消失了。

但它同时做了一件很少有人提醒的事：它把全部风险，集中到了 nonce 这一个参数上。

一、AEAD 承诺了什么，又悄悄要求了什么

AEAD（Authenticated Encryption with Associated Data）承诺三件事：

承诺 含义 失败时
机密性 没有密钥看不到明文 数据泄露
完整性 密文被改一个比特就拒绝 内容被篡改
认证 附带数据（AAD）也被绑定 头部/元数据被伪造

相比”自己拼 Encrypt-then-MAC”，AEAD 的价值是消除了顺序错误的可能——你没法”先加密忘了 MAC”，因为 API 里没有这个选项。

但 AEAD 有一个隐含前提，写在标准的脚注里，不在 API 的签名上：

同一个密钥下，nonce 永不重复。

这个要求是所有 AEAD 方案的共同点，而 GCM 是其中后果最严重的一个。

1.1 GCM 的内部结构：两半，两个不同的失败模式

GCM = CTR 加密 + GHASH 认证。

这个结构决定了 nonce 复用会同时打击两半，而且第二半的后果远比第一半严重。

二、误用一：nonce 复用——从”读到明文”升级到”能伪造”

2.1 第一半：CTR 的两次一密

CTR 模式下，密钥流只由 (K, nonce, counter) 决定。同一个 nonce 用两次，密钥流完全相同：

攻击者拿到两个密文异或，就得到了两个明文的异或。这就是经典的”两次一密”（two-time pad）。

危害程度取决于明文的结构。如果是两份 HTTP 请求，其中一份有大量已知字段（GET / HTTP/1.1、Host:、User-Agent:），那么通过”拖动”（crib dragging）就能把另一份的大部分内容还原。

2.2 第二半：H 泄露，伪造能力到手

这才是 GCM 独有的灾难。

于是攻击者获得了三样东西：

  1. 可以解出任意密文（如果 nonce 重复过）
  2. 可以构造任意密文并附上合法标签
  3. 而且全程不需要密钥 K

这就是为什么 2016 年那篇论文能伪造 Cookie——一旦 H 泄露，服务器的”认证”就完全失效了。

2.3 对比：CBC 的 nonce 复用没那么惨

模式 IV/nonce 复用后的后果 可恢复性
CBC 泄露”两个明文首块是否相同”（等值泄露） 局部影响
CTR 两次一密，明文异或泄露 局部影响
GCM 两次一密 + 认证密钥 H 泄露 + 完全伪造能力 灾难性
ChaCha20-Poly1305 两次一密 + Poly1305 一次性密钥泄露 → 可伪造 灾难性

这张表值得贴在墙上。AEAD 的 nonce 复用不是”稍微差一点”，它是”整个方案崩塌”。

2.4 真实案例：Forbidden Attack（2016）

研究者扫描了 Alexa 前 100 万的 HTTPS 站点，发现 184 台服务器存在 nonce 复用。

原因多半是：这些服务器用了自行实现的 GCM，nonce 不是从计数器或 TLS 序列号派生，而是随手 rand() 或者干脆用了固定值。

攻击者在论文里演示了完整链路：抓两个同 nonce 的握手 → 解出 H → 伪造一段加密 Cookie → 以受害者身份访问。

这也说明一件事：**TLS 本身没有问题，问题在”自己实现的加密层”。**TLS 1.2/1.3 里的 GCM nonce 是 固定部分（4 字节 salt）‖ 显式部分（8 字节序列号），序列号单调递增，天然不会重复。标准协议从来不犯这个错，犯错的都是自己写的那一层。

2.5 一个相关的现代案例：WPA3 的 Dragonblood

2019 年的 Dragonblood 系列漏洞里，有一部分就是围绕 nonce 处理不当——SAE 握手在特定条件下会重用 (key, nonce) 组合，导致降级和侧信道。

Wi-Fi 场景的特殊之处在于：攻击者可以在物理层反复触发握手，采样量几乎无限。这提醒我们，nonce 复用的可利用性取决于攻击者能触发多少次加密——在本地网络里，这个次数是”无限”。

2.6 手动复现：两段密文，一段已知明文

不用任何攻击工具，标准库就能演示第一半：

两段明文必须等长才有意义——CTR 是流式的，长度不同也能异或，但只有重叠部分可还原。

第二半更隐蔽：把两个 tag 也异或一次，会得到一个关于 H 的多项式方程。如果两段密文长度接近，这个多项式的次数很低，在 GF(2^128) 上求根只需要枚举几百种可能，几乎瞬间出结果。

拿到 H 之后，构造伪造包只需要实现一次 GHASH——开源实现满地都是，因为 GHASH 不是秘密，秘密只有 H。

这也说明了 GCM 设计上的一个特点：**它的认证密钥 H 是从主密钥派生出来的，但一旦泄露，攻击者获得的是”无限次伪造权”，而不是”一次解密权”。**这个不对称性，是 GCM 的 nonce 复用比 CBC 严重得多的根本原因。

三、误用二：96 位 nonce 该怎么构造

GCM 标准推荐 96 位（12 字节）nonce，因为这种情况下 J0 = nonce ‖ 0^31 ‖ 1，不需要额外的 GHASH 运算。

问题在于：96 位随机 nonce，能安全地用多少次？

生日悖论给出答案。用 2^32 次之后，出现碰撞的概率约为 2^-33；用 2^48 次之后，碰撞概率接近 1。

NIST SP 800-38D 因此给出限制：使用随机 nonce 时，单个密钥的加密次数不超过 2^32。

三种构造方式的对比：

构造方式 示例 安全上限 适用场景
确定性计数器 nonce = 全局自增 64 位 几乎无限 单机、可控状态
随机 96 位 os.urandom(12) 2^32 次/密钥 分布式、无共享状态
固定前缀 + 序列号 TLS 的 salt ‖ seq 取决于序列号位宽 有状态连接
192 位（XChaCha20） os.urandom(24) 2^64 次 推荐给随机场景

对于”随机 nonce”这个需求，我现在的默认选择是 XChaCha20-Poly1305（192 位 nonce）——它把随机碰撞的边界推到了几乎不可能触及的位置，代价只是多一点 nonce 长度。AES-GCM 没有 192 位版本，所以用它就必须接受 2^32 的上限，或者老老实实用计数器。

3.1 一个常被忽略的细节：密钥轮换不等于 nonce 重置

如果系统每天轮换密钥，很多人会认为”nonce 可以每天从头开始”。这在计数器方案里是对的（新密钥 = 新的 nonce 空间），但在随机方案里是错的——随机 nonce 的碰撞概率是按”每个密钥”算的，轮换确实重置了计数，但如果你轮换周期内就用了 2^32 次，那还是超了。

反过来说，**如果 nonce 是计数器，密钥轮换时必须重置计数器；如果忘了重置，两个密钥会共用同一串 nonce——而它们各自是安全的，只有跨密钥的碰撞才是问题（实际上跨密钥不构成碰撞，因为 K 不同）。**所以计数器 + 密钥轮换是安全的。

真正危险的是同一个密钥被部署到两台机器上，两台各有自己的计数器。这时候计数器会重叠，nonce 必然重复。这是分布式系统里最常见的 GCM 事故来源。

3.2 分布式系统里怎么保证 nonce 不重复：四种架构

这是我被问过最多次的问题。答案取决于你能接受多少协调成本：

架构 做法 优点 代价
中心计数器 Redis INCR 分配，每次取一个号 绝对不重复 一个网络往返 + 单点
号段预分配 每个实例启动时领 100 万个号 无单点、无往返 号段浪费，需处理续租
大 nonce 随机 改用 XChaCha20（24 字节） 无需任何协调 依赖库支持
密钥内嵌实例 ID key_i = HKDF(master, info=instance_id) nonce 空间天然隔离 实例数有上限

最后一行是我最推荐的：如果每个实例用自己的子密钥，那”同一个密钥下 nonce 不重复”这个条件就自动满足了——因为不同实例根本不在同一个密钥空间里。

用一次 HKDF 运算，换掉了整套分布式协调。这是”用密钥分离换 nonce 唯一性”的典型手法，也是 TLS 1.3 每个方向用独立 traffic secret 的同一个思路。

顺带提一句容器的坑：如果实例 ID 来自容器的主机名，而主机名是按 app-1、app-2 这样递增的，那实例重建后 ID 会重复——旧实例的 nonce 空间被新实例继承，计数器又从 0 开始。

正确做法是给每个实例一个持久化或随机的 128 位 ID，而不是可复用的序号。

3.3 发现 nonce 已经重复了，怎么止损

这是运维层面最容易被做错的一步。正确的顺序是：

  1. 立刻轮换密钥——不是”改 nonce 生成器”，而是换密钥。因为 H 可能已经泄露，而 H 一旦泄露，攻击者对这个密钥下的所有历史密文和未来密文都拥有伪造能力。
  2. **把该密钥加密过的全部历史数据视为已泄露。**不是”可能泄露”，是”已泄露”——因为 two-time pad 一旦发生，明文异或就永久留在了日志里。
  3. 检查是否已被利用：有没有出现你从未发送过的合法密文？这只能通过业务侧的审计日志发现。
  4. 最后才修根因（nonce 生成逻辑）。

最常见的错误是第 1 步：只改代码，不换密钥。代码改了，泄露的 H 还是有效的，攻击者照样能伪造，只是不再有新素材让他算更多的 H 而已。

四、误用三：tag 截断

GCM 的 tag 可以截断到 128、120、112、104、96 甚至 64、32 位。

每截断 8 位，伪造的难度就降低 256 倍。算一笔账：32 位 tag 的伪造平均需要 2^31 次尝试，如果服务端允许每秒 1000 次请求，大约 25 天就能蒙对一次——而这 25 天里攻击者只需要跑一个脚本。

工程上的建议很简单：**128 位全用。**如果确实要省，96 位是底线，且必须配合严格的重试限制和速率限制。

截断在某些协议里是有历史原因的（比如 QUIC 早期的一些设计、以及一些物联网协议为了省电），但那些场景都有明确的威胁模型论证。自己拍脑袋截断，通常只是省了几十字节，换来一个可爆破的认证。

问题在于：**一旦明文被交给上层代码，任何”后面再检查”都晚了。**上层的 JSON 解析、反序列化、甚至日志记录，都可能基于这段未经验证的数据产生副作用。

最典型的形态是 OpenSSL 的 EVP 接口：

这类问题在代码审计里非常好找：搜 DecryptFinal，看返回值有没有被检查。在 Java 里搜 AEADBadTagException 有没有被捕获后继续执行。

5.1 后果为什么比”读到脏数据”严重

有人会觉得：反正 tag 会失败，我后面报个错不就完了？

问题在于”后面”这个位置是不可控的。明文一旦交给上层，会经过一整套它不该经过的处理链：

下游动作 后果
JSON / 反序列化 触发解析器漏洞（反序列化 gadget）
写入数据库 脏数据落盘，事后难以区分真伪
写入日志 日志注入，攻击者可以伪造审计记录
作为缓存 key 缓存投毒
反射到响应体 XSS
触发业务动作 转账、改密、发货

最后一行是致命的。一个”解密失败但已经执行了下单逻辑”的接口，等于把认证完全绕开了。

**判断标准只有一句：verify 必须在任何 use 之前，中间不能有任何代码。**这不是”最佳实践”，这是正确性的定义。

5.2 一个具体的绕过场景

设想一个 API：

攻击者只要随便改密文的一个字节，tag 必然失败，但 json.loads 依然能解析出结构（因为 CTR 只影响被改动的那个字节对应的明文位置），订单照常创建。

六、误用五：密钥与方向复用

6.1 双向通信共用一把密钥

设 A 和 B 用同一把 key 通信，nonce 各自从 0 开始。

  • A → B，nonce = 0，密文 C_A0
  • B → A，nonce = 0，密文 C_B0

**同一个密钥下，nonce 0 被用了两次。**两段完全不同的对话，直接构成 nonce 复用。

后果和第二节完全一样：H 泄露、可伪造。

正确的做法是方向分离：

或者至少给 nonce 加一个方向位（比如最高位区分方向）。

TLS 1.3 的做法就是这个思路：每个方向有独立的 traffic secret，由 HKDF-Expand-Label 派生，label 里就包含 "c ap traffic" / "s ap traffic"。

6.2 一把密钥干两件事

更常见的是：同一把 key 既用来做 AES-GCM 加密，又用来做 HMAC 签名，或者既加密又加密另一种数据（比如既加密消息内容又加密文件）。

**密钥复用会打破安全证明的前提。**密码学方案的证明都是在”密钥单一用途”的前提下成立的。

工程上的标准做法是密钥分离（key separation）：

一个主密钥，派生出用途明确的子密钥。这样即使其中一把泄露，也不会横向影响其他用途。

6.3 密钥轮换时的一个陷阱

轮换密钥本是好事，但轮换的实现方式经常引入新问题：

表面上看没问题（新 key 配新 nonce，不会和旧的撞），但如果同一个新 key 被分发给多个实例，各实例的计数器都从 0 开始，跨实例就会撞。

还有一种更隐蔽的情况：密钥轮换后，旧密文仍然需要能解密。此时系统里同时存在多个密钥版本，如果 nonce 的派生没有绑定密钥版本号，就有可能出现”A 版本密钥 + nonce N” 与 “B 版本密钥 + nonce N” 混用时的逻辑混乱。

工程上的两个做法：

  1. 把密钥版本号放进 AAD，让版本和密文强绑定，防止降级或错配。
  2. nonce 从密钥派生而不是从全局计数器派生：nonce_prefix = HKDF(key, info=b"nonce")[:4]，这样换 key 就自动换了 nonce 空间。

第 2 条和 3.2 节里”密钥内嵌实例 ID”是同一个思路的两种应用：用密钥分离来解决命名冲突，比用协调协议解决冲突更省事。

七、误用六：把 AEAD 当成”安全性全包”

这是最认知层面的一条。

AEAD 保证的是：这段密文确实是由持有密钥的人产生的，且没有被修改。

它不保证：

你以为它防 实际上它不防 需要什么
重放 ❌ 同一段合法密文可以原样重发 序列号 / 时间戳 / 去重缓存
乱序 ❌ 消息可以调换顺序 显式序号
截断 ❌ 可能可以丢弃尾部消息 序号 + 结束标记
反射 ❌ 可能可以把 A 发的消息回给 A 方向标识
流量分析 ❌ 长度、时序、频率全都可见 填充 / 混淆

重放是最常被漏掉的一条。

一条”转账 100 元”的合法密文，重发一次，服务端会认为是第二笔转账。AEAD 的 tag 校验完全通过——因为它就是一条真消息。

防御必须来自协议层：

TLS 的做法是把序列号隐式绑定进 nonce（nonce = salt ‖ seq），所以重放的包会因为 nonce 不匹配而直接解密失败——这是用 nonce 机制顺手解决了重放，很巧妙。

TLS 1.3 的 0-RTT 则是显式放弃了这个保护：0-RTT 数据不绑定序列号，因此天然可重放。这是性能与安全的取舍，用在不幂等操作上就是误用。

7.1 重放的代价：三个具体例子

抽象地讲”要防重放”很难落地，具体一点：

**例子一：支付接口。**一条”转账 100 元给 A”的密文，重发 100 次就是 100 笔。每次 tag 都对，因为每次都是同一条真消息。

例子二：设备指令。“解锁门禁”的合法指令被录下来，攻击者在三小时后重放。如果设备不维护序号，门会再开一次。

例子三：一次性令牌。“这个邀请码只能用一次”——如果不记录已用过的密文（或它的序号），重放就是用第 N+2 次。

这三个场景的防御手段不同，但原理一致：**AEAD 保证的是”这条消息来自持钥方”，不保证”这条消息是第一次被使用”。**后者必须由状态来解决——序号、时间窗、去重表，三者选一。

八、CBC / GCM / ChaCha20-Poly1305 怎么选

维度 AES-CBC + HMAC AES-GCM ChaCha20-Poly1305
完整性 需要自己拼（易错） 内建 内建
硬件加速 AES-NI AES-NI + PCLMUL 无（纯软件，但很快）
nonce 复用后果 局部泄露 灾难性（可伪造） 灾难性（可伪造）
nonce 长度 16 字节 IV 12 字节（96 位） 12 字节（XChaCha20 为 24）
随机 nonce 上限 无硬限制 2^32 次/密钥 2^32（XChaCha20 为 2^64）
移动端性能 中 有 AES 指令时最快 无 AES 指令时最快
推荐度 遗留系统 服务端首选 移动端 / 无 AES 加速时首选

选型的三条经验：

  1. 有 AES 硬件指令（x86 的 AES-NI、ARMv8 的 Crypto Extensions）→ AES-GCM，但要严格管理 nonce
  2. 没有 AES 硬件指令（很多低端 ARM、旧设备）→ ChaCha20-Poly1305，软件实现快得多，且天然抗缓存时序
  3. 无法保证 nonce 唯一（分布式、无共享状态、随机 nonce 且量大）→ AES-GCM-SIV（RFC 8452）或 XChaCha20

最后一条值得展开：nonce 误用抵抗（nonce misuse resistance） 是一个独立的安全属性。AES-GCM-SIV 用一段从明文派生的 synthetic IV，使得即使 nonce 重复，也只泄露”两个明文相同”这一条信息，而不会泄露 H、不会丧失伪造抵抗。

代价是：它需要两遍处理（先算 SIV 再加密），吞吐比 GCM 低约一半，且它不是”在线”的（必须先读完整个明文）。

**如果你知道自己的系统管不好 nonce，选 SIV 比选 GCM 更理性。**承认工程现实，比假装能管好 nonce 更安全。

8.1 关于性能，一句实话

很多选型讨论止步于”哪个快”。给个量级参考：

方案 单核吞吐（有硬件加速） 单核吞吐（无硬件加速）
AES-128-GCM GB/s 级 数百 MB/s（表格实现，且有缓存时序风险）
ChaCha20-Poly1305 — GB/s 级（纯软件优化实现）
AES-GCM-SIV 约为 GCM 的一半 更低

关键结论只有一条：**在 ARMv8 之前的设备、以及大量没有 AES 指令的嵌入式芯片上，ChaCha20-Poly1305 比 AES-GCM 快数倍，而且没有缓存时序侧信道。**这不是”更安全的备选”，在很多场景下它就是更优解。

而 AES-GCM-SIV 的那一半吞吐损失，换的是一个整类漏洞的消失。如果你的业务是每秒几千个请求而不是几百万，这笔交易非常划算。

九、一份 AEAD 使用检查清单

# 检查项 不合格后果 优先级
1 nonce 是否保证在单个密钥下永不重复？ H 泄露 → 完全伪造 P0
2 双向通信是否用了不同密钥（或不同 nonce 空间）？ 跨方向 nonce 碰撞 P0
3 解密 API 的 tag 校验返回值是否被检查？ 未认证明文进入业务 P0
4 随机 nonce 的使用次数是否低于 2^32/密钥？ 生日碰撞 P1
5 tag 是否用了完整 128 位？ 伪造可爆破 P1
6 是否做了重放防护（序号/时间戳/去重）？ 重放攻击 P1
7 主密钥是否通过 HKDF 分离成用途明确的子密钥？ 密钥复用破坏安全证明 P2
8 是否有密钥轮换机制，且轮换时 nonce 空间正确隔离？ 长期密钥风险累积 P2

第 1 条和第 2 条是一回事的两面。“管好 nonce”听起来像一句废话，但它是 AEAD 唯一的失效入口。

十、小结

AEAD 的流行，本质上是密码学工程的一次”防呆设计”：

  • 以前：你自己选模式、自己加 MAC、自己保证顺序 → 犯错空间巨大
  • 现在：一个 seal(key, nonce, plaintext, aad) → 只剩一个参数要管

结果是：“忘记认证”这类错误基本消失了，但”nonce 管理”这类错误被集中放大了。

这件事有一个很普遍的规律——防呆设计不会消灭风险，它只会把风险挤压到剩下的那个自由参数上。

  • 密码从”自己算哈希”变成”用 bcrypt”，风险挤压到了”参数选多少”
  • 库从”自己拼 EtM”变成”用 AEAD”，风险挤压到了”nonce 怎么生成”
  • 协议从”自己设计握手”变成”用 TLS 1.3”，风险挤压到了”证书怎么校验、0-RTT 怎么用”

所以看到”我们用了 AES-256-GCM”这句话时，正确的反应不是”那很安全”，而是问一句：

“你们的 nonce 是怎么生成的？”

2016 年那 184 台服务器，全都用了 AES-GCM。它们只是在 nonce 这一件事上，答错了。
