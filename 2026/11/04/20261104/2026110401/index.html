一台 PLC 被 9 个字节拿下：Modbus 的无认证、明文，和「先停机再谈别的」的 OT 攻击面

2026-11-04 #工控安全#OT安全#Modbus#PLC#SCADA#ICS#协议安全#S7comm

2015 年 12 月 23 日，乌克兰伊万诺-弗兰科夫斯克地区，几十万人在寒夜中突然断电。事后调查发现，攻击者没有用任何 0day，只是拿到了变电站 SCADA 系统的合法操作员权限，然后用一把再普通不过的工具，向 RTU 下达了断路器分闸指令。

这是一篇关于工控（OT）安全的文章——也是这个博客在工控方向的第一篇。我会用一个最经典、也最容易被忽视的攻击面开题：Modbus 协议本身。

一、先说清楚一件事：OT 和 IT 是两套完全不同的安全观

我们熟悉的网络安全（IT 安全）里，优先级是 CIA：机密性（Confidentiality）、完整性（Integrity）、可用性（Availability）。保密第一，因为数据丢了值钱。

但在工控系统（OT）里，这个顺序是反过来的，而且反得很彻底：

维度 IT 安全 OT 安全
首要目标 保密性（数据不能泄露） 可用性（设备不能停）
完整性 数据不能被篡改 工艺参数不能被改写
机密性 最高优先级 相对次要
停机的影响 业务中断、金钱损失 物理损坏、人身安全、社会瘫痪
打补丁 越快越好 可能几年不能碰

这个表是整个工控安全理解的基础。它解释了后面几乎所有「反直觉」的现象：为什么一个在 IT 里属于「低级错误」的无认证协议，在 OT 里能原封不动地存在三十年；为什么一台暴露在公网的 PLC 可以几年没人管；为什么安全研究员每次报告 OT 漏洞，厂商的第一反应是「这不算漏洞，这是功能」。

因为你不能用 IT 的思维去套 OT。 在 OT 的世界里，安全的目标不是「防止数据被偷」，而是「防止有人让一台机器做出不该做的动作」。

二、Modbus：一个为「信任」而生的协议

Modbus 诞生于 1979 年，由 Modicon 公司（现施耐德电气）发布，目的是让它的 PLC 能和 HMI（人机界面）、上位机通信。它的设计前提非常朴素：

设备都在厂区内网里，接线的人都是自己人，协议不需要加密，也不需要认证。

这个前提在 1979 年是成立的。那时候工业网络是物理隔离的，网线都得你自己去机房插。但四十年过去，物理隔离这个前提早就不存在了——现在几乎每一台 PLC 都通过某种方式连到了业务网，而业务网又连到了互联网。

于是问题来了：一个为「零信任环境」设计的协议，被原封不动地放进了「零信任环境」里。

2.1 协议结构：比 HTTP 还简单

Modbus 有 TCP 和 RTU（串口）两种传输，我们这里讲 TCP 版（Modbus/TCP），因为它最常见，也最容易被打。

一个 Modbus TCP 请求帧长这样：

就这么多。没有加密、没有认证、没有校验（除了一个聊胜于无的 CRC/LRC）。 谁连上来，谁就能读，谁就能写。

核心是功能码，它决定了这个请求要做什么：

功能码 名称 作用
0x01 / 0x02 读线圈 / 读离散输入 读开关量
0x03 / 0x04 读保持寄存器 / 读输入寄存器 读模拟量、状态
0x05 写单个线圈 写一个开关量（开/关）
0x06 写单个寄存器 写一个模拟量
0x10 写多个寄存器 批量写模拟量
0x08 诊断 回环测试等

注意看标粗的那三个写功能码。它们不需要任何前置认证，也不需要任何校验，只要发对了地址，PLC 就执行。 这就是整件事的核心。

2.2 为什么「无认证」在这里是致命的

在 IT 里，一个无认证的服务，你至少还得想「我连上之后能干嘛」。但在 OT 里，无认证 + 有写功能码 = 直接远程控制物理设备。

举一个具体的例子。假设一台 PLC 控制着一条生产线的某台泵，泵的启停由线圈地址 0x0000 的一个位控制（0=停，1=转）。那么攻击者只需要发一个 12 字节的包：

拆开看这 12 个字节：

字节 含义 说明
00 01 事务标识符 请求/响应配对用，随便填
00 00 协议标识符 恒为 0
00 06 长度 后面还有 6 个字节
01 单元标识符 设备地址
05 功能码 写单个线圈
00 00 线圈地址 要写哪个线圈（这里是第 0 个）
FF 00 线圈值 FF00=ON（置 1），0000=OFF（置 0）

就这一下，泵停了。如果这台泵是给反应釜降温的冷却水泵，那停泵的后果是反应釜过热、超压、爆炸。

这 12 个字节（其中真正「起作用」的只有功能码 + 地址 + 值，共 5 个字节），就是标题里说的「9 个字节拿下 PLC」——说 9 个字节，是因为如果走 Modbus RTU 串口版，去掉 TCP 头部后，核心指令只有 9 个字节（地址 1 + 功能码 1 + 线圈地址 2 + 值 2 + CRC 2，CRC 本身可伪造）。

没有 0day，没有缓冲区溢出，没有任何高级技巧。 只是协议本身允许任何人写，而这个「任何人」在物理隔离失效后，变成了「全互联网的任何人」。

没有 0day，没有缓冲区溢出，没有任何高级技巧。 只是协议本身允许任何人写，而这个「任何人」在物理隔离失效后，变成了「全互联网的任何人」。

三、现实世界：暴露在公网的 PLC 比你想象的多

一个很多人不信的事实：互联网上有大量 PLC、HMI、SCADA 设备直接暴露在公网，且不需要任何认证就能访问。

搜索引擎 Shodan、Censys、FOFA、ZoomEye 上，搜 Modbus 协议的默认端口 502，能搜出成百上千的暴露设备——里面有相当一部分是真实的、正在运行的生产设备，而不是蜜罐。

这是一个真实的问题，不是危言耸听。原因有三层：

  1. 历史遗留：设备部署的时候是物理隔离的，后来为了「远程运维方便」，工程师直接做了端口映射，把 502、102（西门子 S7）、47808（EtherNet/IP）这些协议端口暴露出去，而且没加任何访问控制。
  2. 设备本身做不到：很多老 PLC 的固件里根本没有认证功能，你想加都加不了。要么换设备，要么忍受。
  3. 「没人会来打我」的侥幸：OT 设备往往不被纳入常规的安全扫描范围，安全团队也不知道自己厂里有这些东西暴露着。

3.1 一个令人不安的推论

在 IT 里，你暴露一个无认证的 MySQL 到公网，很快就会被勒索软件扫到、拖库、删库。但 OT 设备被扫到之后，攻击者能做的远不止「拖库」——他可以直接让设备停机，或者更阴险地，在后台偷偷改一个工艺参数，等你在某个特定时刻出事故。

这就是 Stuxnet（震网）教给全世界的：真正高级的 OT 攻击，不是「把设备搞坏」，而是**「让设备看起来正常，实际上已经坏了」**。

四、三个真实案例：OT 攻击从来不是「黑客炫技」

在进入攻击链之前，先看三个真实发生过、并且彻底改变了人们对 OT 安全认知的案例。它们有一个共同点：没有一个是靠「高深技术」打赢的，全是靠「协议裸奔 + 配置错误 + 物理隔离失效」。

4.1 Stuxnet（震网，2010）：第一场「国家级」OT 攻击

震网是绕不开的起点。它的目标很具体——伊朗纳坦兹核设施的离心机。

技术上的关键点在于：震网没有攻击任何「已知漏洞」去「炸掉」离心机，而是做了两件更阴险的事：

  1. 通过 Windows 的四个 0day 从办公网渗透到隔离的工业网（这是「物理隔离」被打破的第一个著名案例）
  2. 篡改西门子 S7-300 PLC 的程序，让它周期性地把离心机转速调到一个会损伤转子的区间，同时把仪表读数伪装成正常值

结果：操作员盯着仪表，一切正常；离心机却在慢性自杀。震网的意义不在于「多难打」，而在于它证明了一件事——OT 攻击的终极形态是「让你在仪表上看到的，和你设备真实发生的，是两回事」。

4.3 美国供水系统（2021）：9 个字节的「加料」攻击

2021 年 2 月，美国佛罗里达州奥德马尔市的一座水厂被攻击。攻击者做的事极其简单：

远程登录了水厂老旧的 TeamViewer（密码还是共享的），然后把氢氧化钠（烧碱）的投加量，从正常的 100 ppm 改到了 11100 ppm——超了 111 倍。

烧碱是用来调 pH 的，这个浓度直接灌进饮用水会灼伤人的食道。万幸的是，操作员正好盯着屏幕，看到光标自己动了一下，当场改了回去。

这个案例的「技术含量」几乎为零，但它完美说明了本文的核心论点：OT 攻击的可怕，不在于「技术多高明」，而在于「一步就能造成物理后果」——而这一步，往往只需要一个弱口令、一个裸奔的远程桌面、或者一个无认证的协议。

五、Modbus 之外的 OT 协议：问题不是 Modbus 独有

Modbus 只是一个代表。实际上，几乎所有经典的 OT 协议都「裸奔」：

协议 默认端口 厂商 认证情况
Modbus/TCP 502 通用/施耐德 无认证，明文
S7comm 102 西门子 早期无认证，后来有弱认证
EtherNet/IP 44818 罗克韦尔 无强制认证
OPC Classic (DCOM) 135 通用 依赖 Windows DCOM，配置复杂易错
DNP3 20000 电力 有 Secure Authentication 但多数未启用
PROFINET 34964 西门子 实时通道无认证
BACnet/IP 47808 楼宇自控 无认证

这张表想说明的是：「协议无认证」是 OT 世界的普遍现象，不是 Modbus 的个案。 所以学 OT 安全，第一个要建立的认知就是——这些协议默认「裸奔」，安全要靠外层网络隔离和访问控制来补，而不是靠协议本身。

这也是为什么 OT 安全的 IDS 要重点盯写操作：在一个正常的厂区网络里，PLC 的写操作频率很低、来源固定（通常是 HMI 或上位机）。突然冒出来一个来自陌生 IP 的 write_coil，基本可以直接拉响最高级别告警。

5.3 重点说说第五步——为什么「不直接停机」更可怕

这是工控攻击和 IT 攻击最大的区别。在 IT 里，你拿了权限，最爽快的是「rm -rf /」或者「拖库跑路」。但在 OT 里，最高级的攻击是让你「看起来一切正常，直到事故发生」。

Stuxnet 的核心手法就是这一条：它没有直接让离心机「爆炸」，而是周期性地把离心机转速调到一个会损伤材料、但仪表上显示正常的速度。操作员看着仪表一切正常，实际上离心机的转子已经在慢性损伤了。

这类攻击为什么难防？因为：

  • 它不触发任何「异常」——设备读数都正常
  • 它可能潜伏几个月才发作，追溯时日志早没了
  • 它的目标不是「破坏」，是「让破坏在特定时刻、特定条件下发生」

这也是为什么 OT 安全的核心指标，不是「有没有被打进来」，而是「设备状态有没有被非法改变」。

七、为什么 OT 安全这么难做：四个结构性难题

理解了攻击面之后，还得理解为什么防护这么难。否则你会奇怪：都 2026 年了，怎么还会有裸奔的 PLC？

难题 说明
不能停 一条生产线停一分钟可能损失几十万，所以「打补丁」这种 IT 常规操作，在 OT 里可能几年都排不上
不能碰 很多 OT 设备是 7×24 运行的，连安全扫描都可能把它扫崩（主动探测对老 PLC 是真实风险）
不透明 OT 设备厂商众多、协议私有、固件不开放，安全研究员想分析都难
责任分离 OT 归「生产/设备部门」管，IT 安全归「信息部门」管，两拨人语言不通，安全责任经常是「没人管」

这四个难题叠加，导致一个结果：OT 安全的现状，大约相当于 2000 年的 IT 安全——漏洞满地，意识淡薄，工具原始。

八、防御：OT 安全不是「给 PLC 装防火墙」

基于前面的分析，OT 安全的防御可以分成四层，按优先级排：

7.1 P0：网络隔离（最重要，也最基础）

别把 OT 网络直接接到 IT 网络，更别接到公网。 如果一定要远程运维，用专线 + 跳板机 + 多因素认证，而不是直接把 502 端口映射出去。

这是投入产出比最高的一条。绝大多数 OT 攻击，都是因为「图方便做了端口映射」才发生的。

7.2 P1：协议层的访问控制

如果设备支持，启用协议自带的认证（比如西门子 S7 的密码保护、DNP3 的 Secure Authentication）。如果设备不支持，用协议网关/防火墙（如工业防火墙）做协议级的深度包检测，只放行合法的读写操作。

7.3 P2：流量监控与异常检测

部署 OT 专用的 IDS（如 Zeek 的 Modbus 解析器、Nozomi、Dragos 等），监控「谁在读、谁在写、写了什么」。重点监控写操作——OT 网络里，正常的写操作是很少的，突然出现一个「写线圈」的请求，本身就是强烈的告警信号。

7.4 P3：资产盘点与暴露面收敛

用被动扫描（不是主动扫描！）摸清自己到底有哪些 OT 设备、哪些暴露了。连自己有哪些设备都不知道，就没法谈防护。

九、一个反直觉的结尾：OT 安全的问题，从来不是技术

写到这里，我想点破一个很多人不愿承认的事实：

OT 安全的技术方案，几十年前就有了。 网络隔离、访问控制、流量监控——没有一样是新技术。真正的问题在于：

  1. 没人愿意停设备：补丁要停机，隔离要改网络，监控要加设备——每一样都会「影响生产」
  2. 责任没人担：IT 说「那是设备部的事」，设备部说「那是信息部的事」，最后没人管
  3. 不出事就没人管：OT 安全是典型的「黑天鹅」——99% 的时间风平浪静，1% 的时间出大事，但代价可能是人命

所以这一篇的真正结论，不是「Modbus 有多不安全」，而是：在一个「可用性压倒一切」的世界里，安全永远排第二。 直到一次事故把它排到第一。

而攻击者等的，就是那一次事故。
