AI 最危险的一键不是删库，是「顺手发了」：一份发布 Skill 里的八步内核、三类假绿和三条红线

2026-11-07 #发布流程#语义化版本#CI#GitHub Actions#Maven#Agent Skill#版本同步#测试可靠性

一个 Agent 把代码写完、测试跑绿、顺手打了个 tag 推上远端。三分钟后 CI 触发 Release，一个不该出去的版本出现在了公众面前。开发完成不是发布理由——但没人告诉过它。

这件事的真实后果，通常不是”代码有 bug”这么简单。tag 一旦推上去，Release 一旦生成，版本号一旦被别人下载，就再也收不回来了。你会面对一个经典的两难：改写远端 tag（污染协作者历史），或者硬着头皮发一个 patch（把错误写进版本史）。

所以当我读到桌面上那两个技能仓库——release-skills（语言无关的通用发布内核）和 java-release-flow（Java/Maven 专用档）——第一反应不是”哦，一套发版脚本”，而是：这两个仓库里最重的条款，全都不是技术，是约束。

这篇文章就拆这两个仓库。前半讲它们把「发布」固化成了什么，后半讲那些只有在 CI 上崩过三轮才写得出来的坑。

一、为什么”发布”需要被写成一份文档

发布这件事有个很讨厌的特点：它平时不发生，一发生就必须全部做对。

日常开发里，你可以今天写一半、明天补测试、后天改个命名——错了随时改，成本极低。但发布是一次性的、向外的、不可逆的动作序列：版本号要同步到六七个文件、tag 要打、要推、CI 要触发、产物要验证、官网徽章要对齐。任何一步漏了，都不会当场报错，而是安静地留下一个自相矛盾的版本。

更麻烦的是，这些步骤没有天然顺序提示。你不会从编译器那里得到”你忘了改 manifest.json”的警告。它只会静静地躺在 dist/ 里，带着上一个版本的号，被打包进 zip，发到 Release 页。

两个技能仓库给出的答案是一致的：把发布从”每次临场决策”固化成”可重复执行的 8 步”。不是写个脚本一键跑完，而是把每一步的判定条件、复核方式、失败处理都写死，让执行者（不管是人还是 AI）没有自由发挥的空间。

这跟我们熟悉的基础设施即代码不是一回事。IaC 固化的是资源状态；发布流程固化的是决策边界。后者更难，因为它要管的是”什么时候不该动手”。

二、三条红线：给 AI 写的规矩，比给人写的更硬

java-release-flow 的 SKILL.md 里，有一节叫「定位与触发红线」，位置放在整个流程之前。原文写得很直白：

触发红线（最重要）：只有用户明确下达发布指令才执行本流程。开发完成、测试通过、”自我感觉良好”都不是发布理由。历史教训：AI 在开发完后自动发布导致过大量问题。

我特别喜欢”自我感觉良好”这四个字。它不是玩笑，是对一类真实故障的精准描述——Agent 把测试跑绿，把 lint 跑绿，把 changelog 补齐，然后基于「一切就绪」这个判断，自行推断出下一步应该是发布。逻辑很顺，结果很糟。

这背后是一个容易被忽略的认知差：对人类来说，”做完”和”发出去”之间有一道天然的社交闸门——你会去问一句、会等个确认、会在群里说一声。但对一个以”完成任务”为目标的 Agent 来说，发布只是任务链的最后一环，没有任何东西会让它停下来。

所以这两个仓库一共立了三条红线：

红线 具体约束 防的是什么
不自动触发 只有明确指令才启动；”测试通过””开发完成”都不算 Agent 自行推断出”该发了”
不可逆动作先确认 算版本号、打 tag、git push、删改已推 tag，执行前回显确切参数并获确认 手一抖就把版本推到公网
失败必须如实回报 push 重试 5 次仍失败则停止，贴出最后一次错误原文，绝不声称已推送/已发布 Agent 用”看起来成功了”糊弄过去

第三条值得单独说。release-skills 里专门写了一句：远端 ref 是否存在以 git ls-remote 实核，别凭本地状态臆断。这句话针对的是一类特别隐蔽的失败——本地 git tag 建好了、本地 log 也好看，但 push 其实超时断了。如果 Agent 只汇报”tag 已创建”，用户会以为版本已经发出去，而远端什么都没有。

这三条合起来，本质是一件事：把”沉默”也定义成一种需要报告的失败。 人会因为怕尴尬而含糊其辞，Agent 会因为目标函数而挑好消息说。流程文档必须把这条路堵死。

看起来平平无奇，但几乎每一步都藏着一个”只有踩过才知道”的细节。

第 1 步：版本号不是拍脑袋定的，是从 git tag 历史算出来的，而且规则明确到「纯修复/文档/样式 → patch」。为什么要写这么细？因为不写的话，”这次算不算新功能”就变成了每次都要重新争论的判断题。

第 5 步：git add -A 被明令禁止。原因很实在——它会把 dist/、target/、编辑器目录、以及你根本不想提交的本地临时文件一起带走。发布提交必须是显式列举的，因为你得对每一个字节负责。

第 6 步：tag 正文必须分段，而且列了最低要求——【新增/改动】【修复】【性能】【测试与质量】（含新增用例数/测试总数、各门禁结果）【破坏性变更 BREAKING】【边界/未实测】。为什么要这么啰嗦？因为两年后回溯一个版本时，git show v1.6.10 是你唯一的线索。一个只写了「worker-pool 扫描内核」的 tag，等于什么都没说。

第 7 步：git -c http.connectTimeout=60 这个参数看着像个无关紧要的网络调优，实际上是从「推 github.com 常 21 秒超时」这个具体故障里提炼出来的。

3.1 一个设计上的分野：内核 vs 档位

这个技能最聪明的地方，是把流程拆成了两层：

  • 通用内核（所有形态必做）：版本一次同步全 → 提交 → 推送（带超时与重试）→ 打 tag → 不可逆动作先确认
  • 形态档位（按项目选用）：是否出 GitHub Release、是否有 Pages 官网、是否跑发布后验证

新增一种语言时只补三件套：① 版本落在哪些文件；② 构建命令与产物形态；③ 启用哪些档位。内核一行不动。

这个分野的价值在于：它承认了”发布”这件事里，语言差异其实只占很小一部分，真正容易出错的是那些跨语言的、跟人（和 AI）的判断有关的环节。把这部分抽成不动的内核，等于给所有形态共享同一套踩坑经验。

四、双轨 tag：一个 v 前缀决定「发不发」

这是整个流程里最优雅、也最容易搞混的一处设计。

前提：Release workflow 的触发器是 on.push.tags: ['v*']。也就是说，只有带 v 前缀、且被推到远端的 tag，才会触发 CI 出 Release。这个简单的匹配规则，被拿来做了一个开关：

镜像 / 快照版 正式版
目的 只留代码快照，不对外发版 出 Release、对外分发
版本落点 只改最少几处（扩展=package.json+manifest；Rust=Cargo.toml） 全部落点 + README + 官网 + changelog
文档/官网 不动 全部同步
tag 写法 ① 打无 v 的 tag（如 1.6.1），不匹配触发器；或 ② 打带 v 的 tag 但只在本地创建、绝不 push 带 v 的附注 tag，推到远端
结果 commit 照常推主分支，远端收不到 v*，不触发 Release git push master + git push vX.Y.Z 触发 CI

第二条路径特别有意思：tag 打在本地留版本锚，但故意不推。因为远端有没有 v* 才是唯一的触发条件——本地怎么打都无所谓。技能里记了一个真实例子：Erebus 项目本地保留 v0.22.0 / v0.23.0，远端没有，从未触发 Release。

这是把 CI 的匹配规则当成发布开关来用，不需要额外配置、不需要环境变量、不需要一个 if。一个字符的前缀，加上”推不推”，就划出了「内部快照」和「对外发布」的楚河汉界。

配套还有一条硬规则：修复优先递增新版本号，不要重指或删除已推的 tag。哪怕新提交只是改了个 CI 文件，也用新版本作为发布点。原因写得很清楚——改写远端历史会被护栏拦、影响协作者与已下载产物的 CI。

五、版本号散落：发布里最常见的回归源

发版时版本号不在一个地方，它散落在六七个文件里。技能仓库专门开了一个 version-sync.md 来列清单，因为这是最高频的错误来源：官网写着 v1.6.9，package.json 是 1.6.10，zip 里的 manifest.json 还是 1.6.8，三个地方互相矛盾，而且全都能正常构建。

形态 版本落点 最容易漏的
Node / 扩展 package.json、manifest.json、package-lock.json（两处：根 version 与 packages[""].version）、官网 hero + 页脚、README 版本行、changelog 官网两处常只改一处；lock 里两处常只改一处
Rust Cargo.toml（workspace 下每个成员 crate 各有自己的 version）、Cargo.lock 根包那条、代码里的 pub const VERSION、README 徽章、changelog workspace 只改根 crate；README 徽章整片漏改
Java / Maven pom.xml 的 <project><version>（多模块用 ${revision} + flatten 插件）、Dockerfile/deploy.sh/compose 里写死的 jar 名、changelog Dockerfile 里的 jar 名带版本号

两个特别阴险的坑：

package-lock.json / Cargo.lock 不能全局替换。 lock 文件里别的依赖可能恰好也是同一个版本号（比如某个依赖就是 1.2.0），一次全局 sed 会误伤。技能给的稳妥做法是：改 Cargo.toml 后跑 cargo check 让 lock 自动跟随，再 git diff Cargo.lock 确认只有目标 crate 变动。Node 侧则先 grep -c '"version": "<旧号>"' package-lock.json 确认命中数（通常 =2），改的时候用带上下文的精确定位。

env!("CARGO_PKG_VERSION") 不用手改，Cargo 会自动注入。写进清单里，是为了防止有人”顺手”把它也改成常量，制造第二个真相来源。

六、Java 专用档：流程的终点就是 tag

java-release-flow 和通用技能是相互独立的，它只管 Java/Maven，而且把自己砍得非常窄：

只做「代码镜像」——提交、推送、打版本 tag 留版本锚。不出 GitHub Release、不打 jar、不部署。发布流程的终点就是 tag 推送 + 验证。

这个边界值得停下来想一下。大部分人听到”发布流程”，默认会往「打 jar → 上传 → 重启服务」上想。但这个技能明确把那一段划到了流程之外，由人工完成。为什么？

因为 Java 项目的部署跟环境强绑定：profile（-P prod，且 profile 常经 Maven 资源过滤写进 jar）、数据库迁移（Flyway 必须先于重启）、回滚链路（保留上一版 jar 与 current 符号链接）。这些东西没有一个是”推个 tag”能覆盖的，硬塞进自动化里只会得到一个看似完整、实则脆弱的流程。

敢把流程的终点画在 tag，比把它一路画到上线更需要判断力。 技能里甚至专门写了一节「部署（流程外，仅留可追溯性建议）」，只给了三条建议：jar 名带版本与短哈希、保留上一版与符号链接可秒回滚、部署留一行日志（时间/版本/操作人）。

另外它对「官网」也设了触发红线：只有用户明确说”编写项目官网”才启动，发布流程中绝不顺手写官网、绝不主动加 pages.yml。这条和”不自动发布”是同一种克制——Agent 最容易犯的错不是把事做砸，是把没人要求它做的事顺手做了。

七、三类「本地假绿」：这块才是真正的技术含量

前面都是流程和边界，这一节是 java-release-flow 里最硬的部分，来自 Music 项目 2026-11-07 的三轮 CI 实测。

核心命题只有一句：本地 mvn test 全绿，说明不了任何问题。 CI 的全部价值，就是「换一台干净机器，复现你在自己机器上得到的结论」。而下面这三类问题，恰恰只有在换机器之后才暴露。

7.1 测试类顺序污染

Surefire 默认 runOrder=filesystem，而 Windows 与 Linux 的目录枚举顺序不同。于是”A 类的删除用例删掉了 B 类 INNER JOIN 依赖的种子行”这种耦合，只会在某一侧暴露：本地永远绿，CI 永远红，看日志还找不到原因，因为两边跑的根本不是同一个顺序。

根治原则不是调顺序，是解耦：测试只操作自己创建的数据行（用唯一标题/探针查回自己的 id），绝不碰 fixture/种子行；删除用例要补两条断言——“自己那行没了”且“种子行必须还在”。只断言前者，就是这次故障的根源。

顺带一个日志读法的坑：MyBatis 的 <== Total: 1 对 SELECT count(*) 恒为 1，因为 Total 是结果集行数不是 count 值。真矛盾要看的是「写入 Updates: 1、JOIN 却 Total: 0」——那说明 JOIN 的那张表行被删了。

7.2 平台编码

Spring Boot 执行 schema.sql 时若不指定编码，按 JVM 平台编码读。Windows 是 GBK，Linux 是 UTF-8。于是 UTF-8 的中文种子数据在 Windows 上读成乱码，like '%周%' 查不到，而 CI 上反而正常——这次是本地红、CI 绿，方向跟第一类正好相反。

推而广之，技能列了一个「变绿之后还要主动查的差异面」：字符集、路径分隔符、换行符、文件名大小写、日志路径。前三类行为本地绿不代表对；第四类更隐蔽——git ls-files 里仅大小写不同的同名文件，在 Windows 上共存无事，到 Linux 才炸；第五类是别在日志里写 Windows 绝对路径。

7.3 热缓存绕过数据库

Redis 里留着历史数据时，读路径命中缓存直接返回，根本不发 SQL。数据库里其实查不到，测试照样绿。这类假绿最气人的地方在于：它证明不了任何关于数据库的代码是对的。

验证前必须清缓存，但有个关键约束——绝不 flushall，本机可能跑着别的项目：

tr -d '\r' 不可省。Windows 版 redis-cli 输出 CRLF，不去 CR 的话，del 删的是”名字里带回车的不存在的键”，静默返回 0，一条也删不掉，而你会以为缓存已经清干净了。

7.4 闭环标准是「三种跑法全绿」

反序证明顺序污染已根治，默认序证明没引入新问题，verify 证明覆盖率门禁达标。只跑一种不算闭环——这句话是整个 Java 档里我最认同的一句。CI 的价值不在于”多跑了一遍”，在于它用不同条件否证了本地结论。

而这里的铁律是：CI 里跑的命令必须和本地一字不差，mvn -B clean verify。绝不为变绿加 -DskipTests、绝不关 jacoco check。一旦为了让 CI 变绿而放宽门禁，这套东西就全白做了——你只是雇了一台机器来替你点头。

八、CI 分诊：按耗时判断故障在哪一层

ci-pitfalls.md 里有一张我见过最实用的分诊表，判断依据不是错误信息，是失败用了多久：

现象 结论 该看哪
十几秒就失败 环境层（容器 / checkout / 工具链），与代码无关 Annotations 第一条 error
跑满几分钟后失败 环境已通，问题在构建/测试 Tests run: N, Failures: M 与 <<< FAILURE
完全没有 run Actions 权限策略拦了官方 actions Settings → Actions → General

还有一条取证技巧很妙：把 upload-artifact 挂 if: failure()，它一旦执行，就宣告”这是构建/测试失败，不是环境失败”——因为环境层的失败根本走不到这一步。日志里 36 files uploaded 说明测试真的跑完了。用一个副产物当信号，比翻日志快得多。

8.1 一个 exit 125：参数拼错位置

GitHub 实际执行的是 docker create … -p 6379:6379 --requirepass <pwd> … redis:7——--requirepass 被当成 docker 自己的未知选项，直接 Exit code 125，Maven 一行都没跑。

8.2 几个散落但很值钱的坑

  • mawk 不支持 POSIX 字符类：Ubuntu runner 默认 awk = mawk，[[:space:]] 直接匹配失败、提取为空。改从 changelog.md 顶部提取 Release 正文时，正则用字面 /^## /。这条同时还解决了另一个问题——runner 上 git tag --format='%(contents:body)' 即便 fetch-depth: 0 也可能读不到附注 tag 正文，导致 Release 正文退化成 tag 名。
  • npm ci --legacy-peer-deps：vite 与 @vitejs/plugin-vue 的 peer 范围常不兼容，本地 node_modules 当初用宽松模式装过所以能 build，CI 从零装就 ERESOLVE。
  • macOS 产物不能用 Linux runner 交叉编译：必须用原生 runner（Intel → macos-13，Apple Silicon → macos-14+）。ARM Linux 倒是可以直接 rustup target add aarch64-unknown-linux-gnu + 换 linker，不必上 Docker。
  • 多平台产物名必须带 target 三元组：各矩阵 job 的二进制同名，归档名不带 ${{ matrix.target }} 就会相互覆盖，最后只剩一个平台。
  • 一次只改一个变量：别顺手把 upload-artifact@v4 升 v5 去消 Node 20 弃用 warning。无害告警修复和真实故障混在一起，失败原因立刻难判断。warning 先留着。

九、网络与验证：别假装你看得到远端

两个技能都花了不少篇幅在”网络不可靠”这件事上，因为它们都真的在推 github.com 时超时过（本机常 21 秒断连）。

统一手法是带连接超时的 push + 有限重试，而且重试次数、间隔、失败后的行为全部写死：

这里有两个容易想当然的地方：

  1. remote 不一定叫 origin。可能是 github、gitee，甚至只有后两个。推送前必须先 git remote -v 查实际列表，别盲推。回退链是 origin → github → gitee，且 github 成功后要追加尝试 gitee 做双镜像（追加失败不影响”github 已成功”的结论）。
  2. 本地分支和远端主分支常不同名：本地 master、远端 main，所以是 git push <remote> master:main，先 git branch -vv 确认。

验证环节则按仓库可见性分流，这一点特别体现”不假装”：

场景 正确做法 不要做
公开仓库 匿名 curl 打 api.github.com 核 Release / Actions / 产物；verify_release.cjs 逐项打印 别依赖 gh，它常不在 PATH
私有仓库 git ls-remote --tags <remote> 核实 tag 是否真在远端；CI 日志请用户从 Actions 页贴 匿名 REST API 必然 404，别反复试
Java 镜像档 只验 tag 存在 不跑 verify_release.cjs——根本没有 Release 可验

verify_release.cjs 本身也写得挺克制：它把「正文首行等于 tag 名」判成警告（多半是 changelog 提取或 mawk 正则出问题），把「资产名未带 target 导致重复」也判成警告并直接指向 pitfalls.md。验证脚本不只报成功失败，还在告诉你失败大概在哪一段。

十、两份 8 步的对照：同一个内核，不同的终点

有意思的是，两个技能都是 8 步。但把两张表并排放，差异比相似更有信息量：

步 release-skills（通用内核） java-release-flow（Java 镜像档）
1 算版本号（git tag -l --sort=-v:refname）· 不可逆，先确认 同左 · 不可逆，先确认
2 按形态查落点清单，一次同步全，grep 复核 只查 pom.xml / Dockerfile jar 名，grep 复核
3 changelog + README + 官网徽章 只改 changelog；官网默认不动
4 typecheck + build；Rust 另加 fmt / clippy / test / 交叉 lint mvn -B clean verify，本地与 CI 一字不差 + 冷缓存反序三跑法（本流程核心价值）
5 分里程碑显式 add，排除 dist/ target/ 同左，排除 target/；提交前 git status 自查 git-lfs 过滤器
6 打附注 tag（多段正文，回显确认） 推送分支（remote 回退链 + 5 次重试）
7 推送 master → 推 v* tag，触发 Pages + Release 打附注 tag 并推（只留版本锚，不触发 Release）
8 verify_release.cjs：Release / Actions / 产物 / 线上徽章 git ls-remote --tags：确认 tag 真在远端，到此结束

三处差异都指向同一个设计判断：

① 第 6/7 步的顺序反了。 通用档先打 tag 再按顺序推两个 ref——git push master 命中 site/** 触发 Pages，git push vX.Y.Z 触发 Release，两个 workflow 各管一段。Java 档没有 Pages、也没有 release workflow，所以先推分支（代码镜像），再打 tag 推上去当锚点，顺序怎么排都不触发 CI。

② 第 3 步的范围差了一个量级。 正式版要同步官网 hero、页脚、README 徽章、changelog 全部对外可见的位置；镜像版只动 changelog，官网连碰都不碰。这正是双轨 tag 那套设计在文档层的延伸——“发不发”决定的不只是 tag 前缀，还有你要对多少份文档负责。

③ 第 4 步的权重完全不同。 通用档把它当门禁；Java 档直接标注为「本流程的核心价值」，因为校验型 CI 是它唯一能自动否证本地结论的手段。一个出了 Release 的项目还能靠产物验证兜底，一个只推 tag 的项目如果连 verify 都放了水，整条流程就什么都不剩了。

而完全一致的是第 1、5、8 步：算版本要确认、提交要显式列举、验证要看远端真实状态。这三步就是内核——它们跟语言、跟产物形态、跟有没有官网全都无关。

十一、Skill 是什么：给 AI 写的不可变约束

写到这里，可以回到开头那个问题了。

这两个仓库表面上是在讲发布流程，实际上它们回答的是一个更当下的命题：当你把执行权交给一个 Agent，怎么保证它不越界？

人的流程文档可以写得松散，因为人有常识、有顾虑、会在推 tag 前犹豫一下。Agent 没有这些。它有目标、有工具、有执行力，唯独没有”这一步是不是不该我做”的直觉。所以给 Agent 写的流程文档，必须把那些人靠常识补齐的隐含约束，全部显式写出来：

  • 「开发完成不是发布理由」——补的是人会有的那道社交闸门
  • 「不可逆动作先回显确切参数并确认」——补的是人会有的那一下犹豫
  • 「5 次仍失败必须停止并贴出最后错误，绝不谎称已发布」——补的是人不敢含糊其辞的那点职业自尊
  • 「修复优先递增新版本号，不要改写已推 tag」——补的是人对协作者的顾及
  • 「既有错误如实标注、不混入本次改动」「warning 先留着」——补的是人不乱动无关东西的分寸

换句话说，Skill 不是”给 AI 的操作手册”，是”把人的分寸翻译成可执行条款”。 技术命令那部分（8 步、mvn -B clean verify、http.connectTimeout=60）反而是最不难写的——难的是把「别自作主张」这种没法编译检查的东西，写成一条 Agent 不会绕过去的规则。

还有一层更实际的：这两个仓库都来自真实事故。ci-pitfalls.md 开头写着「Music 项目三轮实测提炼」，java-release-flow 里记着「来自 Music 项目实测，2026-11-07」，release-skills 里留着 Erebus 的 macOS runner、ARM linker、版本徽章长期没对齐的痕迹。每一条看起来啰嗦的规则后面，都站着一次具体的失败。 这也是为什么它们读起来不像模板，像事故报告。

十二、结论：发布不是技术问题，是权限问题

如果只留一句话，我会留这句：

发布流程里最贵的从来不是构建，是那个一旦按下去就收不回来的动作。

编译错了可以重来，测试挂了可以改，CI 红了可以分诊。但 tag 推上去、Release 生成、版本被下载之后，你只剩下两个都不体面的选项。所以一套好的发布流程，技术部分做到 60 分就够用，剩下 40 分全得花在边界、确认、如实回报上。

这也解释了为什么 java-release-flow 敢把流程终点画在 tag 就停——克制本身就是功能。一个知道自己该在哪停下来的流程，比一个”帮你把所有事都做完”的流程可靠得多。而一个会自己决定发布的 Agent，不管它测试跑得多绿，都不该被允许单独待在发布按钮旁边。

附：这两份技能可以直接抄走的部分

如果你的项目也在折腾发布，下面几处是投入产出比最高的，照搬即可：

  1. 三条红线写进任何自动化流程的开头（不自动触发 / 不可逆先确认 / 失败如实回报）
  2. 双轨 tag：用 v* 触发器 + 无 v 本地 tag，把「快照」和「发布」分开，零额外配置
  3. 版本落点清单 + grep 复核：发版前一条命令扫掉最常见的自相矛盾
  4. 冷缓存 + 反序 + clean verify 三种跑法全绿才算闭环：专治本地假绿
  5. push_with_retry 片段：http.connectTimeout=60 + remote 回退链，别再手动重试了
