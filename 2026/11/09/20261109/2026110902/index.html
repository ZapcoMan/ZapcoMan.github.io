用户亲手点的「允许」，凭什么算漏洞：Android 银行木马的六道工序，从无障碍服务到洗钱

2026-11-09 #设备指纹#黑灰产#风控#Android安全#银行木马#无障碍服务#移动端攻防#覆盖攻击

这套产业链最聪明的地方，是它从头到尾不需要提权。不找内核漏洞，不越狱，不破解沙箱。它需要的每一个权限，都是用户自己点头给的——只不过用户以为自己点的是「安装安全控件」，实际给出去的是「替我看着这块屏幕，也替我按下去」。

在 PC 上要凑齐全套攻击条件，得打穿好几层：拿到凭据要过钓鱼、拿到二次验证码要控短信网关、要转账得绕过 U 盾或设备绑定。而在一台手机上，身份、凭据、支付通道、二次验证全在同一个设备里，还都归同一个操作系统管。这不是四个目标，是一个目标。

所以移动端的黑产没有走「更狠的漏洞」这条路，走的是「更顺的流程」。下面按工序拆这条流水线——六道工序，每一道都有明确的分工、可外包的环节和自己的成本结构。这也是它比单点木马更难防的原因：你打掉其中任何一环，都有人能补上。

一、六道工序全景

# 工序 干什么 谁在做 失败代价
① 投放 把安装链接送到目标面前 流量组 / 话术组 低，换渠道即可
② 诱导安装 让用户自己装上并放行 伪装包 / Dropper 中，包会被查杀
③ 权限获取 拿到无障碍、通知读取等能力 引导脚本 最高，全链瓶颈
④ 凭据采集 账号、口令、OTP、卡号 覆盖页 / 读屏 / 通知监听 中
⑤ 自动转账 在真银行 App 里按完整个流程 自动化脚本 + C2 高，触发风控
⑥ 洗钱分赃 把钱变成不可追的东西 钱骡 / 卡池 / 跑分 高，唯一有现实身份风险的环节

看这张表要注意两点。第一，③ 是瓶颈：前面所有工序都是为了把用户送到那个权限对话框前，后面所有工序都依赖它。第二，⑥ 是唯一暴露物理身份的环节，所以整条链的组织形态是「前五段 online 可外包、最后一段必须线下落地」——这也是各地警方最常从钱骡这一端反向打掉整个团伙的原因。

二、第 ① 道：投放，本质是筛人不是撒网

投放渠道本身没什么技术含量，真正的技术在于筛分。同样的量，撒给随机人群和撒给「正在等快递 / 刚办了退税 / 刚收到银行风控短信」的人，转化率差两个数量级。

渠道 常见话术壳 筛分逻辑
短信 / iMessage 包裹派送失败、ETC 过期、社保认证 广撒，靠低成本换绝对量
即时通讯群 兼职、刷单、投资群「内部 App」 主动筛出有转账意愿的人
仿冒应用商店 / SEO 「XX 银行安全控件」「官方最新版」 用户主动搜索 = 高意图
二维码 / 线下物料 停车缴费、充电、活动登记 场景绑定，信任度最高
二手设备预装 / 供应链 刷机包、保修店「优化」 一次性拿到长期控制

这里有个和 PC 时代很不一样的判断：**移动端钓鱼不追求「像」，追求「顺」。**用户在 6 寸屏上不会去看域名、不会去看证书、也不会去核对包名。短信里一个短链、页面上一个人人见过的蓝色盾牌图标，就够了。相比之下，PC 钓鱼要跟浏览器地址栏、HTTPS 指示器、邮件网关斗一整轮。

从防御侧看，这一段能做的其实有限——渠道在别人的地盘上。真正可控的是第 ① 道和第 ② 道之间的那一秒：用户点开链接之后、安装之前。所以银行侧最有效的动作不是发提醒短信，而是在自己的官方 App 里对「本行从不会要求安装任何安全控件」做反复、具体、非泛泛的告知。

三、第 ② 道：诱导安装与 Dropper，一场和商店规则的猫鼠游戏

直接把完整木马传上应用商店几乎不可能过审，于是行业里分化出标准的两段式投放：

这套结构的经济学很直白：壳被下架的成本极低（换个图标重新传），载荷不进商店所以不必过审。壳与载荷分离还带来一个额外好处——静态扫描在商店侧只能看到壳，看不到后半段。

几个常见的技术点：

手法 目的 对抗什么
动态代码加载（DexClassLoader） 主包不含恶意逻辑 商店静态扫描
载荷加密放在 assets / 图片尾部 躲字符串特征 特征码查杀
延迟投放（装后 N 天 / 特定地区才拉载荷） 躲审核期的动态沙箱 商店自动化检测
版本号伪装成系统更新 提高用户授权意愿 用户判断力
拆分 APK / 多 dex 单点分析看不到全貌 逆向分诊

平台侧的收紧也主要打在这一段。Android 13 引入的**受限设置（Restricted Setting）**是其中最有分量的一条：从侧载来源安装的 App，系统不再允许直接开启无障碍服务与通知监听使用权，会弹出「出于安全考虑，设置受限」并拒绝。这条规则精准打在第 ③ 道的前门上。

黑产的适配方式也随之变化，最有代表性的是会话式安装（session-based install）：不再让用户手动点一个 APK，而是用一个自己有安装权限的「安装器」把包通过 PackageInstaller.Session 分片提交，系统看到的来源就不再是「未知文件」，从而绕开受限设置的前置判断。平台随后又收紧了这条路径。这个来回很典型：移动端攻防的主战场不在内存破坏，在权限授予流程的措辞与边界上。

四、第 ③ 道：无障碍服务，整条链真正的核心

AccessibilityService 是 Android 为视障用户设计的辅助能力。它的设计前提是「申请者是善意的」，因此一旦用户开启，它能拿到的是：

能力 对应 API / 行为 对木马的价值
读取屏幕上任意文字 AccessibilityEvent / getRootInActiveWindow() 读余额、读验证码、读收款人
遍历控件树 AccessibilityNodeInfo 按 id / 文本定位按钮
模拟点击与输入 performAction(ACTION_CLICK / ACTION_SET_TEXT) 代替用户完成转账
全局操作 performGlobalAction（返回、 HOME、通知栏） 阻止用户退出、关闭弹窗
监听窗口变化 onAccessibilityEvent 判断「银行 App 已前台」的时机

把这五行连起来读，你会发现它已经是一套完整的屏幕级远程控制：能看、能点、能输入、能知道什么时候该动手。而且全程不需要 root，不需要 exploit，不需要越狱。在 PC 上实现等价能力要写驱动或注入进程，在这里只需要一个系统设置开关。

更关键的是权限提示的措辞。系统弹窗说的是「使用无障碍服务可以帮您……」，展示的是辅助功能语境，用户看到的是「读屏辅助」，看不到的是「此应用将能观察您的所有操作并代为点击」。这不是 Android 的实现漏洞，是权限模型与用户心智模型之间的落差——安全提示描述的是能力，用户理解的是用途，两者之间那一整段被黑产拿去当成了通道。

从检测角度，这一环反而是最亮的信号。一个银行 App 在前台时，若设备上存在非辅助类应用启用了无障碍服务，这本身就是极高危的组合：

企业 MDM 和银行风控都可以在服务端把这个状态作为一个布尔信号采集。「无障碍开启」不等于恶意，但「无障碍开启 + 银行 App 前台 + 应用为侧载来源」基本就等于事件。

五、第 ④ 道：凭据采集，四条互相兜底的路径

拿到无障碍之后，采集手段不止一种。真实样本里通常同时上三四条，因为任何单条都可能被某个系统版本或某家银行挡住：

路径 拿什么 依赖 近年收紧情况
覆盖页（Overlay） 账号、口令、卡号 SYSTEM_ALERT_WINDOW / 无障碍绘制 Android 12 起限制不可穿透的覆盖层，仍需用户授权
屏幕读字 余额、OTP、交易结果 无障碍 未收紧，但 FLAG_SECURE 可阻断截图/部分读取
通知监听 短信验证码、推送 OTP NotificationListenerService Android 13 起通知权限改为运行时授予
自定义输入法 逐键记录 用户主动切换键盘 未收紧，但启用步骤多、转化低
短信读取 OTP RECEIVE_SMS 应用商店权限声明审查大幅收紧，多数地区已不可用

覆盖攻击的经典形态是：监测到目标银行 App 进入前台 → 立刻在它上面盖一张像素级复刻的登录页 → 用户输入的账号口令直接进 C2。因为盖的是「自己画的窗口」，银行 App 本身完全不知道发生了什么，服务端的登录日志看起来就是一次正常登录。

FLAG_SECURE 是这里少数几个由 App 自己就能加的硬防护：设置了这个标志的窗口，系统禁止截图、禁止在非安全显示器上录制，部分读屏链路也会因此拿不到内容。它的代价是用户不能截屏（银行 App 里通常可以接受），收益是把「读屏」这条最通用的采集路径砍掉一截。

一个容易被忽略的细节：OTP 的价值在下降，但没归零。设备绑定、生物核身、交易签名确实让「拿到验证码就能转账」不再普遍成立，可黑产的解法不是去破这些机制，而是在真银行 App 里、用用户自己的会话、走完整个流程——这就引出了第 ⑤ 道，也是为什么第 ④ 道里最值钱的其实不是口令，而是「用户此刻正在操作银行 App」这个时机信号。

六、第 ⑤ 道：自动转账，把风控当成要绕的下一关

这一段的本质是 UI 自动化。载荷里通常带一份按银行 App 版本维护的「脚本配置」：包名、Activity 名、控件 resource-id 或文本、点击顺序、金额策略。C2 下发配置，端上按配置执行。

注意 guard 和 amount_rule——这是整条流水线里最「工程化」的地方，也是最像正经软件的部分。团伙会针对每家银行的风控规则维护分支，甚至做 A/B：同一批受控设备分两组跑不同金额策略，看哪组成功率高，再把配置推给全网。这和之前拆 SEO 投毒团伙时看到的「用统计工具核算 ROI、按效果迭代仿冒主题」是同一种组织能力。

端侧还要解决三个存活问题：

问题 常见应对 平台侧对策
被卸载 注册 Device Admin / 设备管理器，拦截卸载；隐藏图标 Android 逐步限制 Device Admin 的可用能力
被杀后台 前台服务 + 常驻通知；JobScheduler 拉活 后台启动限制、前台服务类型声明
被用户发现 伪装成系统设置页、拦截返回键 让用户能从系统设置里看到已启用的服务

C2 通道也在变。早期直连固定 IP/域名容易被封，现在更常见的是搭在合法云消息服务上（FCM、第三方推送、公开即时通讯 Bot API）——流量看起来和普通 App 没区别，且不需要自己维护基础设施。对防守方来说这很难受：封域名封不动，只能靠端侧行为检测。

七、第 ⑥ 道：洗钱，唯一有肉身的一环

钱转出去不等于拿到手。这一段的分工通常是：

层级 角色 特征
一层卡 钱骡账户、租来的实名卡 收款后几分钟内转出，生命周期以小时计
二层 分散到多张卡 / 多个支付账户 拆小额，避开单笔阈值
三层 换成虚拟资产、礼品卡、实物代购 切断法币链路
结算 团伙内按贡献分成 常用链上资产跨地域结算

这一段的技术含量最低，但风险最高：卡主要实名、取现要露面、跑分平台要落地。所以整个团伙的组织形态往往呈哑铃状——线上部分高度模块化、可外包、可替换，线下部分却是少数几个固定的人。执法侧从这一端往回打，能牵出前面的技术组，反过来从线上往回打则经常断在匿名基础设施上。

这也解释了一个反直觉现象：打击效果最好的往往不是技术封堵，而是压低一层卡的供给。技术侧封掉一个载荷，团伙换壳重传的成本是一天；压住卡池，前面五道工序全都会因为「钱出不去」而停摆。

八、Android 版本收紧史：一条被逐步关窄的路

把系统版本和对应的收紧点排开，能看清这场攻防的方向：

版本 / 时间 收紧内容 打在哪一道 黑产适配
Android 10 后台启动 Activity 限制 ⑤ 覆盖页弹出时机 改用无障碍与前台服务触发
Android 11 包可见性（<queries>） ④ 枚举已装银行 App 通过无障碍窗口事件反推
Android 12 覆盖层可隐藏、需显式授权 ④ 覆盖页 转向纯读屏 + 模拟点击
Android 13 通知运行时权限、侧载应用的受限设置 ③ ④ 会话式安装、引导用户手动解锁
Android 14+ 无障碍进一步收紧、后台与前台服务类型细化 ③ ⑤ 更依赖社会工程引导用户「亲手放开」
Play Protect 实时扫描侧载应用、按行为告警 ② 延迟投放、无网络时不拉载荷

看得出一个规律：**平台能封的是「能力」，封不住的是「用户主动授予」。**每一轮收紧之后，黑产都会把成本从技术侧转移到话术侧——既然系统不让直接开，那就教用户自己进设置里一步步开。于是攻击链的最后一道防线，落在一句用户看得懂的解释上。

九、检测与取证：哪些信号端侧藏不住

信号 采集位置 判据
侧载安装来源 包管理器 / 安装来源 API 银行类操作 + 侧载应用 = 高危
无障碍服务由非辅助类应用启用 系统设置 与包名白名单比对
通知监听使用权 系统设置 非通知类应用申请即为异常
覆盖窗口出现在银行 App 之上 窗口层级 / 无障碍事件 前台包名与窗口所有者不一致
银行 App 前台时发生高频点击 端侧行为埋点 点击间隔过于规则、无触摸轨迹
设备存在 Device Admin 且非 MDM 系统设置 拦截卸载的典型特征
应用在后台持续拉活、常驻通知 电池 / 用量统计 与宣称功能不匹配

银行侧真正可行的策略不是「识别木马」（这是杀软的活，而且永远滞后一个版本），而是把设备状态当成风控输入：无障碍开启、侧载来源、覆盖窗口、无触摸轨迹的自动点击——这四个信号里命中任意两个，就把当前会话降级到「只允许查询、禁止转账」，并把二次确认推到另一台已绑定设备或独立通道上。木马能控制这台手机，控制不了用户手上的第二台设备，也控制不了柜面与电话。

关键设计原则：**不要在已被攻陷的设备上做验证。**凡是「在同一块屏幕上弹一个确认框」的二次确认，无障碍服务都能替用户点掉。

十、三层防御清单

层 动作 说明
用户侧 关闭「安装未知应用」；定期查看已启用的无障碍服务列表 第 ③ 道唯一能被用户自己关掉的门
用户侧 只从官方商店装；银行 never 要求装「安全控件」 打断第 ① ② 道的话术前提
银行侧 P0 登录与交易窗口设 FLAG_SECURE 砍掉截图与部分读屏路径
银行侧 P0 无障碍开启时降级交易、二次确认走独立通道 直接让第 ⑤ 道失效
银行侧 P0 设备绑定 + 行为生物特征（触摸轨迹、按压、节奏） 自动点击与真人轨迹差异明显
银行侧 P1 转账收款人首次变更设冷静期 / 延时到账 给第 ⑥ 道留追索窗口
平台侧 P1 侧载无障碍收紧、Play Protect 行为检测 打第 ③ 道
行业侧 P2 卡池治理、可疑一层卡快速冻结与情报共享 打第 ⑥ 道，杠杆最大
行业侧 P2 样本与配置指纹共享（脚本配置比样本本体更稳定） 缩短新变种的检测空窗

最后一行值得展开：同一个团伙换十次壳、换十次签名，它下发的转账脚本配置往往还是同一套结构（控件 id、点击顺序、金额策略）。所以情报共享里最值钱的不是 hash，而是配置模板与 C2 通道特征——这跟恶意样本分析里「IOC 分层，hash 最易变、TTP 最稳定」是同一条道理。

十一、结尾：这不是漏洞，是授权

回头看六道工序，会发现整条链上没有任何一处内存破坏、没有任何一个 CVE。它靠的是三样东西：

  1. 一个为善意场景设计的高权限接口（无障碍服务）
  2. 权限提示与用户理解之间的落差（能力 vs 用途）
  3. 四样高价值资产集中在同一块屏幕后面（身份、凭据、支付、OTP）

所以「用户亲手点的『允许』，凭什么算漏洞」这个问题，答案其实有点冷：**它确实不是漏洞，这比是漏洞更难办。**漏洞可以打补丁，授权流程只能被重新设计，而每一次重新设计都要在可用性、无障碍诉求和安全性之间重新谈判。

从防守角度最值得带走的一句话是：**当整台设备都可能被代为操作时，可信的根就不能还放在这台设备上。**独立通道、第二设备、冷静期、行为生物特征——这些机制的共同点不是「更难被绕过」，而是「根本不在这块屏幕的可达范围内」。

本文仅用于授权环境下的安全研究、风控建设与反欺诈科普。文中内容与配置示意用于识别与防御，不涉及可用载荷实现，请勿用于任何未授权场景。
