设置里翻不到它，jadx 里它自己全招了：SystemHelper.apk 的四类采集代码、60+ 厂商反射适配与 5 个上报端点

2026-11-09 #SystemHelper#Android逆向#jadx#OMA DM#TelephonyManager#UsageStats#反射适配#隐私合规

上一篇写这个组件时，我把它当成一场舆情来拆：谁先发帖、谁转述了什么、哪些说法够不上证据。后来读到「kali笔记」2026 年 11 月 8 日那篇《来看看SystemHelper干了什么？》，才发现问题不在我写错了什么，而在整个视角就不对——人家把 APK 从手机里拖出来，反编译，逐文件把调用点贴了出来。

于是这篇推倒重来。不谈传闻，不谈时间线，只谈代码：一个 1.6 MB 的 APK 里，定义了哪些字段、调了哪些 API、给 60 多家厂商写了多少反射适配、往哪 5 个地址发东西，以及哪些事是静态反编译根本证明不了的。

方法上要说清三件事：

边界 说明
单样本 一个 APK、一台设备、一个版本；不同品牌/固件版本的组件行为可能不同
静态方法 jadx 反编译 + 代码阅读 + AI 辅助归纳，看到的是「代码能做什么」，不是「运行时做了什么」
AI 辅助 配图结论由作者将反编译源码交给 AI 分析得出，属于归纳性结论，需要按代码逐条复核

**静态分析能证明能力，不能证明行为。**这句话决定了本文后面每一段能写多重。

二、样本指纹：先把这个 APK 钉死

图 1 给出的样本信息是整篇文章的地基，逐项抄录如下：

项目 值 值得注意的地方
文件名 SystemHelper.apk（约 1.6 MB） 体积极小，符合「一个采集与上报客户端」而非完整应用
SHA256 416d0fc0405fc19b243e72f2a7963517e5b88991a7dfac494934449969a6015d 可用于比对不同设备取出的样本是否同一份
包名 com.mobiletools.systemhelper 与 2023 年学术论文点名的包名一致
版本 versionName 1.2-20220907（2022-09-07 构建），versionCode 3 构建于 2022 年，不是 2026 年才出现的新组件
sharedUserId com.mobiletools.systemhelper.uid（共享 UID） 与同签名组件共享 Linux UID，越过普通沙箱的数据隔离
SDK minSdk 24（Android 7.0）/ targetSdk 33（Android 13） 横跨七个大版本，解释了后面为什么需要海量兼容代码
签名 APK Signing Block + META-INF/CERT.RSA 标准 APK 签名方案，具体签发主体需验签确认

三个容易被跳过的点：

  • **版本号里的日期是最硬的一条时间证据。**2022-09-07 构建、versionCode 只有 3，说明这套代码在两年前就已成型。舆论场里「新出现的监控组件」这个说法，至少对这份样本不成立。
  • **sharedUserId 比包名更关键。**普通 App 各自一个 UID，数据目录互不可见；声明共享 UID 后，同签名、同 UID 的组件可以互读数据、共享权限。这是系统级组件才玩得起的安排。
  • **minSdk 24 到 targetSdk 33 的跨度，几乎预告了后面的 60+ 适配。**Android 7 到 13 之间，设备标识符读取权限、后台定位、非 SDK 接口管控、双卡 API 全都变过好几轮。

顺带对一下旧稿：我之前写的是 1.2-20230228，与本次配图的 1.2-20220907 不一致。这不是谁抄错，更可能是不同设备/不同批次取出的样本版本不同——所以任何「所有手机上都是这一个版本」的推断都不成立，样本哈希必须和结论绑定写。

三、从 /product/priv-app 到 jadx：一条只读取证链

原文的起步只有两步，都是只读操作：

adb pull 是取文件，不是卸载、冻结或刷机；设备需为本人所有且已授权调试。本文不提供任何改动系统分区的操作。

路径本身比命令更有信息量：

安装位置 典型权限来源 用户可见性 普通 App 能否拿到同款权限
/data/app 用户安装，运行时授权 可见、可卸载 否
/system/app 出厂预置，仍受常规权限模型 通常可见 否
/system/priv-app 平台签名 → signature 级特权 常无图标 否
/product/priv-app 厂商/产品分区的特权预置 常无图标 否

组件落在 priv-app，意味着 getImei()、getSubscriberId()、后台读取使用统计这类普通 App 在 Android 10 之后基本拿不到的能力，在出厂时就被授予了。它不是绕过了权限模型，而是从一开始就不站在普通 App 那一侧。

这也解释了一个反直觉的事实：**这类组件不需要「漏洞」。**它拿到的每一个 API，都是系统按签名特权正常发放的。

主文里还有一处非常关键的分流逻辑，在 device/DeviceManager.java:539-552：

按主文说明，联通号段（MNC 46001 / 46006 / 46009）的数据为明文采集上报，其他运营商卡走 MD5 匿名化。这里有两个层次：

  1. **「匿名化」不等于匿名。**MD5 是确定性无盐哈希，手机号 11 位、IMSI 有固定前缀，取值空间有限，彩虹表可反查。对可枚举标识符做 MD5，在工程上通常只算「脱敏」，不算不可逆匿名化。
  2. **分流依据本身是代码里的 isUnicomNetwork 判断。**它说明采集策略按运营商做了区分，但判断分支是否覆盖所有情况、被 MD5 的字段是否还在别处以明文出现，都要看完整调用链，不能凭这一屏下结论。

**这 60 多个 Reader 不是「功能多」，是 Android 碎片化的成本。**同一件事（拿双卡 IMEI、拿手机号、拿小区）在不同厂商、不同芯片平台、不同 Android 版本上要用完全不同的入口。用反射把它们兜住，短期可行，长期极脆——每一个 hidden API 都是一颗随系统升级可能失效的钉子。从工程角度看，这部分代码恰恰最像「老系统组件的包袱」，而不像一个 2026 年新写的采集器。

九、定性：不是木马，但也不是「没什么」

图 2 的定性结论照录如下：

这是中国联通（China Unicom）的 OMA DM 设备管理/注册激活预装应用，用于定制机（合约机）的设备注册、数据采集与上报。服务器为联通官方域名。

不是恶意木马：无短信拦截/发送、无通话权限、无摄像头/麦克风、无远程命令执行。但属于高度敏感的数据采集类应用（采集手机号、基站定位、应用行为画像）。

这段结论我认同，而且认为它比舆论场里的多数标题更值得传播。两端都要守住：

常见误读 代码层面的事实
「这是木马/后门」 无远程命令执行、无短信与通话权限、无摄像头麦克风；能力集中在读取与上报
「它在偷看聊天记录」 四类采集里没有任何内容读取路径，取的是元数据与统计值
「只是普通运维数据，无所谓」 IMEI + 手机号 + 小区 + 应用使用与流量，具备可关联的身份画像能力
「它 2026 年才被塞进手机」 样本构建于 2022-09-07，包名 2023 年已见诸学术文献
「明文 HTTP = 内容裸奔」 主注册走 RSA+AES；明文的是另外几条通道，两者不能混写
「MD5 过就匿名了」 无盐 MD5 对可枚举标识符不等于不可逆匿名化

反诈与设备注册本身是真实、正当的业务需求，运营商对定制机做激活注册、网络质量采集也有明确的运维理由。把这套组件整体污名化，既不准确，也不公平；但反过来，用「不是木马」来结束讨论同样草率——风险不来自恶意，来自权限范围与可关联性。

十、证据边界：这份分析能证明什么，不能证明什么

这是整篇文章最该被记住的一节。把结论按重量分三层：

层级 结论 依据
A · 代码可见 字段常量定义、四类采集调用点、5 个端点字符串、MD5 分流、反射适配链、样本指纹 jadx 输出、配图、主文代码
B · 需运行时验证 是否真的每次都采集全部字段、触发频率、请求体实际内容、加密实现强度、5 个端点当前是否都活跃 需要抓包、动态插桩、多机型复测
C · 无法由本材料判断 数据留存周期、谁可访问、后续如何使用、与任何具体外部事件的因果、其他品牌/版本行为是否一致 超出单样本静态分析的能力

再列几条必须显式写出的限制：

  • **静态分析看到的是能力，不是行为。**代码里存在 getLine1Number()，不等于每台设备每次都拿到了号码并返回了非空值。
  • **AI 辅助归纳要复核。**配图里的定性结论与能力矩阵由作者把反编译源码交给 AI 得出，本文按主文贴出的代码逐条对过，但结论性表述仍应视为作者判断。
  • **图中遮挡部分不还原。**5 个端点的地址段有打码，任何「补全域名」的写法都是编造。
  • **不要把两个组件混回来。**社区讨论里那套「约 3 秒录屏、加密上传」的行为属于另一个系统安全组件，主文与本文分析的是 SystemHelper.apk，两者不是一回事。
  • **不作合规性定性。**是否适用「最小必要」、如何归类无图标的 priv-app 服务，涉及具体产品形态与监管解释，应由官方给出结论。

十一、防御与合规视角：该公开什么，该问什么

先说不做什么：**本文不提供卸载、冻结、禁用或刷机指令。**这类组件可能与 SIM 注册、双卡识别、运营商配置下发相关；不同机型与固件版本行为不同，别人「亲测没事」不是你的保险；改动系统分区还可能影响保修。为了「清理」去装来路不明的一键工具，方向与担忧正好相反。

用户真正需要的，其实是一份能对上号的清单：

应当公开的最小信息集 为什么
系统级组件清单（包名、归属方、版本、安装路径、样本哈希） 让「它在不在」可查，而不是靠 root 后翻目录
每个组件的采集字段与触发条件 让「收了什么」可被第三方复核
端点清单、传输保护方式、数据去向与留存周期 让「传给谁、怎么传」有答案
用户可操作的开关及其真实效果 让「关了会怎样」可预期
版本变更说明与回退路径 让 OTA 带来的行为变化可追溯
第三方独立验证与公开回应机制 让下一次不必靠一条帖子才被发现

工信部、国家网信办《关于进一步规范移动智能终端应用软件预置行为的通告》（工信部联信管函〔2022〕269 号）要求「最小必要」「谁预置、谁负责」、保障知情权与选择权，并明示预置应用软件信息。而一个无图标、平台签名、以服务形态存在的组件，究竟按「预置应用软件」还是按「系统基本组件」管理，公开讨论里仍缺少明确说法。这里只指出分类地带的存在，不作定性。

能做的、也更有效的四件事：

动作 价值
只读核对（在自有设备上查看系统应用、比对包名与版本） 把「听说」变成「我核对过」
阅读厂商隐私政策与开发者文档列明的数据类型 分清代码事实与官方披露
通过厂商客服、官方反馈入口、12321 等正规渠道反馈 让诉求进入可被统计与回应的通道
关注后续公开说明，尤其是字段清单、留存周期与开关设计 避免用未经证实的信息做长期判断

十二、结论

把 1.6 MB 的 APK 拖出来反编译之后，能确定的东西其实相当具体：一个 2022 年构建、带 sharedUserId 的 OMA DM 预装组件，用四类代码读取设备与 SIM 标识、小区位置、应用使用与流量、IP；用 60 多个反射适配跨过厂商碎片化；把主注册数据经 RSA+AES 发往运营商端点，并对非联通卡做 MD5 脱敏。

**它不是木马。**但把它归为「普通运维」也不诚实——一套绑定了唯一设备标识、手机号、位置与行为时间序列的系统级采集，讨论的重点从来不是恶意与否，而是可关联性、透明度与可预期性。

这轮重写换掉的不只是内容，是提问方式：从「网上都说了什么」换成「代码里到底写了什么，以及代码证明不了什么」。前者靠转述，后者靠可复核的调用点。真要继续往下查，缺的也不是更激烈的措辞，而是多机型样本哈希、运行时抓包、以及一份官方给出的字段与端点清单。
