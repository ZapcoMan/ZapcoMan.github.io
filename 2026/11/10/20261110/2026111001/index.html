网络安全

服务器没被打穿，管理员权限却自己长腿跑了：IMDS、角色信任策略与云上那条没有边界的权限链

2026-11-10 #SSRF#最小权限#权限提升#IAM#IMDS#临时凭据#AssumeRole#CloudTrail

本地环境里，拿到一台机器的 shell，你拿到的是这台机器。云上不一样：一台机器上往往躺着一份能操作整个账号的凭据，而且它是云厂商亲手发给你、定期自动轮换、看起来完全合法的。攻击者也用不着「偷」——按规定的接口问一句，它就给了。

传统渗透里我们习惯画网络边界：外网、DMZ、内网、核心区，一层层往里打。到了云上，这套图会骗人。两台网络完全不通的虚拟机，只要共用一个角色、或者角色之间能互相 Assume，它们在权限图上就是同一台机器。真正隔开的不是 VPC、不是安全组，而是 IAM 策略里那几行 JSON。

所以云上最舒服的入侵路径，往往不是打穿什么，而是让平台自己把权限交出来：一个 SSRF，一次元数据请求，一份临时凭据，然后顺着角色信任关系一路换下去。整条链上没有任何缓冲区溢出、没有任何 0day、没有任何告警会告诉你「被入侵了」——因为每一步在日志里都叫「合法调用」。

一、先把概念摆正：云上「身份」才是边界

本地机房 云上对应 关键差别
网段 / 防火墙 安全组、NACL、VPC 网络隔离仍在，但不再是主要边界
主机账号 / 本地 sudo IAM 主体（用户、角色、联邦身份） 身份不绑机器，可跨主机、跨账号、跨区域
服务账号口令 Access Key / STS 临时凭据 静态口令变成可自动签发的短期令牌
域管理员 账号根用户 / AdministratorAccess 权限可被策略组合间接拼出来
审计日志 CloudTrail / 云审计 记录「谁调用了哪个 API」，不判定「是否合理」
一台主机被拿下 一份角色凭据被读走 影响面从单机扩展到该角色能碰的一切

这张表里最要命的是最后一行。**云厂商为了让应用不必硬编码密钥，设计了「实例角色」：跑在这台机器上的程序，可以向一个本地链路本地地址索取临时凭据。**设计本身是好的，它消灭了明文 AK 泄露；代价是把「能在这台机器上发一个 HTTP 请求」和「拥有这个角色的全部权限」划了等号。

而「能发一个 HTTP 请求」，在 Web 应用里实在太常见了。

二、IMDS：那个「别人访问不到」的假设

实例元数据服务（Instance Metadata Service，各大云都有对应实现）监听在链路本地地址 169.254.169.254。它不走常规路由、不出主机网卡，设计者默认只有本机进程能碰到它。

问题在于，「本机进程」里包括那台跑着你业务代码的 Web 服务器。一旦应用存在服务端请求伪造（SSRF）——比如「输入图片 URL 我来抓预览」「填个 Webhook 地址我帮你探测连通性」「从 URL 导入配置」——攻击者填的地址就可以是元数据端点。

维度 IMDSv1 IMDSv2
请求方式 直接 GET /latest/meta-data/iam/security-credentials/<role> 先 PUT /latest/api/token 换 token，再带 X-aws-ec2-metadata-token 头请求
典型 SSRF 能否直接利用 能，一个 GET 就够 单纯 GET 型 SSRF 打不通，需要能控方法或请求头
防护实质 无 要求攻击者具备「发 PUT + 自定义头」的能力
网络层额外约束 无 可配合 HttpTokens=required 与 HopLimit=1
是否免疫所有 SSRF 否 否：带 header 注入、CRLF、代理型 SSRF、可回显的 SSRF 仍可能绕过
遗留风险 老镜像、老 SDK、容器里手写的 curl 脚本 应用自身若充当反向代理并转发原始头，token 机制形同虚设

要特别说清一件事：IMDSv2 不是「修好了 SSRF」，它只是把攻击门槛从「一个 URL」抬到「一个可控的请求方法与头」。很多文章把它写成银弹，那是误读。真正的边界在于：只要应用能把外部输入变成对外发起的 HTTP 请求，且这个请求能触达链路本地地址，风险就还在。

常见的几条触达路径：

触达方式 说明
直接 SSRF url 参数被服务端直接请求，最经典
反向代理 / 网关误配 应用转发外部请求时保留 Host 与自定义头，等于帮攻击者完成 PUT
容器内访问 容器网络里 169.254.169.254 通常照样可达，Pod 拿的是节点角色或 IRSA 映射的凭据
无头浏览器 / 服务端渲染 SSRF 藏在图片加载、PDF 生成、链接预览里
依赖组件 图片处理、URL 抓取、OAuth 回调探测等第三方库的隐式请求
云函数 函数环境里的元数据/凭据端点，配合环境变量注入

关键是多出来的那个 PUT 和那个自定义头：只控制 URL 的 SSRF 到这里就断了，而能控制请求方法、或能让应用原样转发请求头的场景仍然能过。把它理解成「门槛抬高」而不是「漏洞修复」，后面的防御排序才不会排错。

2019 年那起广为引用的大型银行数据泄露事件，公开材料描述的正是这条链：一个 Web 应用层的 SSRF，读到实例角色的临时凭据，再用这份凭据去列举并读取对象存储里的桶。事后讨论大多聚焦在「WAF 为什么没拦」，但更该问的是：为什么一台面向公网的 Web 服务器，会挂着一个能读全量数据桶的角色？

三、临时凭据为什么反而更难防

很多团队一听「临时」两个字就放心了。恰恰相反，短期凭据在检测和响应上有几个很别扭的性质：

性质 后果
自动签发、无需人工审批 攻击者不需要拿到任何「密码」，没有口令爆破痕迹
有效期短但可刷新 只要还占着那台机器，就能持续换新凭据，封一批没用
调用来自合法 API、签名合法 云审计只看到「某角色调用了 GetObject」，与正常业务难以区分
凭据不绑定来源 IP 拿到后可从任意网络重放，包括攻击者自己的机器
归属是角色而非个人 归因困难，日志里没有「谁」，只有「哪个角色」
无 MFA 概念 机器身份本来就不做二次认证
权限即角色权限全集 应用只需要读一个桶，角色却常挂着通配策略

一个很实用的判断：**如果一份凭据能在你的 VPC 之外被正常使用，那它就不该被放在能被 SSRF 触达的地方。**这不是配置细节，是设计约束。

顺带说个常被忽略的点：凭据泄露后，攻击者的第一通电话往往是 GetCallerIdentity。这个 API 不产生资源变更、不写数据、几乎不触发任何告警，却能一次性告诉他「我是谁、账号 ID、ARN、能走多远」。它是最便宜的侦察，也是防守方最容易漏掉的一条日志。

四、角色信任策略：四种常见写法错误

权限提升的主战场不在「策略允许做什么」，而在「谁能变成这个角色」。信任策略（Trust Policy）写松了，等于把门钥匙挂在门把手上。

错误写法 问题 更稳的写法
Principal 用 "*" 任意主体可尝试扮演，只靠后续策略兜底 精确到账号根、具体角色 ARN 或联邦主体
只写信任、不加 Condition 缺失上下文约束，任何来源的 AssumeRole 都成立 加 aws:SourceIp、aws:PrincipalOrgID、时间/标签条件
跨账号缺 sts:ExternalId 典型的混淆代理人（confused deputy）场景 第三方代管场景强制外部 ID
联邦 OIDC 信任不限制 sub 任意仓库、任意分支、任意工作流都能换到生产凭据 限制 repo:org/name:ref:refs/heads/main 等具体声明
允许 iam:PassRole 且不限制服务 可把高权角色递给任意可创建资源的服务 iam:PassedToService 条件限定具体服务
允许角色更新自己的信任策略 等于允许把后门写进门锁本身 把 UpdateAssumeRolePolicy 从业务角色剥离

注意 Principal 里写账号根并不等于「把权限给了根用户」——它表示「由该账号下的身份策略决定谁能扮演」，真正的收口还得靠对方账号内的 sts:AssumeRole 授权与这里的 Condition 共同完成。这一点常被读反。

CI/CD 里的 OIDC 联邦是这几年最值得单独讲的一块。它本意是好事：不再往流水线里塞长期 AK，改用短时令牌交换。但如果信任条件只写到「来自这个身份提供商」，那么该提供商下任何一个能触发工作流的仓库、任何一次 PR 里的脚本，都具备换生产凭据的资格。联邦解决的是「长期密钥」，没有解决「谁有资格」。

五、从一份凭据到整个账号：权限提升路径表

拿到初始角色之后，攻击者不会立刻去翻数据，而是先画权限图。下面这些动作单独看都「合法」，组合起来就是提权：

已有权限 组合动作 效果
iam:PassRole + lambda:CreateFunction 创建函数并挂上高权角色 用函数执行角色权限，绕过自身限制
iam:PassRole + ec2:RunInstances 起一台挂高权角色的实例 登录新实例即可取得角色凭据
iam:CreateAccessKey 给别的用户创建 AK 直接变成另一个身份，长期可用
iam:AttachUserPolicy / AttachRolePolicy 给自己挂 AdministratorAccess 一步到位
iam:UpdateAssumeRolePolicy 改信任策略加入外部账号 留下跨账号后门
sts:AssumeRole 链 A→B→C 逐跳切换 单看每一跳都合规，全链越权
iam:PutRolePolicy 内联策略写通配 不留独立策略对象，审计更隐蔽
secretsmanager:GetSecretValue 读数据库口令/第三方 token 横向出云、进入业务系统
kms:Decrypt + 数据读取 解开加密数据 单独禁读无用，密钥权限也是数据权限
s3:PutBucketPolicy 给桶加一条允许外部账号 不搬家、不下载，直接开一条长期读取通道
events:PutRule + PutTargets 建定时事件触发后门函数 无进程、无主机的持久化
cloudtrail:StopLogging / DeleteTrail 关审计 通常紧随提权之后，本身就是最强告警

这张表想说明的不是「有哪些 API 危险」，而是：**IAM 的危险性来自组合，不是来自单个动作。**逐条审策略永远审不出问题，得看「从当前主体出发，能到达哪些状态」，也就是可达图，而不是允许列表。

六、持久化：不打进程，改配置

云上的持久化比主机上省事得多，因为配置本身就是「状态」，改一次就一直在，不需要驻留进程、不需要重启存活。

手法 藏在哪 为什么不容易被发现
新建第二份 Access Key IAM 用户/根用户 用户最多两份 AK，管理员很少逐份核对
在信任策略里塞外部账号 角色 Trust Policy 策略是文本，改动不产生新资源
定时任务 + 后门函数 事件规则 无主机、无进程，只在触发时活动
高权角色的内联策略 角色内联策略 不在托管策略列表里，巡检容易漏
桶策略/对象 ACL 授权外部账号 存储层 数据在原地，无外传流量峰值
镜像/启动模板注入 自定义 AMI、启动模板 每次扩容都自动「复活」
容器镜像里埋环境变量 镜像仓库 重新部署即重新带入

对应的排查顺序也该反过来：先查「身份与策略发生了什么变化」，再查「主机上有没有异常进程」。云上排查从进程开始，通常已经晚了一步。

七、对象存储与 Serverless 的两个特有面

对象存储的坑在于权限是「多层叠加」的：桶策略、ACL、公共访问阻断、账号级设置、对象自身加密、预签名 URL，任意一层松了都会漏。尤其预签名 URL——它是一段把「持有者的权限」临时封装进 URL 的东西，转发给谁，谁就在有效期内拥有这份权限。它不产生新的 IAM 实体，日志里也只是一次普通的 GetObject。

Serverless 的坑在于「凭据与代码同处一室」：函数环境变量里常塞着数据库口令、第三方 token；函数的执行角色又往往图省事给了通配；事件源（队列消息、对象上传通知、API 网关参数）全都是外部可控输入。于是「一个恶意输入 → 函数用高权角色执行 → 结果写回外部可达位置」这条链特别短。函数没有主机可以给你查进程，唯一能查的只有调用日志和角色权限。

场景 常见误配 收敛方向
静态网站托管桶 为图方便开公共读，误把日志桶一起放开 公共访问阻断 + 按前缀隔离桶
上传回调 对象名直接拼进下游命令/路径 白名单字符、隔离命名空间
预签名 URL 有效期过长、权限过大、可转发 短 TTL、最小动作、绑定来源
函数环境变量 明文长期密钥 移到密钥管理，运行时按需取
函数执行角色 复制粘贴通配策略 一函数一角色，按 API 收敛
事件源 未校验消息体来源与结构 入参校验 + 事件源鉴权
层/依赖 共享层被污染影响全部函数 固定版本摘要、独立审计

八、检测：云审计里真正该盯的几件事

CloudTrail 类日志的特点是「全都是合法调用」，所以检测思路不是找「非法」，而是找「不合常理」。

事件 值得警惕的形态
GetCallerIdentity 来自非预期 IP / 新区域 / 首次出现的 UA，常是凭据泄露第一步
AssumeRole 新的主体→角色组合、跨账号、非常规时间、链式连续调用
CreateAccessKey / CreateLoginProfile 任何非变更窗口的新身份凭据
Attach*Policy / PutRolePolicy / UpdateAssumeRolePolicy 策略文本出现 * 或新 Principal
GetSecretValue / kms:Decrypt 调用量突增、来自新角色
GetObject / ListBucket 同一身份短时大量枚举、跨桶扫描
PutBucketPolicy 出现非本组织账号主体
StopLogging / DeleteTrail / 改告警规则 最高优先级，几乎无需上下文即可判定异常
RunInstances / CreateFunction 挂了与创建者不匹配的高权角色

两个实践建议：一是把审计日志投到独立账号并开启日志文件校验，别让被攻陷的账号自己保管自己的账本；二是给「策略变更」和「审计关闭」单独做实时告警，这两类事件的信噪比远高于流量类告警。

九、防御分层：按「能不能挡住整条链」排序

层级 措施 挡住的是哪一环
P0 设计 面向公网的应用不挂高权角色；角色按应用实际 API 逐一收敛 整条链的起点与放大倍数
P0 网络 强制 IMDSv2（HttpTokens=required）+ HopLimit=1；容器侧用网络策略限制链路本地地址 绝大多数简单 SSRF
P0 身份 全面改用 OIDC 联邦/短期凭据，清理长期 AK；联邦信任条件精确到仓库与分支 长期密钥与混淆代理人
P1 应用 出网白名单、禁用任意 URL 抓取、DNS 重绑定防护、转发时不透传原始头 SSRF 与代理型绕过
P1 权限 权限边界（Permissions Boundary）、组织级 SCP、禁止 iam:PassRole 通配 提权与角色传递
P1 数据 公共访问阻断、桶策略巡检、KMS 密钥策略与数据权限同审 数据外泄面
P2 检测 审计日志跨账号留存、策略变更实时告警、身份可达图定期扫描 缩短发现时间
P2 响应 预案里预置「吊销角色会话 / 禁用凭据 / 回滚信任策略」的操作清单 缩短止血时间

有个反直觉但很关键的排序：「把角色权限改小」比「把 SSRF 修干净」更能兜底。前者一次配置就能把最坏结果从「整个账号」压到「一个桶的几个前缀」；后者需要在每一处出网、每一个依赖、每一次转发上都做对，长期看总会漏。这不是说不用修 SSRF，而是别把全部赌注押在永不犯错上。

十、把整条链走一遍

时间 攻击者动作 防守方视角
T0 在「图片 URL 预览」处填入元数据端点 一次普通的 HTTP 200
T+1min 拿到角色名，读取临时凭据 一次本机元数据访问，通常不进云审计
T+2min GetCallerIdentity 确认身份与账号 一条无害的只读 API
T+5min ListBucket 枚举桶、GetSecretValue 尝试取密钥 合法签名调用，与业务流量混在一起
T+12min 发现角色可 iam:PassRole，创建函数挂高权角色 一次资源创建，无进程、无登录
T+20min 用高权角色建立跨账号信任 / 新 AK 策略文本变更，未产生告警
T+30min 经桶策略或预签名 URL 建立长期读取通道 数据没「搬走」，只是被允许读
之后 定时触发维持，凭据自动刷新 若不查策略变更与异常 AssumeRole，可长期无感

整条链上，没有任何一步需要漏洞利用程序。这也是云安全和传统主机安全最大的分野：防守对象从「代码有没有 bug」变成了「身份能不能到达不该到的地方」。

十一、结论

一句话：云上最贵的不是那台被 SSRF 的服务器，而是挂在它身上的那个角色。

  • 把「网络隔离」当边界，会漏掉身份这一整层；
  • IMDSv2 是抬高门槛，不是消灭 SSRF；
  • 临时凭据的「合法签名」让它天然免疫大部分异常检测；
  • 提权来自权限组合，逐条审策略没用，要看可达图；
  • 持久化发生在配置里，排查顺序应该是「身份 → 策略 → 日志 → 主机」。

真要只做一件事，就从把所有面向公网实例的角色的权限清单打出来开始。那份清单通常会比任何漏洞扫描报告都更让人清醒。
