网址输对了，服务器却换了人：DNS、BGP、CA 三条信任链各自能守什么、守不住什么

2026-11-10 #DNS#BGP#PKI#证书透明度#RPKI#DNSSEC#子域接管#CAA

地址栏里那把绿锁，证明的只是「你和某个持有该域名私钥的对端之间，这条 TLS 会话没有被改动」。它不证明那个对端就是你想找的人。域名怎么变成 IP、包怎么走到那个 IP、公钥怎么被绑到那个名字，是三条彼此独立、各自持有信任根的链——任何一条被换掉，绿锁都可以照样亮着。

很多文章讲「网址输对了却被换了人」，讲的是伪造页面、相似域名、话术诱导、会话凭据被拿走。那属于内容层与身份层的欺骗：链本身没坏，是链末端那个「人」在演戏。本文不讨论这些，也不讨论子域侦察工具、加密代理协议或主机登录加固——前者是找名字的手段，中间是传输封装，后者是链末端主机的准入，都不在这条链的三个环节上。

本文只讨论一件事：「域名 → IP → 路径 → 公钥」这条解析与验证链本身被改写。DNS 给出的地址不是原来那个地址，BGP 把包送到不是原来那条路，CA 把公钥绑给不是原来那个申请者。页面可以一模一样，证书可以完全有效，用户每一步操作都「合规」。

三条链之间没有共享的信任根，也没有任何一个主体同时看全三条。所以单点加固不会自动传导：DNSSEC 签得再完整，也管不到 BGP 把流量绕走；ROV 开得再严，也管不到 CA 签出一张新证书。这是全文的起点，也是所有反直觉结论的来源。

一、三条链各自负责什么、不负责什么

先把职责摆正。三条链的输出是串起来的，但它们的输入、信任根和「合规」的定义完全不是一回事。

链 输入 → 输出 信任根 负责什么 不负责什么 被改写时的表现
DNS 名字 → 地址（A/AAAA/CNAME 等） 根区、各级委派、注册商账号与区域文件 把名字映射成记录，并按 TTL 缓存 那个地址上跑的是谁、包怎么走、公钥是谁 解析结果漂移，或答案「正确」但指向的资产已易主
BGP 前缀 → AS 路径与下一跳 AS 之间的双边关系与本地路由策略 宣告可达性、在候选路由里选一条 宣告者是否有权、AS 路径是否被策略允许、内容 AS_PATH 变化、RTT 跳变、局部地域不可达
CA / PKI 名字 + 公钥 → 证书 客户端内置的根证书信任列表 证明「某公钥在验证时刻与某名字绑定」 名字解析到哪、包走哪条路、站点内容是否可信 CT 日志出现未申请的证书，或私钥易主后旧证书仍有效

这张表里最容易被读错的是最后一行。CA 签的不是「这个网站是合法的」，签的是「申请者在验证那一刻，能控制这个名字的某个可观测面」。「控制」不等于「所有」，「那一刻」不等于「证书有效期内」。DV 证书把这两点压缩成一次自动化的探测，安全性全押在这次探测没被误导上。

再看绿锁。它是一份关于加密通道的声明，不是一份关于对端身份的声明。

绿锁证明了 绿锁没证明
TLS 握手完成，通道内容不被第三方读取或改动 DNS 答案没有被改过
对端持有与证书公钥匹配的私钥 数据包走的是预期那条 AS 路径
证书链可回溯到客户端信任的根 证书是域名所有者本人申请的
证书在有效期内，且 SAN 与地址栏名字匹配 名字对应的是你以为那个组织
证书带有可被校验的 SCT（在要求 SCT 的策略下） 站点内容不是仿冒、脚本不是被注入的
协商出的加密套件没被降级 私钥没有同时握在别人手里

一个判断口径：**加密保护的是「比特不被读改」，不保护「比特交给了谁」。**TLS 建立在 TCP 之上，TCP 只关心「这个 IP 可达」，它的协议里根本没有「路径」这个字段。你连的仍是那个 IP，只是那个 IP 的流量被绕去别处了——握手照样成功，绿锁照样亮。

二、DNS 层：名字到地址这一段的每一跳

一次完整解析是「根提示 → 顶级域 → 权威」逐级委派，中间由递归解析器代跑并缓存。委派关系本身是分布式状态：父区只告诉你「去问这几台 NS」，并不保证那几台 NS 现在还归原主。

解析链环节 谁控制 可被改写的点 现有约束 残留问题
本机 stub / hosts 终端 hosts 文件、本地 DNS 覆盖、恶意网络下发 操作系统权限 终端被控时整链从这里就断了
递归解析器 ISP / 公共 DNS / 企业 缓存内容、转发目标、是否做验证 源端口随机化、0x20 大小写熵、缓存 bailiwick 规则 解析器自身被改或被动持时，下游全信
根与顶级域 根区 / 注册局 委派 NS、DS、胶水记录 根区签名、注册局流程 合法变更流程被接管后，「新数据」同样合规
权威 NS 域名所有者 / 托管商 区域文件内容、NS 记录 区域签名（若启用 DNSSEC） 区域文件本身被改，签名照样有效
胶水记录 父区 NS 对应的 A/AAAA 与子区 NS 记录一致性 改父区比改子区更隐蔽，且常被忽略
区域记录 区域文件 A / AAAA / CNAME / TXT / CAA 变更审计、TTL 悬空 CNAME 不产生任何「异常记录」

缓存投毒的经典条件

缓存投毒不是「发一个假包就行」，它需要几个条件同时成立。描述条件是为了说明防护为什么这样设计，不是流程。

条件 为什么是条件 对应的缓解
抢在权威应答之前返回 缓存只接受「第一个匹配查询的应答」 降低窗口、限制并发未决查询
猜中事务 ID 与源端口 二者共同构成应答匹配的熵 源端口随机化、事务 ID 随机化
伪造记录落在 bailiwick 内 解析器不接受越权的附加记录 in-bailiwick / credibility 规则
缓存未命中或已过期 命中期内注入不生效 合理 TTL、限制重复查询窗口
应答里的附加记录被一并缓存 一次投毒可连带改 NS 与 A 附加记录校验、DNSSEC 签名
无数据来源认证 解析器无法区分应答真假 DNSSEC 的 RRSIG 链

注意最后一行：**前五条都是「抬高门槛」，只有 DNSSEC 改变了「能不能」的性质。**源端口随机化把猜测空间变大，没让伪造变得不可能；DNSSEC 让无签名的伪造应答直接验证失败。

注册商与账号接管

接管路径 依赖的前提 防守要点
注册商控制台账号被登 弱口令、无 MFA、凭据复用 独立强 MFA、专用邮箱、登录告警
联系人邮箱被控后重置 WHOIS/RDAP 邮箱与注册商账号同域 联系人邮箱放到独立受控域
API / EPP 凭据泄露 长期密钥、无 IP 白名单 最小权限令牌、来源限制、定期轮换
域名转移（转出到别的注册商） 未上转移锁 clientTransferProhibited 等 EPP 锁
改 NS / 改区域 / 改 DS 未上更新锁 clientUpdateProhibited、变更二次确认
社工注册商支持流程 人工审核可被绕过 账户级 PIN、变更通知到多渠道

这里有个常被漏掉的顺序问题：**注册商层面的「合法变更」对 DNSSEC 不构成障碍。**攻击者按流程改 NS、改区域、同步 DS，签名链依然完整有效。密码学验的是「数据与签名一致」，不是「这次变更经过所有者同意」。

NS 与胶水记录

胶水记录（glue）放在父区，用来回答「NS 名字本身就是被委派域的子域」这个循环依赖。正因为它在父区，改父区胶水往往比改子区 NS 更隐蔽：子区自己看自己的区域文件毫无异常。

改写位置 谁看得见 检查方式
子区 NS 记录 查询该域 NS 即可见 与预期 NS 清单逐条比对
父区胶水 A/AAAA 只在 +trace 的父区应答里出现 从根侧走一遍委派链核对
父区 DS 记录 影响 DNSSEC 信任链 核对 DS 摘要与自有 KSK
注册局层面的委派 通常不可见，只能通过 RDAP / 注册商确认 变更通知与定期 RDAP 快照

TTL 的两难

**TTL 不是安全参数，是「一个错误答案能活多久」的参数。**这句话决定了取舍方向。

维度 长 TTL 短 TTL
错误答案存活时间 久，一次投毒或误配影响很长 短，收敛快
故障切换 / 迁移 慢，得等各地缓存过期 快，切换窗口小
递归器查询量 低 高，权威压力大
缓存未命中窗口 少，投毒机会少 多，注入窗口更频繁
权威被路径劫持时的暴露面 已有缓存仍可服务 更快被打到权威或假权威
负缓存（SOA minimum） NXDOMAIN 影响久 恢复快，但抖动放大
适合 稳定、极少变更的基础记录 需要快速切换、已具备监控与容量的记录

反直觉的一点：**把 TTL 盲目调短不等于更安全，它同时缩短了攻击者的持久性，也放大了你自己的重查询面与投毒窗口。**合理做法是「稳定记录长、可切换记录短、变更前主动降 TTL」，而不是全局一刀切。

子域接管：DNS 答案完全正确

这是本章最值得单独讲的一类。悬空 CNAME 指向一个已经释放、且名字可被他人重新注册的云资源——对象存储桶、PaaS 应用名、CDN 自定义域、托管页。DNS 记录没被改、没被投毒、区域文件完全合法，只是链末端那个资产的归属变了。

悬空记录类型 常见来源 判定口径 防守动作
CNAME 到对象存储桶 静态站点桶被删 解析成功，但 HTTPS 返回「桶不存在/可注册」 先删 DNS 记录，再释放资源
CNAME 到 PaaS 应用名 应用下线、项目删除 平台回显「该名称可用」 下线清单里包含 DNS 清理项
别名到 CDN 自定义域 加速域名解绑 回源失败且域名可被别账号添加 校验自定义域归属绑定
指向托管页/文档平台 空间取消、订阅到期 页面变成平台默认占位 定期对每个 CNAME 发一次请求
NS 指向已停服的 DNS 托管 子域委派出去后服务停用 子域 NS 无响应或可被人接管 收回委派或改回自有 NS
MX / TXT 指向过期服务 邮件/验证服务退订 记录存在但服务不再响应 纳入资产台账，不只是 A 记录

**关键结论：DNSSEC 对子域接管零作用，因为记录本身就是「合法且签过名的」。**同样，CT 日志也帮不上忙——很多平台会在占用该名字后自动为这个子域签发一张完全合规的证书。这里失守的不是解析链，是「解析链末端资产的所有权」没有被任何一层验证。

区域记录与只读核查示意

下面是一段区域文件片段与几条只读查询示意。全部使用文档保留域名与保留地址段，不指向任何真实系统。

最后一条不是凑数：对每个 CNAME 目标做一次解析加一次 HTTPS 请求，是发现悬空记录最便宜的办法。判断标准不是「能不能解析」，而是「这个目标现在是否落在一个别人可以重新注册的命名空间里」。

三、DNSSEC 能修什么、修不了什么

DNSSEC 的思路不复杂：区域用 ZSK 给每个 RRset 签 RRSIG，用 KSK 签 DNSKEY，父区放 DS 摘要把信任从根区 KSK 这个信任锚一级级传下来；NSEC / NSEC3 让「这条记录不存在」这件事也能被认证。于是递归解析器可以判断：数据有没有被改、是不是来自持钥的权威。

但它修的边界非常明确。

DNSSEC 能修 DNSSEC 修不了
权威应答在传输途中被改 注册商/账号被接管后按流程改出的「新数据」
无签名的缓存投毒伪造应答 递归解析器到终端的最后一公里
区域数据被第三方篡改 子域接管（记录合法且已签名）
「记录不存在」被伪造 权威服务器不可达（可用性问题）
数据来源可认证到持钥者 「这个名字该由谁控制」这类授权问题
缓存里被塞入越权的假 NS 终端 hosts、企业 DNS 代理、恶意网络覆盖

**验证发生在递归侧，不在终端。**绝大多数 stub resolver 只是把问题丢给递归器并接受答案，自己不验签名。这意味着从递归器到你机器这一段仍是明文可覆盖的：同一 Wi-Fi 下的伪造应答、被改过的本地 DNS 配置、企业代理的重写，都不在 DNSSEC 的保护范围里。

机制 解决的是 不解决的是 与 DNSSEC 的关系
DNSSEC 数据完整性与来源认证 传输机密性、终端到递归器这段 基础
DoT / DoH 终端到解析器的传输加密与解析器绑定 数据本身是否被签名 互补，不替代
本地验证解析器 把验证点拉回终端 上游数据本身错误 补齐最后一公里
多地域探测 发现「答案不一致」 判定哪个答案是真的 观测层，非验证层

所以「上了 DoH 就等于有 DNSSEC」和「上了 DNSSEC 就等于终端安全」都是误读。前者加密管道，后者签名数据，两件事。

部署与运维成本：失败模式是硬失败

DNSSEC 最劝退的不是部署，是它验证失败返回 SERVFAIL，而不是降级到不安全。签名过期、时钟偏移、DS 没同步、密钥轮转没走完，表现都是「整个域解析不了」。

运维动作 出错后的后果 降低风险的做法
KSK 轮转 父区 DS 未更新 → 信任链断，全区验证失败 双签 + 预发布 + 等足 TTL 再切
DS 同步到注册局 摘要与实际 KSK 不符 → 硬失败 把 DS 更新写进变更 Checklist 并双人复核
ZSK 轮转 签名覆盖不全 → 部分 RRset 验证失败 预发布新密钥、检查 RRSIG 有效期重叠
RRSIG 有效期 签名过期、或验证端时钟偏移 受保护的 NTP、签名有效期留冗余
NSEC / NSEC3 选择 NSEC 可被区枚举；NSEC3 加盐迭代参数影响成本 按zone 是否介意枚举选择，参数不过度
负缓存与 TTL 变更后长时间 SERVFAIL 变更前提前降 TTL
CDN / 动态 DNS / 多签服务商 多方写区域导致签名不一致 明确唯一签名方与同步接口
解析器侧未开验证 签了也白签 把「验证开启率」当作部署验收项

一个判断口径：**DNSSEC 把「数据有没有被改」变成可验证，但没把「这次变更是不是所有者本意」变成可验证。**把它当银弹，通常会在第一次 KSK 轮转时以另一种方式付出代价。

四、BGP 层：地址之后，包走哪条路

BGP 里没有「所有权」字段，只有「谁宣告了哪段前缀」和「谁愿意信」。AS 之间靠双边关系与本地策略选路，常见决策次序里 LOCAL_PREF 在 AS 内部优先于 AS_PATH 长度，之后才看 ORIGIN、MED、eBGP 优先等（各实现细节有差异）。这套机制的默认前提是「对端宣告的是真的」，而不是「对端有权宣告」。

三种常被混为一谈的情况，成因、影响面和处置完全不同。

类型 宣告内容 生效机制 典型影响面 ROV 判定
同等前缀劫持 另一个 AS 宣告与你完全相同的源前缀 各网络在本地按偏好与路径长度二选一 常呈地域性，偏好劫持者的网络受影响 通常 Invalid
更具体前缀劫持 宣告你前缀里更长掩码的子前缀 转发层面按最长前缀匹配，优先于同一前缀的选路策略 往往近乎全局，本地偏好很难抵消 取决于 ROA 的 maxLength
路由泄漏 把从一侧学到的路由违规再宣告给另一侧 该 AS 变成意外中转，流量被吸引绕行 与泄漏方向、客户锥大小相关 通常仍 Valid
路径伪造 缩短或改写 AS_PATH 让路径显得更优 影响依赖路径长度的选路 局部到较大范围 ROV 不检查路径

第二行是本章最该记住的：**更具体前缀不与你的路由「竞争」，它在转发表里就是另一条更精确的条目。**你针对原前缀做的选路优化、本地偏好、甚至部分过滤，对它都不起作用。而 maxLength 设得过宽时，这类子前缀在 ROV 眼里甚至可能是 Valid。

本地偏好如何放大影响

选路因素 作用范围 被策略覆盖的程度 放大效应
LOCAL_PREF 单个 AS 内部 管理员完全可控，优先级最高 一个高偏好 peer 的错误路由会在该 AS 全体生效
AS_PATH 长度 跨 AS 比较 常被 LOCAL_PREF 压过 路径短不保证被选中
客户路由优先 常见于运营商策略 客户路由常优于 peer / provider 下游客户的错误宣告可被上游优先传播
客户锥传播 上游 → 全部下游客户 下游多默认信任上游 一个网络的判断失误沿客户锥放大
路由过滤 / peerlock 边界入向 依赖人工维护且常不全 没过滤就等于接受

为什么「加密」挡不住路径被改

层 能看到什么 看不到什么
IP 源/目的地址、TTL 包实际经过了哪些 AS
TCP 对端 IP 与端口是否可达 路径、对端是不是「原主」
TLS 握手对端是否持有匹配私钥 包走了哪条路、DNS 答案对不对
BGP 前缀与 AS_PATH 宣告 内容、证书、业务身份

结论很干脆：**路径被改时，TLS 通常完全无感。**如果劫持只是把流量绕去别处再送回真服务器，握手、证书、内容全部正常，唯一的痕迹是 RTT 变大；如果劫持者要冒充，它还得再跨过 CA 那一关——这正是第七节组合视角要处理的情况。

给一个实用的区分口径：**RTT 跳变而证书指纹不变，优先按绕路查；RTT 变化且证书指纹也变了，按冒充查。**这两件事的处置等级差一个数量级。

五、RPKI / ROV：谁有权宣告，而不是路径该长什么样

RPKI 用资源证书把「地址前缀 → 授权 AS」的绑定做成可验证对象：前缀持有者签发 ROA，写明 origin AS、前缀和 maxLength；网络侧做 Route Origin Validation（ROV），把每条路由标成 Valid / Invalid / NotFound。

它解决的是**「谁有权宣告这个前缀作为源」**这一件事，而且只解决这一件。

ROV 结果 含义 常见处置 后果
Valid 有 ROA 且 origin AS 匹配 正常接受 仍需依赖其他机制查路径
Invalid 有 ROA 但 origin AS 不匹配 丢弃或降偏好 能挡同等前缀的伪造源
NotFound 该前缀没有对应 ROA 通常放行 未签 ROA 的前缀毫无保护
ROA 配置项 写松了的后果 更稳的写法
prefix 范围过大 把未实际使用的地址段也授权出去 与实际宣告粒度逐条对齐
origin AS 填了非自有 AS 等于替别人背书 只填自己实际作为源的 AS
maxLength 过宽 未授权的更具体子前缀被判 Valid 收紧到实际需要的最长掩码
ROA 过期未续 自有路由突然变 Invalid 被丢弃 纳入证书生命周期管理
多宿主 / 代宣告未覆盖 合法备用路径被自己判 Invalid 变更前先核对全部 origin

至于「部署率与部分验证」的现实，只用定性描述就够了，不必引用任何数字：ROA 签署覆盖在不同地区、不同地址族之间参差；很多网络只对 Invalid 做丢弃、对 NotFound 放行；一台边界路由器没开验证，就等于这个 AS 没验证；上游验证了也不会自动让下游受益；某个网络丢弃 Invalid，只保护它自己和客户的出向选路，挡不住别人继续接受那条路由。所谓「部分验证」的关键不是覆盖率，而是验证是逐网络、逐方向的局部行为，没有全局仲裁者。

ROV 之外的机制也各有边界：BGPsec 一类对 AS_PATH 做签名，能治路径伪造，但要求路径上逐跳部署，且不处理「策略上不该这么走」的泄漏；基于 AS 关系的泄漏检测（OTC、ASPA 一类）针对的才是泄漏，同样依赖部署。把这些和 ROV 混成一句「RPKI 解决了 BGP 安全」，是最常见的过度概括。

攻击类型 × 缓解手段 × 残余风险

这张表的用法不是「挑一行打勾」，而是看同一列里有没有跨链的空白：只填 DNS 那一列，CA 与 BGP 两列的残余风险原封不动。

六、CA 层：把公钥绑到名字，绑的是「控制」

CA 的核心动作叫域名验证（DV）：在签发前的某一刻，确认申请者能控制这个名字的某个可观测面。这个定义本身就说明了弱点在哪。

验证方式 确认的是 主要弱点 适用与备注
HTTP-01 能控制该名字 80 端口的指定路径 DNS 被指向攻击者主机、或 80 端口流量被路径改道即可通过 最普遍，多视角验证能缓解但非根治
DNS-01 能改该名字下的指定 TXT 注册商/DNS 账号被接管即通过 可签通配符证书，风险随 DNS 链传导
TLS-ALPN-01 能控制 443 端口并完成特定握手 依赖 443 可达与端口未被劫持 避免占用 80，边界类似
邮箱 / WHOIS 验证 能收到发往登记邮箱的确认 邮箱被控、WHOIS 数据被改、邮件路径被截 早期方式，现已弱化
OV / EV 额外核验组织身份 浏览器 UI 差异已弱化；不增加对解析链的保护 组织身份 ≠ 本次解析正确

**DV 验证的是「控制」，不是「所有」；是「那一刻」，不是「证书有效期内」。**名字的控制权在证书有效期内易手，没有任何一层会自动重新验证。

误签发路径 被绕过的是 可见性
域名验证请求被中间人应答 HTTP-01/DNS-01 的探测结果 很低，CA 侧看是一次合规验证
注册商或 DNS 账号被接管后走合法申请 「谁在控制这个名字」的前提 只有 CT 与解析漂移能事后发现
CA 或其验证代理被入侵 签发流程本身 取决于审计与 CT
验证逻辑实现缺陷 校验步骤 通常事后复盘才清楚
相似字符域 / 大小写与通配变体 人工核对 取决于监控是否覆盖这些变体

证书透明度：事后可见，不是事前阻止

CT 要求 CA 把每张证书提交到只追加、可审计的公开日志，拿回 SCT 随证书下发；要求 SCT 的客户端不会信任「没登记」的证书。这套机制真正的贡献是把「悄悄签发」变成「必须留痕」。

CT 提供的 CT 不提供的
所有合规签发的证书都可被公开检索 签发前的拦截能力
未登记证书在要求 SCT 的客户端下不可用 已签发并登记的误签发证书会失效
append-only 与一致性证明，日志难以悄悄删改 自动吊销
域名所有者可订阅并发现「没申请过的证书」 覆盖你没列入监控的域名变体
事后归因与审计证据 阻止私钥被滥用

一句判断口径：**CT 把误签发从「不可见」变成「可发现」，没有变成「不可能」。**监控有效的前提有两个，且都常被忽略：一是真的在盯，二是监控名单里包含通配、子域与相似字符变体。只监控主域，等于把最容易出事的那部分留白。

CAA、HSTS 与退场的密钥固定

机制 作用边界（能） 不能
CAA issue / issuewild 指定允许哪些 CA 为该域签发 限制「能不能签」，只能限制「谁来签」
CAA iodef 让 CA 把违规尝试上报到指定地址 上报本身不产生拦截
CAA 沿 DNS 树向上查找 子域无记录时继承父域策略 父域策略被绕过时的例外（issuewild 等）
HSTS 强制 HTTPS，阻止明文降级与首次之后的降级 防 DNS 改写、路径劫持、误签发的合法 HTTPS
HSTS 预加载 关掉「首次访问」那个空窗 关掉之后移除很慢，需按长期承诺对待
HPKP（已废弃） 把特定公钥钉死，理论上能挡误签发 钉错/轮转即把自己锁死，且没有刹车

CAA 有个绕不开的循环：**它自己是一条 DNS 记录。**攻击者若能先改 DNS，就能先删 CAA 再申请证书；或者从「被允许的那家 CA」的验证环节下手。CAA 限制的是「哪家 CA」，不是「这次签发该不该发生」。

HSTS 与预加载挡的是「降级到明文」这一类，不是「对端是谁」。一个带着有效证书、被 HSTS 覆盖的仿冒端点，浏览器照样认为一切正常。

HPKP 的退场值得多说一句，因为它是个典型的反直觉案例：**它不是效果不好，是效果太强且没有刹车。**把公钥钉死确实能挡误签发，但一旦钉错、密钥轮转或证书更换，站点会在固定期内对自己不可用，且没有可靠恢复路径；这种「自伤式」失败模式让收益风险比变得无法接受，浏览器陆续移除支持，取而代之的是「CT 监控 + SCT 要求 + 短期证书 + CAA」这套更温和的组合。安全机制能不能活下来，有时不取决于它挡住了什么，而取决于它失效时能不能收场。

证书侧只读核查示意

核查的重点不是「证书有效」——有效是默认状态——而是**「指纹和签发者是不是我计划内的那一个」**。非计划内的更换，即使链完全可信，也应当按事件处理。

七、组合视角：单链失守与多链同时被绕过

单看一条链被攻破，其实大部分情形会被另一层挡住或暴露；真正难缠的是多条链被同时绕过，让每一层按自己的规则都「合规」。

场景 被改的链 用户/客户端看到 单点防护能否发现
只改 DNS，指向无证书的对端 DNS 证书域名不匹配或握手失败，告警 能，TLS 会报错
只改路径，绕路后仍回真服务器 BGP 一切正常，仅 RTT 变大 几乎不能，只能靠 RTT/路径基线
只误签发证书，解析与路径未动 CA 绿锁正常，无感 只有 CT 监控能发现
DNS + CA：改指向并为该域拿证书 DNS + CA 绿锁亮、内容受控 需要解析漂移 × CT 同时看
注册商改 NS/DS + 重新签名 DNS 签名链仍有效，绿锁可亮 DNSSEC 验不出「授权」问题
BGP 更具体前缀 + 误签发 BGP + CA 中间人可解密，绿锁亮 ROV 与 CT 各自只看到一半
DNS + BGP + CA 三层同时 全部 与正常访问几乎无法区分 只有跨层对照与多地域一致性

「每一层都合规」仍可能整体失守，原因不在于某一层没做好，而在于这四条结构性事实：

事实 后果
三个信任根互不共享（根区/注册商、AS 间策略、根证书库） 没有任何一层能验证另一层的结论
每层的「合规」按自己的规则定义 签名一致 ≠ 变更获授权；源 AS 在 ROA 里 ≠ 路径合理；DV 通过 ≠ 是合法运营者
验证是局部且按视角的（递归器、某个 AS、某家 CA、某个浏览器） 没有主体同时看全三条链，也没有全局仲裁者
时间维度错配（TTL、证书有效期、路由随时可变） 三者的「一致」只在某一瞬间成立，之后各自漂移

一个反直觉但更准确的结论：**整体安全不是三层之和，而是「有没有人做跨层对照」的函数。**DNSSEC、ROV、CT 分别把各自那一段从「不可验证」提升到「可验证/可发现」，但把三段结果放在一起比对的那件事，协议栈里没人负责，只能由防守方自己补。

跨层对照不是一句「加强监控」，它得落成可采集、可比对的具体量。下面这张表按「信号 → 可能原因 → 也可能是误报 → 核查动作」组织。

两条判断口径：单点异常多半是变更，多地域不一致才更像劫持；「解析漂移 + CT 新证书 + 指纹变化」同时出现，按入侵处理，不要按变更处理。反过来说，只盯证书有效性的监控，会漏掉整条链里最安静的那类失守——绕路。

九、分角色防守清单

优先级按「能不能压缩最坏结果」排，不按「实施难易」排。P0 的验收标准不是「配置写过了」，而是「模拟一次非授权变更，告警有没有响」。

角色 优先级 动作 判断口径（怎么算做到）
域名所有者 P0 注册商账号独立强 MFA、开启 EPP 转移/更新/删除锁 尝试一次改 NS，是否触发二次确认与多渠道通知
域名所有者 P0 联系人邮箱放到独立受控域，与业务域分离 业务域失陷时，注册商邮箱是否仍独立可控
域名所有者 P0 清理悬空 CNAME/别名；先删 DNS 再释放资源 逐个 CNAME 请求，目标是否落在可被人重注册的命名空间
域名所有者 P0 为全部自有名字签 CAA，指定 CA 与 iodef 用非指定 CA 试签是否被拒、是否收到上报
域名所有者 P1 建立含子域、通配、相似字符变体的域名清单 清单能否覆盖 CT 里出现过的所有名字
域名所有者 P1 部署 DNSSEC，把 DS 同步与 KSK 轮转纳入变更单 演练一次轮转，全区是否仍可验证解析
域名所有者 P1 关键记录变更前主动降 TTL，同步核对 negative TTL 切换窗口是否短于业务可忍受时长
域名所有者 P2 定期核对 NS、胶水、DS、RDAP 快照并留痕 能否回答「上一次委派变更是谁、何时」
服务提供方 P0 资源释放后设置名字不可被立即重占的冷却/归属校验 删资源后立刻用别账号注册同名，是否成功
服务提供方 P0 自动证书签发前做多地域、多视角的域名控制验证 单地域被改时，验证是否仍会失败
服务提供方 P0 CA 侧强制 CAA 检查、CT 提交、SCT 随证书下发 抽查证书是否带可校验 SCT、CAA 是否被查询
服务提供方 P1 为自有前缀签 ROA，maxLength 收紧到实际宣告粒度 用更长子前缀模拟宣告，ROV 是否判 Invalid
服务提供方 P1 对 peer / 客户路由做入向过滤与泄漏检测 违规再宣告的路由是否被拦在边界
服务提供方 P1 向租户输出解析、证书、路由变更事件 租户能否在不提工单的情况下收到变更
服务提供方 P2 提供可消费的审计事件与历史查询 事后归因能否拿到跨层时间线
运维与监控 P0 CT 监控覆盖自有域全部变体，未申请证书实时告警 用一张测试证书触发，告警时延是多少
运维与监控 P0 多地域一致性基线：解析 / 指纹 / AS_PATH / RTT 某一地域被改，是否在同一屏里显出差异
运维与监控 P0 证书指纹与签发者变更纳入变更管理 非计划内续期是否会自动开事件
运维与监控 P1 DNS 答案与 TTL 漂移检测、NS/胶水一致性巡检 与区域文件逐条比对，差异是否可解释
运维与监控 P1 递归解析器开启 DNSSEC 验证，并监控 SERVFAIL 突增 签名出错时是否被当成普通故障掩盖
运维与监控 P1 边界丢弃 Invalid 路由，记录 NotFound 前缀清单 未签 ROA 的自有前缀是否进了清单
运维与监控 P2 保留多视角历史数据；把受保护 NTP 列为依赖项 能否复盘三个月前某次解析漂移
终端用户 P0 不忽略证书告警、不手动导入来路不明的根证书 浏览器信任根列表里有没有陌生项
终端用户 P1 使用带验证/加密 DNS 的解析器，并理解它只覆盖最后一公里 是否误以为「加密 DNS = 全链安全」
终端用户 P1 高敏操作用书签直达，不从消息链接进入 入口是否绕过了「名字」这一环节
终端用户 P2 关注 HSTS 预加载状态，定期检查信任根列表 列表变更是否有感知渠道

有个排序上的反直觉结论值得单独说：**「把 CT 监控和多地域一致性基线跑起来」比「再多叠一层单点加固」更能兜底。**前者是唯一能同时看见 DNS 与 CA 两层、并把 BGP 的痕迹（RTT、AS_PATH）放在同一屏里的视角；后者无论叠多少层，都只在自己那一层里正确。

十、常见误解表

# 误解 为什么不对 更准确的说法
1 用了 HTTPS 就不会被劫持 加密不认证路径，也不认证名字归属 HTTPS 保护通道内容，不保护「你连的是谁」
2 绿锁说明网站是真的 绿锁只要求证书域名匹配且链可信 仿冒端点同样可以有绿锁
3 DNSSEC 全覆盖就安全了 它验数据完整性，不验变更授权，也不覆盖最后一公里与子域接管 它是「数据没被改」的证明，不是「变更被批准」的证明
4 证书透明度能阻止误签发 证书已签出、已可用，CT 只让它留痕 CT 把误签发从「不可见」变成「可发现」
5 配了 CAA 就没人能给我签证书 只限制「哪家 CA」，且 CAA 本身是 DNS 记录 限制签发者，不限制「该不该签」
6 RPKI / ROV 上了 BGP 就安全 只验源授权，不验路径，也不处理泄漏 ROV 回答「谁有权宣告」，不回答「路径合理吗」
7 路由泄漏就是前缀劫持 源 AS 常合法，ROV 判 Valid，成因与处置都不同 泄漏是「关系/策略违规」，不是「伪造源」
8 更具体前缀和同等前缀差不多 最长前缀匹配让前者近乎全局生效，本地偏好难救 二者影响面差一个量级
9 HSTS 预加载能防中间人 防的是降级到明文 防不了 DNS 改写、路径劫持、误签发的合法 HTTPS
10 把公钥钉死是最强防护 钉错或轮转即自锁，且无恢复路径 HPKP 因失败模式不可收场而退场
11 TTL 设短一定更稳 放大查询量与投毒窗口，权威压力上升 短 TTL 只让错误答案死得快
12 子域接管是 DNS 被黑了 DNS 答案往往完全正确，是末端资产归属变了 这是资产所有权问题，不是解析完整性问题
13 每一层都合规 = 整体安全 三个信任根互不校验，没主体看全三条链 安全取决于有没有人做跨层对照
14 证书有效期内就不用担心 DV 是一次性验证，名字控制权可在有效期内易手 有效期是加密参数，不是持续授权
15 加密 DNS（DoH/DoT）等于 DNSSEC 一个加密管道，一个签名数据 二者互补，不能互相替代

十一、把一次「每层都合规」的失守走一遍

下面这条时间线里，没有任何一步需要绕过某个密码学原语。每一步在该层自己的日志里都叫合规操作。

时刻 发生什么 该层日志怎么看 谁本可以发现
T0 注册商账号被接管，NS 与胶水记录被改 一次带有效凭据的 EPP 变更 变更通知与 RDAP 快照
T+TTL 窗口 部分递归器仍返回旧答案，地域间开始不一致 正常缓存过期与刷新 多地域解析一致性基线
T+数分钟 新权威上按流程同步 DS，签名链重新完整 DNSSEC 验证全部通过 没有人——这正是问题
T+数分钟 攻击者在自己控制的 IP 上完成 HTTP-01 / DNS-01 CA 侧：一次合规 DV 验证 多视角验证若覆盖被改地域才有机会
T+数分钟 证书签发、提交 CT、SCT 齐全下发 CT 里多一张完全合规的证书 CT 监控：唯一「未申请」的痕迹
T+可选 更具体前缀宣告，把到权威/CDN 的流量也吸引过来 ROV 若 maxLength 过宽或前缀未签，判 Valid/NotFound AS_PATH 与 RTT 基线
T+用户访问 绿锁亮、SAN 匹配、内容受控，仅 RTT 略变 浏览器：一切正常 只能靠跨层对照
事后 证书在有效期内持续可用，缓存逐步收敛到新答案 各层都「稳定」 若不看 CT 与解析漂移，可长期无感

T+数分钟那两行是整条链最刺眼的地方：DNSSEC 验证通过、CA 验证通过、CT 提交合规——三件本该是防护的事，在这里全都正常发生，只是「正常」的主语换成了别人。防护机制验的是规则，不是意图；规则没被破坏，被替换的是执行规则的人。

十二、结论

  • 三条链、三个信任根、没有任何一层负责端到端一致性；单点加固不会自动传导。
  • 绿锁是关于加密通道的声明，不是关于对端身份的声明；加密不保护路径，签名不保护授权，日志不阻止签发。
  • DNSSEC 把「数据有没有被改」变成可验证，但失败模式是整域硬失败；ROV 只回答「谁有权宣告」；CT 只把误签发变成可发现。三者都不是银弹，且都不看另外两层。
  • 「每一层都合规」仍可能整体失守，因为按各自规则合规，与跨层一致，是两件事。
  • 能补上这个空缺的只有跨层对照：解析漂移 × CT 新证书 × 指纹变化 × AS_PATH × RTT × 多地域一致性。
  • 反直觉但最该记住的一条：单点异常多半是变更，多地域不一致才更像劫持；三条信号同时出现，按入侵处理。

真要只做一件事，就把「自有域名的 CT 监控 + 多地域一致性基线」先跑起来。它是唯一能同时看见 DNS 与 CA 两层、并把 BGP 的痕迹放在同一屏里的视角。其余所有加固，都只是让某一层在自己那一段里更正确而已。
