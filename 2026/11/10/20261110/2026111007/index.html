翻日志不叫威胁狩猎：假设驱动、数据模型，以及「什么都没猎到」为什么也算结果

2026-11-10 #威胁狩猎#假设驱动#数据模型#进程树#基线偏离#日志治理#检测转化#蓝队

告警响了才去翻日志，那叫响应；告警没响，你却因为「这台机器上不该出现这个父进程」而主动走进全量数据，才叫狩猎。两者的工具几乎一样，起点完全不同：狩猎带着一个可以被证伪的假设进去，而不是带着「看看有什么」的期待进去。最容易被忽略的差别是，一次什么都没猎到的狩猎，只要判据写死了、覆盖率算清了，依然是一份能归档的结果；而「看看有什么」式的翻日志，翻到什么都能自圆其说，翻不到什么也说不清到底排除了什么。

先把边界划清楚。本站写勒索软件应急响应实战指南，讲的是事后流程：起点是「已经出事了」，顺着时间往回止损；写恶意样本反分析与脱壳，对象是「一个已经拿到手的样本」，做的是纵深拆解；同批次那篇云上 IAM 权限链，对象是「配置文本」，静态可审、逐行能读。这三篇都不是狩猎。狩猎的起点是没有告警——不知道有没有事，甚至没有任何一条记录告诉你该往哪看；对象是全量环境里持续发生的行为流；产出是对一个假设的判定，外加这个判定能覆盖到哪里。

所以「翻日志」和「威胁狩猎」之间隔着的不是技术门槛，是一张写死了否定条件的假设卡。这篇不谈某次真实事件、不谈某个编号漏洞，只谈这套方法怎么立起来：假设从哪来、什么假设才算数、数据模型怎么决定你能问什么、结果怎么变成资产，以及为什么「什么都没猎到」不等于白干。

一、先把边界划清：狩猎的起点是「没有告警」

「没有告警」不等于「平安无事」，它只说明一件事：现有检测规则的并集没有覆盖到这个行为，或者覆盖到了但特征没触发。规则是「已知坏」的枚举，枚举永远有补集；狩猎处理的正是那块补集里「说不上坏，但不对劲」的状态。反过来说，如果一类行为本该触发告警却没触发，那是检测工程的规则缺陷，该去修规则，不该包装成一次狩猎。

维度 告警响应 威胁狩猎
触发条件 一条告警、一张工单、一个外部通报 一个可证伪的假设，无需任何外部触发
输入 告警上下文的那几条记录 全量环境、跨数据源、跨时间窗
思维方向 「这条是不是真的、要不要处置」 「这个假设在当前环境里成立吗」
对「没查到」的解释 误报，或规则失效 需分情况：证伪、不可判定、覆盖不足，三者完全不同
时间压力 分钟到小时，受处置时效约束 天到周，受留存周期约束
与检测规则的关系 消费规则 主动寻找规则的盲区，并把结论回喂给规则
主要风险 处置过慢、误报疲劳 自欺：把「没看到」当成「没有」

这里有个很实用的判断：如果一件事能直接改写成一条稳定的检测规则，它就不该长期停留在狩猎清单里。狩猎的用武之地，恰恰是那些暂时写不成规则、需要人带着上下文去判的部分。

再拿三篇近似文做一次对照，边界会更清楚：

近似文 对象 起点 与本文的分界
勒索软件应急响应实战指南 已发生事件的处置流程 已经出事、已有告警 时间方向向后回溯止损；本文起点是「不知道有没有事」
恶意样本反分析与脱壳 一个已获得的样本文件 样本已在手里 对象是一个静态实体；本文对象是全量行为流，没有样本
云上 IAM 权限链（同批次） 策略与信任配置 配置可读、静态可审 对象是配置文本；本文对象是随时间演化的行为
本文 环境里的行为与身份 没有告警 产出是假设判定、排除范围与数据缺口清单

二、狩猎、告警响应、取证、威胁情报：四者的区别

这四件事经常被塞进同一个动作里，因为用的都是日志平台。但它们的起点、时间方向、产出物、成功率口径全不一样，混在一起最直接的后果是：用错误的标准考核正确的工作。

维度 威胁狩猎 告警响应 数字取证 威胁情报
起点 无告警，一个假设 一条告警或工单 已确认的事件或已固定的证据载体 外部输入：报告、指标、团伙画像
时间方向 面向当下与近历史，主动向前扫 面向已发生的事件，向后回溯 面向已固定的过去，重建时间线 面向外部与趋势，跨组织
核心问题 「这个假设在当前环境里成立吗」 「这条告警是不是真的、要不要处置」 「当时到底发生了什么、证据链是否完整」 「谁在打、用什么、打谁」
产出物 假设判定、排除范围、数据缺口清单 处置动作与真/误报结论 证据与可复现的时间线 可消费的指标与画像
成功率口径 被有效判定（证实或证伪）的假设占比，不是命中数 处置时效与误报率 证据完整性与可复现性 转化率：多少进了检测与狩猎
「什么都没找到」 是结果，前提是覆盖率足以支撑排除 是误报或规则失效 是取证不完整 是情报与本地环境不相关
数据范围 全量环境、跨数据源 告警上下文那几条 被固定的介质与镜像 外部为主，本地只用于验证
与检测规则 找规则盲区、把结论回喂成规则 消费规则 不消费规则 为规则提供特征输入

表里最容易被做错的是「成功率口径」。很多团队拿「这次发现了几个」考核狩猎，结果会非常稳定地导向两个坏行为：挑软柿子写一定会命中的假设，以及把「疑似」也算成「发现」。一个成熟的狩猎体系，命中率应该长期偏低——因为容易命中的那部分早就该被写成规则了。狩猎卖的是确定性，不是惊喜；把惊喜当 KPI，等于奖励大家把检测工程的欠账包装成战果。

还有个反直觉的推论：如果某次狩猎「满载而归」，更该先怀疑的是判据是不是写松了、基线是不是被污染了，而不是先庆祝。四者里只有狩猎会把「证伪」也算作成功产出，因为「确定地排除了某类行为在某个范围内存在」本身就是防御资产。

三、假设从哪来：六个可追溯的来源

假设不是灵感。它是「外部输入」与「本地可观测性」的乘积：情报报告里写「攻击者会滥用计划任务」，这只是一个事实；「在我们采集覆盖到的终端全集里，过去一个留存周期内新增的、由非管理员账户创建、且命令行引用了网络路径的计划任务，预期为零」，这才是一个能跑的假设。

来源 具体形态 转成假设的动作 天然弱点
情报与公开手法 公开报告、手法描述、工具行为摘要 把「手法」翻译成「本地可观测的字段组合 + 预期值」 报告写的是别人家的环境，字段未必采得到
ATT&CK 技术 技术项、子技术、数据源与检测建议 选一项技术，问「它的必需字段我们有没有、预期频次是多少」 只照抄技术名会停留在存在性判断，写不出否定条件
环境自身异常 上一次查询里没解释干净的残项、配置漂移 把「没解释干净」升级成带范围与判据的正式假设 容易被当成「顺手再查查」，不落假设卡就不可复现
上一次红队复盘 红队用过但当时没被检测到的路径 逐条问「哪一步本该留下日志、为什么当时没告警」 复盘常聚焦「怎么进来的」，忽略「留下了什么可观测痕迹」
业务知识 变更窗口、排班、部署拓扑、哪些机器本该互相通信 把「业务上不该发生」写成可判定的否定条件 业务知识在人脑子里，不写进假设卡就会随人员流动失效
数据源缺口反推 某字段未采集、留存过短、采样过狠 反过来问「若对手恰好用这类行为，能否从别的字段间接看出来」 产出常是数据需求而非发现，容易被当成「没成果」

最后一个来源最值得展开，因为它逆着大多数人的直觉。常规思路是「先有数据，再想能问什么」；缺口反推是「先承认有一整类行为我们永远看不见，再问能不能用别的字段把它逼出来」。比如进程创建事件没有记录祖父进程，那你至少还能用「会话 ID + 启动时间邻近」去做弱关联；如果连会话 ID 也没有，那结论就只能是「这类父子链在当前数据模型下不可判定」——这个结论本身就该进数据缺口清单，而不是被含糊地写成「未见异常」。

一个来源能不能用，检验方式很朴素：能不能填进下一章那张假设卡的四个必填格。填不进去，说明它还只是素材，不是假设。

四、什么样的假设才可证伪

一个假设必须同时回答三个问题：预期看到什么、看到什么就否定它、需要哪些字段。三者缺一，它就不是假设，是感觉。感觉的特点是无论数据长什么样都能自圆其说，因此永远不会被证伪，也永远产不出排除范围。

坏假设 为什么坏 改写后可证伪的版本
「看看有没有异常进程」 「异常」未定义，没有判据也没有否定条件 「父进程为办公套件的脚本解释器启动事件，在基线期内从未出现；若出现且可归因到已知分发流程则否定」
「查一下是不是被入侵了」 不可证伪，任何结果都能解释成「迹象不明显」 拆成若干个带范围、带字段、带否定条件的独立假设
「关注一下最近的可疑登录」 「可疑」「最近」都是滑动标准，事后可随意调整 「管理级账户在变更窗口外的认证事件，且无对应变更单或值守排班」
「验证某项 ATT&CK 技术是否出现」 只有存在性判断；没出现不等于没发生，可能只是字段没采 补上「数据覆盖足以支撑排除」的前置条件与否定条件
「外联流量里有没有 C2」 C2 无字段定义，且「没看到」极可能是 DNS 未采集 「周期稳定、单连接字节量低、目标不在已登记服务清单的连接序列」
「这个路径下的文件都不太对」 「不太对」是主观判据，第二个人无法复跑 「签名者罕见且位于用户可写路径、首次出现在本窗口、且无软件分发记录」

把「预期 / 否定 / 字段」三件套摊开，一个假设长这样：

要素 内容（以异常父进程为例）
预期看到什么 一组「父进程 → 子进程」组合在基线期从未出现，且子进程属于脚本解释器或系统管理工具集合
看到什么就否定它 该组合在基线期内稳定存在；或可归因到已登记的分发、运维、终端管理流程，且命令行与签名一致
需要哪些字段 进程 GUID、父进程 GUID、父子镜像路径、命令行、签名状态、主机标识、事件时间、会话 ID
范围与时间窗 采集覆盖到的终端全集；本窗口与一个等长的洁净基线窗口
前置覆盖条件 进程创建事件覆盖率、父子字段非空率、基线期洁净标注

假设卡落成结构化记录，才谈得上归档、复跑和度量。下面是一份刻意保持通用的字段约定，不绑定任何具体产品：

两个细节决定这张卡有没有用。一是否定条件必须先写死再跑查询，否则人一旦有了「这里有问题」的预期，任何长尾项都会被读成迹象；二是范围必须写死（哪批资产、哪个时间窗、哪版数据源），否则「没猎到」既无法复现，也无法归档成排除范围。省掉这两步，后面第八章那五种自欺就会全部找上门。

五、数据模型：没有字段，假设就是空话

假设能不能被判定，不取决于分析者的经验，取决于数据模型。下面六个面，任何一个没交代清楚，都可能让一次看似严谨的狩猎得出一个根本不成立的结论。

进程树与父子关系。 关键不是有没有 ppid，而是这个字段记录的是「启动时刻的父进程」还是「采集时刻查到的父进程」。父进程一旦退出、其标识被复用，后者会指向一个完全无关的进程，于是「异常父进程」这类假设会凭空造出一批命中。进程 GUID、会话 ID、启动与退出时间、孤儿进程标记，缺一样，父子链就只能在短窗口内成立。

身份与会话。 同一个「人」在日志里可能以域账号、本地账号、服务主体、机器账号四种身份字段出现，提权之后还会带不同的令牌上下文。不把「会话」作为一等公民建模，就没法回答「这次管理凭据使用是不是同一个人同一次登录」，只能退化成「某账号在某时刻做了某事」。

网络连接。 五元组、方向、关联进程、DNS 与连接的对应关系、连接时长与字节数、是否只记录成功建立的连接，这几项决定了「低慢速外联」能不能被判定。特别注意 NAT 之后的源地址归并：它会把多台机器的心跳叠成一个看似高频的假象，也会把单台机器的低频外联稀释掉。

时间同步。 时钟偏移会让「父子先后」「先外联后落盘」这类时序判据整体失效；跨数据源若一个用采集端时间、一个用入库时间，关联查询会产出大量假相关。每个时间字段都得标明基准与来源，关联前先做偏移核对，而不是默认它们对齐。

字段归一化。 同一语义在不同源里叫不同名字，不归一化就没法 join。归一化不是改名，是要定义类型、单位、空值语义、时区与主键；做错比不做更危险，因为 join 会「成功」，只是连的是错的实体。

留存周期与采样率。 这是最隐蔽的杀手：假设要回看一个窗口，日志只留了更短的一段，那结论不是「没命中」，是「不可判定」；网络流按比例采样，低频外联可能整段被采掉，长尾法会直接失效。

字段组 关键字段 关联用途 常见缺失后果
进程标识 进程 GUID、父进程 GUID、启动/退出时间 重建进程树、判定父子先后 父子链断裂，异常父进程类假设不可判定
进程上下文 镜像路径、命令行、签名状态、哈希 归因到分发流程、识别罕见二进制 无法区分「首次出现」与「重新打包」
身份与会话 账户标识、会话 ID、认证包、令牌类型、提权上下文 判定「是否同一次登录」、管理凭据使用 把自动化任务与真人操作混为一谈
网络连接 五元组、方向、字节数、时长、关联进程 低慢速外联、目标固定性 只能看到「有连接」，看不到周期与体量
名称解析 DNS 查询、应答、查询发起进程 把目标地址与手法关联 「未知域名外联」无法归因到已登记服务
时间基准 采集端时间、入库时间、时区、时钟来源 跨源关联、时序判据 假相关、先后关系反转
资产与归属 主机标识、资产分组、业务标签 定义假设范围、计算覆盖率 结论无法标注作用域，排除范围不可复用
采集元数据 数据源版本、覆盖率、留存、采样比例 判定空结果能否算「排除」 把「数据缺失」误读成「行为正常」

反直觉但很关键的一点：数据模型没建好之前，别急着换更聪明的分析工具。先做这张「字段 → 数据源 → 覆盖率 → 留存 → 采样」的账，很多「狩猎没结果」其实不是分析能力问题，是字段账从来没算过，空结果被当成了结论。

六、三类方法：基线偏离、聚合长尾、模式匹配

维度 基线偏离 聚合与长尾异常 已知手法模式匹配
基本思路 先定义常态，找偏离它的项 不定义常态，找分布里的稀有项与孤立点 把已知手法的特征写成查询
适用面 行为稳定、变更可控的资产与身份 高基数、天然长尾的字段 已知技术项、已公开手法
前置成本 高：要养基线、处理季节性与变更窗口 中：要能算分布、去重、排序 低：字段齐备就能写
误报主要来源 上线、发布、运维窗口、人员轮班 合法但罕见的长尾项 手法变种、特征过窄或过宽
失效条件 基线期已被污染；环境本身高频变化 全量都稀有，没有「常态」可依 手法不在已知集里；字段缺失导致匹配不上
对数据量的要求 需要一段连续历史窗口 需要全量，采样会直接毁掉长尾 命中字段即可，不强求全量
典型产出 偏离列表 + 基线修订记录 待人工判定的候选集 可直接转成规则的查询

基线偏离最贵的不是算法，是养基线的纪律：变更窗口、新机器上线、节假日、轮班，都得进模型，否则每次发布都是一次「全网异常」。更麻烦的是它有个自毁性质——基线期里若已经存在未被发现的活动，它会被学成常态，此后同类行为永远不再偏离。所以基线必须带「洁净假设」标注，并用与基线无关的判据（签名、外部归因）定期抽查基线本身。反直觉的是：环境变化越快的组织越爱用基线偏离，而它恰恰在那里最不可用。

聚合与长尾的价值在「排序」，不在「判定」。长尾里绝大多数是合法但罕见的东西——一次性的安装脚本、某台老机器上的遗留工具、 rarely 触发的维护任务。把它们当发现会迅速耗光分析预算。正确的用法是让长尾法生成候选集，再由人带着上下文逐条归因；它回答的是「先看哪几条」，不是「哪几条是坏的」。

模式匹配其实最不像狩猎：它本质是补检测覆盖，成功率最高、最可交付，也最容易被当成「狩猎做完了」。把它放在一次狩猎的收尾更合适：先用它扫掉已知的，再用长尾法生成候选，最后用基线法给候选补上下文。三者不是三选一，是同一趟流程里的三段。

七、六个可复用的狩猎假设示例

下面六个假设共用同一套结构：假设、数据、判据、否定条件、常见误判。它们不针对任何具体环境，落地时要把「集合」「窗口」「已登记清单」替换成本地真实定义。

编号 假设 数据 判据 否定条件 常见误判
H-01 异常父进程 端点进程创建事件 基线期从未出现的「父 → 子」组合，且子为解释器/管理工具 可归因到已登记分发或运维流程，签名与命令行一致 终端管理代理、进程标识复用
H-02 非工作时间管理凭据使用 认证日志、权限清单、变更日历 管理级账户在变更窗口外的会话 有变更单、值守排班或自动化任务且目标主机在范围内 时区未统一、备份服务账号、轮班制
H-03 罕见签名/路径二进制执行 进程创建、文件元数据、软件清单 签名者罕见或位于用户可写路径、首次出现在本窗口 对应软件分发、经批准的临时工具或本地构建，哈希在清单内 无签名不等于恶意、合法的用户可写部署路径
H-04 周期性低慢速外联 网络流、DNS、资产登记 间隔方差低、单连接字节量低、目标固定、跨天持续 目标在已登记服务清单且周期与心跳配置一致 遥测/证书检查/许可证心跳、采样失真、NAT 归并
H-05 持久化配置增量 配置审计、变更流水、变更单 窗口内新增或改动的持久化项逐条查归因 每条有变更单、操作者、批准记录且命令行无网络路径 软件安装批量写入、补丁改写服务、快照缺失
H-06 身份侧首次区域或设备 认证日志、设备清单、归属数据 身份的「已见集合」在窗口内出现新组合 对应出差、新设备发放、出口变更且同会话无权限跃迁 移动网络出口不稳、共享出口串台、把首次当失陷

H-01 异常父进程。 判据的关键不是「出现了没见过的组合」，而是先排除两类代理型父进程：终端管理 agent、软件分发 agent 本来就会拉起脚本。真正要处理的是进程标识复用——父进程退出后标识被新进程占用，采集时查到的「父」根本不是启动时的那个。所以查询里必须先按启动时间与退出时间做一次有效性过滤，再做 anti_join，否则候选集里会混进一批结构性假阳性。

H-02 非工作时间管理凭据使用。 「非工作时间」必须先定义成组织口径而不是钟表口径：轮班、值守、跨时区团队都会让 22 点变成正常时段。判据里要把变更日历和排班表作为否定条件的数据源接入，而不是事后靠人回忆。最隐蔽的误判是备份与批处理任务复用了同一批服务账号——它们在日志里长得和「有人半夜用了管理凭据」一模一样。

H-03 罕见签名/路径二进制执行。 「首次出现」是个脆弱概念：同一个工具重新打包一次哈希就变了，于是老工具被算成新文件。签名「无」也完全不能当恶意信号，内部构建和大量开源工具都无签名。这个假设的正确产出往往不是发现，而是「软件清单覆盖率不足」这条数据缺口。

H-04 周期性低慢速外联。 判据落在「间隔方差」而不是「绝对频次」，因为低慢速的特征是稳定，不是少。误判几乎全来自合法心跳：遥测、时间同步、证书状态检查、许可证校验都长这样。两个数据陷阱要提前处理——采样率会让本就稀疏的间隔看起来不规则从而漏掉，NAT 归并则把多台机器的心跳叠成一条看似高频的记录。否定条件因此必须绑定「已登记服务清单」，而不是「看着不像坏域名」。

H-05 计划任务与持久化配置的增量。 这是典型的「差集」假设，而差集的可靠性完全依赖「上一次快照」是否存在。快照缺失时，全部存量都会被算成新增，一次软件安装批量写入十几项配置，看上去就像批量持久化。所以第一步永远是核对快照完整性，第二步才是逐条查变更归因。

H-06 身份侧首次出现的区域或设备。 「已见集合」要按身份维护，不能用全局集合，否则共享出口会让 A 的「首次」串到 B 身上。区域字段本身在移动网络和云代理环境下就不稳，必须配合设备标识与客户端类型一起判。最常见的过度解读是把「首次出现」直接写成「疑似失陷」——首次只意味着「需要解释」，不意味着「已确认」。

八、判据与自欺：五种把自己骗过去的方式

狩猎没有告警替你兜底，判据就是唯一的护栏。下面五种自欺，每一种都对应一个能写进流程的强制动作。

自欺类型 具体表现 为什么会骗过自己 强行纠正口径
幸存者偏差 只基于留存期内、字段已采、采集端在线的那部分数据下结论 看得见的部分看起来就是全貌 每个结论必须附「本结论适用的数据覆盖范围」
把数据缺失误读成行为正常 查询返回空，直接写「未发现」 「没记下来」和「没发生」在结果里长得一样 先看覆盖率与采样率，空结果默认标「不可判定」
基线被污染 基线期里已有的活动被学成常态 此后同类行为永远不再偏离 基线标「洁净假设」，用无关判据定期抽查基线本身
确认偏误 先有「这里有问题」，任何长尾项都读成迹象 人会为预期寻找佐证 先写死否定条件再跑；第二人独立复跑同一张假设卡
只看命中不看覆盖率 报告写「发现若干起」，不写覆盖了多少资产 孤立数字天然显得像成果 命中数与覆盖率、未覆盖清单同表呈现

空结果必须再细分一层，否则「未发现」这三个字会掩盖完全不同的三种情况：

空结果情形 正确标注 错误标注
覆盖率充分、字段齐备、查无此项 证伪：在该范围与窗口内该假设不成立 「环境很干净」
字段缺失、留存不足或采样过狠 不可判定：需补数据源后复跑 「未发现异常」
资产根本不在采集范围内 未覆盖：结论不适用，列入范围缺口 「全网已排查」

一个能当体检指标用的反直觉结论：一份诚实的狩猎报告里，「不可判定」的条目应该比「确认发现」多得多。如果一份报告全是发现、没有一条不可判定，多半不是环境干净，而是判据没写严、覆盖率没算过，或者空结果被悄悄翻译成了「没问题」。

九、把结果转成资产：规则、数据需求、假设库

一次狩猎的终点不是「写出报告」，是分流。三分法看似简单，难点在于「剩下的」到底放哪、以及「什么都没猎到」该归档成什么。

结果类型 判定条件 转化动作 归档位置
能写成规则 判据稳定、误报可控、字段齐备、可准实时取到 转成检测规则，标注来源假设编号 检测规则库，并跟踪后续误报率
需要补数据源 假设成立但字段缺失、留存不足、采样过狠 提数据需求，写清字段、资产范围、留存、采样比例 数据治理需求队列
只能沉淀为假设 判据依赖人工上下文、无法规则化、一次性结论 连同范围、否定条件、覆盖率、复跑日期入假设库 假设库
纯排除结论 已证伪，且覆盖率足以支撑排除 归档为排除范围，写明范围、窗口、依据字段与失效条件 排除范围台账
不可判定 空结果由数据缺口造成 不做行为结论，转成缺口条目 数据缺口清单

「什么都没猎到」的正确产出是「排除范围 + 数据缺口清单」，不是零，也不是「环境很干净」。 排除范围是一条有作用域、有保质期的断言：它必须写清「在什么资产范围、什么时间窗、基于哪些字段与哪版数据模型，该假设不成立」。数据模型变了、资产变了、留存变了，它就失效，所以必须带复跑日期。数据缺口清单则是给数据治理的需求队列，每一条都要具体到「缺哪个字段、覆盖哪批资产、要留多久、采样比例多少」，而不是含糊一句「提升可见性」——后者既无法排期，也无法验收。

还有一层反直觉：如果把猎到的东西全都写成规则，狩猎会把自己做没——规则覆盖越多，「没有告警」的区域越小，狩猎的用武之地越小。这不是坏事，说明能力在往检测工程迁移。真正要保留的是「规则写不出来的那部分判断」，也就是那些依赖上下文、只能由人带着假设去判的东西。反过来，一次「什么都没猎到」若没有产出数据缺口清单，那多半是偷懒，不是干净。

十、度量：成对上报，别用发现数糊弄自己

指标 定义与口径 它防的是什么 常见误用
假设通过率 被证实数 / 已判定假设总数（证伪也计入分母） 假设质量与来源是否靠谱 当绩效考核，逼人写一定会命中的软假设
发现数 可复现、可归因的检测缺口或活动 产出是否真实 单看此数，激励挑软柿子与「疑似也算」
转化为规则数 由狩猎结论进入规则库的条数 结论有没有变成长期能力 只数新增，不跟踪规则后续误报与存活
数据源补齐数 由狩猎反推并已落地的数据需求 数据治理有没有被真正推动 把「提了需求」当成「补齐了」
复现率 第二人或第二次独立跑出同样结论的比例 结论是否可依赖 几乎从不统计，是最被低估的指标
不可判定占比 空结果里被标「不可判定」的比例 报告是否诚实、数据账是否清楚 被当成「能力不足」而刻意压低
假设库增长与清理 新增数对照标记失效/归档数 假设库是否还可用 只增长不清理，半年后变成垃圾场

「发现数」是最不该单独考核的指标，因为它能被「写更保守的假设」稳定刷高。判断一个指标有没有失效，有个简单标准：如果它能靠调整假设难度刷上去，它就已经不能当 KPI 了。度量必须成对出现——发现数配覆盖率，通过率配假设总数，转化为规则数配规则的存活率与误报率。「复现率」和「不可判定占比」看着不体面，却最能反映体系成熟度：前者说明结论经得起第二个人跑，后者说明团队肯把「不知道」如实写出来。

十一、一次完整狩猎的时间线推演

阶段 动作 产出 关键纪律
T0 假设登记 写假设卡：预期、否定条件、必需字段、范围、窗口 一份可归档的假设卡 否定条件先写死，缺一项不予立项
T0+ 字段核对 逐字段确认数据源、覆盖率、空值语义、时间基准 字段可用性清单 字段不齐就降级为「待补数据」，不硬跑
T+1 覆盖率核对 算资产覆盖率、留存是否够、采样比例 覆盖率与未覆盖清单 覆盖率必须与最终结论同表出现
T+2 判据固化 定基线窗口、洁净标注、变更日历、已知集合 可复跑的查询与参数 参数写成常量，不留在人脑里
T+3 查询与候选集 按第六章的顺序生成候选，先过滤再反连接 候选集 + 覆盖标注 有效性过滤必须早于反连接

T+5 独立复跑 第二人用同一张假设卡独立跑一遍 复现结论 结论不一致时回到判据，不回到「感觉」
T+6 判定 证实 / 证伪 / 不可判定，三选一 判定记录 空结果禁止直接写「未发现」
T+7 转化分流 规则 / 数据需求 / 假设库 / 排除范围 / 缺口清单 分流动作清单 每条都带去向与责任人
T+8 归档 更新假设卡、排除范围、缺口清单、复跑日期 可检索的归档条目 没有归档的狩猎等于没发生过
定期 复跑 数据模型、资产范围或留存变更后重跑 结论有效性维护 排除范围到期自动回到待判定

整条时间线里最容易被跳过的是「字段核对」和「独立复跑」，而恰恰是这两步决定结论能不能叫「结果」。另一个常见截断是把 T+6 判定当终点：判定只是对假设的回答，T+7 分流与 T+8 归档才把它变成组织资产。少了后面两步，同一批人半年后还会把同一个假设再猎一遍。

P0 定义假设卡模板，强制「预期 / 否定 / 字段 / 范围」四要素 没有否定条件就不算假设 每次狩猎都有可归档、可复跑的假设卡
P0 建「字段 → 数据源 → 覆盖率 → 留存 → 采样」台账 空结果能否判定全靠这张账 一张有人维护、有版本的字段账
P0 统一时间基准与身份主键 跨源关联的前提，错位会让时序判据整体失效 时间字段有明确时区与时钟来源
P1 归一化进程树与会话字段 父子链与身份上下文能被正确 join 进程 GUID、会话 ID 跨源一致
P1 基线洁净标注 + 变更窗口登记 基线偏离不靠运气，发布不再等于全网异常 基线带洁净假设与变更日历
P1 假设库与排除范围带复跑日期 结论有保质期，不随数据模型变更而腐烂 每条排除范围都有作用域与失效条件
P2 双人独立复跑机制 对抗确认偏误 复现率有记录、结论可追溯
P2 度量成对上报 防止刷指标 报告里不存在孤立的数字
P2 规则转化后跟踪误报与存活率 避免规则库腐化 规则有退役与修订机制

结论

  • 狩猎的起点是「没有告警」，产出是确定性，不是惊喜；拿发现数考核它，会把它做成检测工程的欠账展销会。
  • 假设必须能被否定：预期看到什么、看到什么就否定、需要哪些字段，三件套缺一，那就只是感觉。
  • 数据模型决定你能问什么问题；字段账、时间基准、留存与采样，比换一个更聪明的分析工具靠前得多。
  • 「什么都没猎到」的正确产出是排除范围加数据缺口清单；写不出缺口清单的「干净」，多半是没查清。
  • 别用孤立的数字汇报狩猎：发现数配覆盖率，通过率配假设总数，规则数配存活率，再补上复现率与不可判定占比。

真要只做一件事，就从把下一句「我去翻翻日志」改写成一张带否定条件的假设卡开始。翻日志不叫威胁狩猎；带着一个写死了否定条件的假设走进去，并且愿意接受「它不成立」，才叫。
